## Actual

- El push es solo operativo: `pushPayloadSchema` (`src/server/push/sender.ts`) admite cinco eventos de solicitudes y
  ofertas, con ids y sin texto; `public/sw.js` replica ese schema a mano y arma títulos fijos.
- `push_subscriptions` guarda las suscripciones por usuario; `sendPushNotification(userIds, event)` las recorre en serie

- El admin no tiene forma de avisar nada a comercios ni repartidores.

## Propuesto

### Tablas

```sql
announcements (
  id uuid pk default gen_random_uuid(),
  audience text not null check (audience in ('merchants','couriers','all')),
  title text not null check (char_length(title) between 1 and 60),
  body text not null check (char_length(body) between 1 and 140),
  cta text not null default 'none'
    check (cta in ('none','merchant_plan','merchant_new_request','courier_feed')),
  visible_until timestamptz not null,
  created_by uuid not null references profiles(id),
  created_at timestamptz not null default now(),
  push_targets integer, push_sent integer, push_failed integer, push_recorded_at timestamptz,
  check ((audience = 'merchants' and cta in ('none','merchant_plan','merchant_new_request'))
      or (audience = 'couriers' and cta in ('none','courier_feed'))
      or (audience = 'all' and cta = 'none'))
)
announcement_dismissals (announcement_id fk on delete cascade, profile_id fk on delete cascade,
  dismissed_at timestamptz default now(), primary key (announcement_id, profile_id))
promotion_preferences (profile_id pk fk on delete cascade, push_promotions boolean not null,
  updated_at timestamptz default now())
```

Índice `announcements_visible_idx on announcements (visible_until desc, created_at desc)` y
`announcements_created_idx on announcements (created_at desc, id desc)`. Las tres tablas: RLS activada, `revoke all …
from public, anon, authenticated` y una policy `as restrictive for all to anon, authenticated using (false) with check
(false)` (`<tabla>_no_client_access`), el mismo patrón que las tablas de CC-029. Esa policy es una segunda barrera de
denegación y cumple el control global `rls_enabled.sql` (decisión D01 = A de la revisión de la PR #542).

### Consentimiento (decisión de Lautaro073)

- Al **activar las notificaciones**, el texto del pedido de permiso aclara que incluyen «avisos de tus pedidos y
  novedades o promociones de cadeApp». Si la suscripción se registra bien, la app llama a
  `set_promotions_opt_in(true)`: queda una fila con `push_promotions = true`.
- **Solo reciben promociones por push** los perfiles con `push_promotions = true`. Quien activó los avisos antes de
  este cambio no tiene fila y **no** recibe promos por push hasta volver a activarlos con el texto nuevo.
- El banner muestra la novedad a todos los del público elegido **salvo** a quien se dio de baja (`push_promotions =
  false`). La baja es el enlace «No recibir más promociones» del banner (`set_promotions_opt_in(false)`), exigido por el
  art. 27 de la Ley 25.326. La baja no afecta los avisos de pedidos.

### Público de un envío

Perfiles con `consent_status = 'active'` y:

- `merchants`: `role = 'merchant'` con fila en `merchants`;
- `couriers`: `role = 'courier'` con `couriers.status = 'approved'`;
- `all`: la unión de los dos.

### Evento push

`pushPayloadSchema` suma, estricto:

```json
{ "event": "announcement", "announcementId": "uuid", "title": "1–60", "body": "1–140",
  "url": "/merchant/plan | /merchant/requests/new | /merchant/dashboard | /courier/feed | /login" }
```

- `url` sale de un mapa fijo en el servidor: `merchant_plan` → `/merchant/plan`, `merchant_new_request` →
  `/merchant/requests/new`, `courier_feed` → `/courier/feed`; sin acción, la home del público (`/merchant/dashboard`,
  `/courier/feed`) o `/login` para `all` (que redirige a la home de cada rol).
- `public/sw.js` replica la validación (claves exactas, longitudes y `url` dentro de esa lista) y muestra título y
  cuerpo tal cual. Cualquier otra cosa cae en el aviso genérico de siempre.
- El texto es público y lo escribe el admin: no lleva datos personales.

### Envío

La server action del admin crea la novedad con `admin_create_announcement`, pide los destinatarios a
`announcement_push_recipients` (cliente de servicio, en `src/server/push`), envía con `sendPushNotification` y registra
el resultado con `admin_record_announcement_push`. El push es best-effort: si falla, la novedad igual queda creada y se
ve en el banner. `sendPushNotification` pasa a enviar en tandas de 10 en paralelo para no exceder el tiempo de la
función. Para no perder destinatarios con públicos grandes (decisión D02 = A de la revisión de la PR #542), los
destinatarios se paginan de a 1000 y las suscripciones se consultan de a 100 usuarios, también paginadas. Una falla
antes de enviar (sin ningún intento) no se registra como «0 enviados», y si el registro del resultado falla, la acción
lo informa.

## Seguridad y permisos

- **RLS:** las tres tablas nuevas, sin policies para clientes; todo pasa por las RPC.
- **Grants:** cada RPC pública con `revoke all … from public, anon, authenticated` y `grant execute … to
  authenticated`; `announcement_push_recipients` con `revoke all … from public, anon, authenticated` y `grant execute …
  to service_role`.
- **`security definer`** y `set search_path = public, pg_temp` en todas; las de admin llaman primero a
  `app_private.assert_admin_aal2()`.
- **Acceso directo frente a RPC:** sin grants de tabla para clientes; nadie escribe las tablas fuera de las RPC.
- **Datos que nunca devuelve:** las RPC del usuario no exponen quién creó la novedad, el público completo, los conteos
  ni la preferencia de otros.

## Concurrencia e idempotencia

- El tope diario se evalúa bajo advisory lock: dos altas simultáneas no pasan el tope.
- `dismiss_announcement` y `set_promotions_opt_in` son idempotentes (`on conflict`).
- `admin_record_announcement_push` registra una sola vez (`for update` y `push_recorded_at is null`).

## Compatibilidad, rollout y rollback

- **UI anterior contra el esquema nuevo:** todo es aditivo; la UI vieja no usa las RPC nuevas.
- **Esquema anterior contra la UI nueva:** las lecturas nuevas fallan y el banner no se muestra (error silencioso en la
  home, sin romperla); el admin ve su error. La migración va en la misma PR y `migrate-*` corre antes de `deploy-*`.
- **Service worker:** el SW nuevo entiende `announcement`; uno viejo cachea y muestra el aviso genérico hasta
  actualizarse.
- **Rollback:** borrar las RPC y las tablas; ningún flujo operativo depende de ellas.
