## Propuesto

### Decisiones de producto cerradas (ratificadas por Lautaro073 el 2026-10-18, NO reabrir)

- **1-A:** La RPC `public.get_request_cancellation_history` proyecta **exclusivamente** eventos con `action = 'courier_cancel_match'`. No incluye `report_no_show` ni `cancel_request` (que pertenecen a otros ciclos del pedido). No se abre `SELECT` directo a la tabla `request_cancellation_reasons` por RLS.
- **2-A:** Clasificación exacta y determinística basada en las opciones oficiales del formulario de cancelación del repartidor (`COURIER_CANCELLATION_REASONS`), incorporando `unforeseen_issue` para «Tuve un imprevisto», `vehicle_breakdown` para «Problema con el vehículo», `pickup_issue` para «No puedo llegar al punto de retiro», `personal_emergency` para «Emergencia», y mapeando cualquier motivo desconocido o texto libre a `other` / `"Otro motivo"`, sin heurísticas de subcadenas ni expresiones regulares sobre texto libre.
- **3-A:** Categorías normalizadas y allowlist estricta; `rawReason` es forzado a `null` para comercio y cadete (D3), visible únicamente para `admin` sobre los eventos de `courier_cancel_match`.
- **4-A:** Mostrar la cronología de cancelaciones de asignación en el **detalle del pedido** (`/merchant/requests/[id]` para el comercio y vista de viaje / actividad para el repartidor legitimado), incluso cuando la solicitud vuelve a `published`, distinguiendo visual y semánticamente «Cancelado por el repartidor» del estado `delivery_requests.status = 'cancelled'`.

### 1. Firma exacta de la RPC en PostgreSQL

```sql
create or replace function public.get_request_cancellation_history(
  p_request_id uuid,
  p_limit integer default 50,
  p_before_created_at timestamptz default null,
  p_before_id uuid default null
)
returns jsonb
language plpgsql
security definer
stable
set search_path = public, pg_temp;
```

### 2. Estructura versionada de salida (`version: "1.0"`)

La función retorna un objeto `jsonb` con contrato estricto, acotado exclusivamente a eventos `courier_cancel_match`:

```json
{
  "version": "1.0",
  "requestId": "a0000000-0000-0000-0000-000000000001",
  "events": [
    {
      "id": "c0000000-0000-0000-0000-000000000001",
      "action": "courier_cancel_match",
      "actionLabel": "Cancelado por el repartidor",
      "category": "vehicle_breakdown",
      "categoryLabel": "Problema con el vehículo",
      "createdAt": "2026-10-18T20:30:00.000Z",
      "actor": {
        "id": "b0000000-0000-0000-0000-000000000001",
        "role": "courier",
        "displayName": "Juan P."
      },
      "offerId": "d0000000-0000-0000-0000-000000000001",
      "rawReason": null
    }
  ],
  "pagination": {
    "limit": 50,
    "hasMore": false,
    "nextCursor": null
  }
}
```

#### Definición de tipos y nullabilidad real:

| Campo | Tipo | Nulable | Descripción / Regla |
|---|---|---|---|
| `version` | `text` | No | Versión del payload (`"1.0"`). |
| `requestId` | `uuid` | No | ID del pedido consultado. |
| `events[].id` | `uuid` | No | ID del registro en `request_cancellation_reasons`. |
| `events[].action` | `text` | No | Acción registrada; **siempre** `'courier_cancel_match'` en esta proyección. |
| `events[].actionLabel` | `text` | No | Etiqueta oficial en español es-AR; **siempre** `"Cancelado por el repartidor"`. |
| `events[].category` | `text` | No | Categoría normalizada (`unforeseen_issue`, `vehicle_breakdown`, `pickup_issue`, `personal_emergency`, `other`). |
| `events[].categoryLabel` | `text` | No | Etiqueta amigable de la categoría en es-AR (ej. `"Problema con el vehículo"`). |
| `events[].createdAt` | `timestamptz` | No | Fecha y hora exacta del evento en ISO 8601 UTC. |
| `events[].actor` | `object` | **Sí** | `null` si `actor_id` es `NULL` (perfil eliminado por `ON DELETE SET NULL`). |
| `events[].actor.id` | `uuid` | No | ID del perfil del actor. |
| `events[].actor.role` | `text` | No | Rol del actor (`'courier'`). |
| `events[].actor.displayName` | `text` | No | Nombre público seguro del perfil (`profiles.display_name`), con fallback a `"Repartidor"` si estuviera vacío. |
| `events[].offerId` | `uuid` | **Sí** | ID de la oferta vinculada, o `null` si fue desvinculada por `ON DELETE SET NULL`. |
| `events[].rawReason` | `text` | **Sí** | **`null` obligatorio para `merchant` y `courier` (D3)**. Solo accesible para `admin` sobre eventos `courier_cancel_match`. |
| `pagination.limit` | `integer` | No | Límite efectivo aplicado (acotado entre 1 y 100). |
| `pagination.hasMore` | `boolean` | No | `true` si existen más eventos anteriores para paginar (calculado **después** del filtrado de rol y acción). |
| `pagination.nextCursor` | `object` | **Sí** | `{ "beforeCreatedAt": "...", "beforeId": "..." }` o `null` si `hasMore = false`. |

### 3. Keyset pagination y ordenamiento determinístico

- **Orden canónico:** `ORDER BY created_at DESC, id DESC`.
- **Filtro obligatorio base:** `rcr.request_id = p_request_id AND rcr.action = 'courier_cancel_match'`.
- **Filtro adicional por rol:** para repartidores, se agrega `AND rcr.actor_id = auth.uid()`.
- **Cláusula de cursor keyset:**
  ```sql
  where rcr.request_id = p_request_id
    and rcr.action = 'courier_cancel_match'
    and (
      v_role <> 'courier' or rcr.actor_id = v_uid
    )
    and (
      p_before_created_at is null
      or (rcr.created_at, rcr.id) < (p_before_created_at, p_before_id)
    )
  ```
- **Límite acotado:** `v_effective_limit := least(greatest(coalesce(p_limit, 50), 1), 100);`.
- Se consultan `v_effective_limit + 1` registros para determinar de forma determinística `hasMore` y extraer el `nextCursor`. El cálculo de `hasMore` se realiza estrictamente **sobre el conjunto filtrado por actor y acción**, impidiendo que eventos ajenos o de otras acciones afecten la paginación.
- **Validación del cursor:** `p_before_created_at` y `p_before_id` deben proporcionarse conjuntamente; si se envía uno solo sin el otro, la RPC rechaza la llamada con la excepción `VALIDATION_ERROR` (`P0001`).

### 4. Alcance de consulta y autorización por actor

La RPC **no acepta** `p_merchant_id` ni `p_actor_id` como argumentos del cliente. La identidad, rol y pertenencia se derivan exclusivamente de `auth.uid()` y de las filas verificadas en la base de datos:

| Actor | Pertenencia y validación SQL | Alcance de eventos visibles | Respuesta si no pertenece |
|---|---|---|---|
| **Comercio dueño** | `v_request.merchant_id = auth.uid()` con `role = 'merchant'` y `app_private.is_active_operational_actor()`. | Ve todos los eventos `courier_cancel_match` asociados a su pedido (`rcr.request_id = p_request_id`). | `NOT_FOUND` (no revela si el ID existe). |
| **Repartidor legitimado** | `role = 'courier'` y `app_private.is_active_operational_actor()`. Debe figurar como actor en al menos un evento `courier_cancel_match` del pedido. | Ve **únicamente sus propios eventos** (`rcr.actor_id = auth.uid()`). **Jamás lista cancelaciones de terceros repartidores.** | `NOT_FOUND` (no revela el pedido ni cancelaciones ajenas). |
| **Administrador** | `app_private.is_admin() = true`. | Ve todos los eventos `courier_cancel_match` del pedido, incluyendo `rawReason`. | `NOT_FOUND` solo si el pedido realmente no existe. |
| **Comercio ajeno** | `v_request.merchant_id <> auth.uid()`. | Ninguno. | `NOT_FOUND`. |
| **Repartidor no participante** | No figura como `actor_id` en ningún evento `courier_cancel_match` de este pedido. | Ninguno. | `NOT_FOUND`. |
| **Usuario anónimo (`anon`)** | Invocación sin sesión autenticada. | Ninguno. | Denegado en PostgreSQL por ausencia de `GRANT EXECUTE` (SQLSTATE `42501`); o excepción `'UNAUTHENTICATED'` (`P0001`) si se ejecuta sin `auth.uid()`. |
| **Consentimiento inactivo** | `consent_status <> 'active'` (salvo admin). | Ninguno. | `UNAUTHORIZED_ACTOR` (`P0001`). |

### 5. Allowlist de categorías y mapeo determinístico

Para cumplir con la Decisión 2-A y 3-A, se elimina cualquier heurística de subcadenas o expresiones regulares arbitrarias. La clasificación se basa en la correspondencia exacta normalizada (con `trim`, minúsculas y eliminación de acentos diacríticos únicamente para equiparar etiquetas oficiales) frente a las opciones de `COURIER_CANCELLATION_REASONS`:

| Opción oficial del formulario (`COURIER_CANCELLATION_REASONS`) | Código canónico admitido | Categoría normalizada (`category`) | Etiqueta segura es-AR (`categoryLabel`) |
|---|---|---|---|
| «Tuve un imprevisto» | `unforeseen_issue` | `unforeseen_issue` | `"Tuve un imprevisto"` |
| «Problema con el vehículo» | `vehicle_breakdown` | `vehicle_breakdown` | `"Problema con el vehículo"` |
| «No puedo llegar al punto de retiro» | `pickup_issue` | `pickup_issue` | `"No puedo llegar al punto de retiro"` |
| «Emergencia» | `personal_emergency` | `personal_emergency` | `"Emergencia"` |
| «Otro» o cualquier texto libre no reconocido / vacío | `other` | `other` | `"Otro motivo"` |

#### Reglas de clasificación:
1. Se admiten como entradas válidas equivalentes tanto las etiquetas literales del formulario como los códigos canónicos (`unforeseen_issue`, `vehicle_breakdown`, `pickup_issue`, `personal_emergency`, `other`).
2. No se aplican búsquedas difusas tipo `LIKE '%moto%'` ni inferencias sobre texto libre.
3. Todo texto libre arbitrario o valor no reconocido se asigna estrictamente a `other` / `"Otro motivo"`.

#### Política de texto libre (D3):
- Para `merchant` y `courier`: `rawReason` es forzado a `null`.
- Para `admin`: `rawReason` conserva el texto original registrado en la fila, únicamente para eventos `courier_cancel_match`.

## Seguridad y permisos

- **RLS:**
  - `public.request_cancellation_reasons` conserva su RLS activa intacta.
  - La policy `request_cancellation_reasons_admin` permanece como la única política de SELECT directo sobre la tabla, restringida a `app_private.is_admin()`.
  - **No se agrega ninguna policy amplia** tipo `USING (true)` ni se crea lectura directa por RLS para `authenticated`.
- **Grants y revokes:**
  - Tabla `public.request_cancellation_reasons`: `revoke all from public, anon, authenticated; grant select to authenticated;` (restringido por RLS). Ningún usuario cliente tiene permisos de `insert`, `update` o `delete`.
  - RPC `public.get_request_cancellation_history`:
    ```sql
    revoke all on function public.get_request_cancellation_history(uuid, integer, timestamptz, uuid) from public, anon, authenticated;
    grant execute on function public.get_request_cancellation_history(uuid, integer, timestamptz, uuid) to authenticated;
    ```
  - El rol `anon` **no tiene permiso de ejecución** (`REVOKE ALL`).
- **Diferenciación de llamadas no autenticadas (H03):**
  1. *Llamada anónima regular vía API / cliente PostgreSQL (rol `anon` sin permiso `EXECUTE`):* PostgreSQL deniega la ejecución en la capa de permisos antes de evaluar el cuerpo de la función:
     - Error: `permission denied for function get_request_cancellation_history` (SQLSTATE `42501`).
  2. *Llamada ejecutada en contexto con permiso pero sin UID (`auth.uid() IS NULL`):*
     - La guarda inicial de la función `if v_uid is null then raise exception 'UNAUTHENTICATED' using errcode = 'P0001'; end if;` aborta con código `'UNAUTHENTICATED'` (`P0001`).
- **`security definer` y hardening:**
  - La función se declara con `SECURITY DEFINER` y `SET search_path = public, pg_temp`.
  - Todos los accesos a tablas y funciones están calificados con el esquema `public.` o `app_private.`.
  - Validaciones defensivas inmediatas: autenticación, formato de UUID y cursor (`VALIDATION_ERROR`), verificación de rol y consentimiento operacional mediante `app_private.is_active_operational_actor()` (`UNAUTHORIZED_ACTOR`), y comprobación de pertenencia estricta en PostgreSQL (`NOT_FOUND`).
- **Acceso directo frente a RPC (barrera de base de datos):**
  - Un usuario autenticado no administrador que ejecute un `SELECT` directo a `public.request_cancellation_reasons` recibe `0` filas debido a la RLS.
  - Un intento de `INSERT`, `UPDATE` o `DELETE` directo es bloqueado por PostgreSQL por ausencia de grants.
  - La RPC es la **única vía autorizada** para proyectar esta historia, y aplica filtros ineludibles por `auth.uid()` y `rcr.action = 'courier_cancel_match'`.
- **Prevención de fugas de información:**
  - Si un comercio consulta un pedido que no le pertenece, o un cadete consulta un pedido donde no canceló asignación, la respuesta es `NOT_FOUND` (error `P0001`), impidiendo adivinar o enumerar UUIDs de pedidos ajenos.

## Concurrencia e idempotencia

- **Locks y orden:**
  - La RPC es `STABLE` y realiza operaciones exclusivamente de lectura mediante snapshots MVCC de PostgreSQL.
  - No solicita locks de fila explícitos (`FOR UPDATE` ni `FOR SHARE`).
  - No interfiere ni genera bloqueos mutuos (deadlocks) con `app_private.request_cycle`, `app_private.match_offer`, ni con las transacciones de escritura de pedidos.
- **Idempotencia:**
  - Ejecutar la RPC repetidamente con los mismos argumentos devuelve el mismo resultado mientras no se confirmen nuevos eventos de cancelación.
  - No produce efectos secundarios en la base de datos, no muta registros, no emite eventos y no inserta en `audit_log`.
- **Carreras concurrentes relevantes:**
  1. *Lectura concurrente con `courier_cancel_match`:* MVCC garantiza aislamiento. Si la transacción de cancelación confirma antes de que inicie la consulta, el evento aparece inmediatamente en la primera posición; si confirma después, se reflejará en la siguiente consulta o refetch.
  2. *Inserción de nuevo evento durante paginación keyset:* Si el comercio está paginando eventos históricos y ocurre una nueva cancelación simultánea, el cursor `(created_at, id) < (cursor_created_at, cursor_id)` garantiza que los eventos más antiguos se sigan recuperando en orden estricto sin desplazamientos de índice ni registros duplicados o salteados.
  3. *Reoferta y nuevo match concurrente:* Que la solicitud pase de `published` a `matched` con otro repartidor no altera la visibilidad del evento histórico previo para el comercio dueño; la fila histórica permanece inmutable en `request_cancellation_reasons`.

## Decisiones de producto

- **1-A (Ratificada 2026-10-18 por Lautaro073):** La RPC `public.get_request_cancellation_history` proyecta **exclusivamente** eventos con `action = 'courier_cancel_match'`. No incluye `report_no_show` ni `cancel_request`. Se rechaza abrir `SELECT` directo a la tabla `request_cancellation_reasons` por RLS.
- **2-A (Ratificada 2026-10-18 por Lautaro073):** Clasificación exacta y determinística basada en las opciones oficiales de `COURIER_CANCELLATION_REASONS`, incorporando `unforeseen_issue` para «Tuve un imprevisto», `vehicle_breakdown` para «Problema con el vehículo», `pickup_issue` para «No puedo llegar al punto de retiro», `personal_emergency` para «Emergencia», y mapeando cualquier motivo desconocido o texto libre a `other` / `"Otro motivo"`, sin heurísticas de subcadenas ni regex.
- **3-A (Ratificada 2026-10-18 por Lautaro073):** Categorías normalizadas y allowlist de motivos, ocultando el texto libre (`rawReason = null`) a comerciantes y repartidores para salvaguardar D3; visible únicamente para `admin` sobre eventos `courier_cancel_match`.
- **4-A (Ratificada 2026-10-18 por Lautaro073):** Cronología en el detalle del pedido; la solicitud reabierta tras cancelación del cadete se conserva en estado `published` y no se trata como solicitud cancelada.
- **Cero decisiones de producto abiertas:** No se introducen cambios de comportamiento sin definición previa.

## Motivo

La tarea T-365 resolvió la coherencia transaccional y el ciclo de ofertas (Frente I), pero dejó en evidencia que ni el comercio ni el repartidor disponen de un mecanismo seguro para consultar qué ocurrió con las asignaciones previas de un pedido.

Hoy, cuando un repartidor cancela una asignación (`courier_cancel_match`), el pedido regresa a `published` y el campo `delivery_requests.cancel_reason` se restablece a `NULL` para permitir nuevas ofertas. La información histórica del evento queda confinada en `public.request_cancellation_reasons`, cuya RLS solo permite lectura a administradores. Sin este CC, el comercio no puede comprender por qué su pedido volvió a estar disponible, ni puede auditar los motivos autorizados de los cadetes sin comprometer la privacidad o exponer texto libre arbitrario.

Este CC establece la RPC segura, determinística y tipada requerida para desbloquear T-373.

### Pruebas exigidas en la suite pgTAP (`supabase/tests/cc032_request_cancellation_history.sql`)

1. **Lectura legítima del comercio dueño:** Consulta SQL retorna un objeto `jsonb` con `version = '1.0'`, array `events` con `action = 'courier_cancel_match'`, `actionLabel = 'Cancelado por el repartidor'`, categoría normalizada conforme a allowlist oficial (`unforeseen_issue`, `vehicle_breakdown`, `pickup_issue`, `personal_emergency`, `other`), nombre público del repartidor, y `rawReason = null`.
2. **Lectura legítima del repartidor participante:** Repartidor que canceló consulta el pedido -> la función retorna un objeto `jsonb` conteniendo **exclusivamente sus propios eventos** `courier_cancel_match` con su nombre, categoría normalizada y `rawReason = null`.
3. **Aislamiento entre repartidores:** Repartidor A consulta un pedido donde él canceló una asignación y otro repartidor B canceló una asignación posterior -> la RPC retorna **únicamente** el evento del actor autenticado A; el evento del cadete B no aparece en el resultado.
4. **Repartidor ajeno denegado:** Repartidor que nunca participó en el pedido consulta la RPC -> la función lanza excepción `NOT_FOUND` (`P0001`), impidiendo confirmar la existencia del pedido.
5. **Comercio ajeno denegado:** Comercio consulta un pedido perteneciente a otro comercio -> la función lanza excepción `NOT_FOUND` (`P0001`).
6. **Denegación anónima (dos contextos de prueba):**
   - 6.1. *Rol `anon` sin permiso:* Invocación por rol `anon` en PostgreSQL falla con error de permisos de base de datos (`permission denied for function get_request_cancellation_history`, SQLSTATE `42501`) antes de ejecutar el cuerpo de la función.
   - 6.2. *Contexto sin UID:* Invocación con permiso de ejecución pero con `auth.uid() IS NULL` ejecuta la guarda defensiva y lanza la excepción controlada `'UNAUTHENTICATED'` (SQLSTATE `P0001`).
7. **Guardia de consentimiento operacional:** Usuario con rol `merchant` o `courier` pero con `consent_status = 'pending'` o `'reconsent_required'` -> la función lanza la excepción `'UNAUTHORIZED_ACTOR'` (`P0001`).
8. **Lectura administrativa completa:** Administrador (`is_admin() = true`) consulta cualquier pedido -> recibe todos los eventos `courier_cancel_match`, incluyendo el campo `rawReason` con el texto original registrado.
9. **Eventos múltiples y rematches:** Pedido asignado a Cadete 1 -> cancela (`courier_cancel_match`) -> republicado a `published` -> asignado a Cadete 2 -> cancela (`courier_cancel_match`) -> republicado -> comercio dueño consulta y recibe ambos eventos ordenados estrictamente por `created_at DESC, id DESC`.
10. **Paginación keyset del repartidor con eventos intercalados y desempate:**
    - Escenario: Cadete A cancela en T1, Cadete B cancela en T2, Cadete A cancela en T3.
    - El filtrado de actor (`rcr.actor_id = auth.uid()`) y acción (`courier_cancel_match`) se ejecuta **antes** de ordenar y paginar.
    - Cadete A consulta con `limit = 1`:
      - Página 1: retorna evento T3, `hasMore = true`, `nextCursor = { beforeCreatedAt: T3, beforeId: id3 }`.
      - Página 2 con cursor T3 y `limit = 1`: retorna evento T1, `hasMore = false`, `nextCursor = null`.
      - El evento T2 de Cadete B jamás ingresa al conjunto ni altera `hasMore`.
    - Empate exacto en `created_at` desempata por `id DESC`.
    - Cursor incompleto (`beforeCreatedAt` sin `beforeId` o viceversa) es rechazado inmediatamente con la excepción `'VALIDATION_ERROR'` (`P0001`).
11. **Manejo de nulos y tolerancia a borrado de perfiles:** Registro histórico con `actor_id = NULL` (perfil borrado) o `offer_id = NULL` -> la RPC responde correctamente con `actor: null` y `offerId: null` sin lanzar excepción ni fabricar identidades sintéticas.
12. **Bypass de tabla directa (RLS):** Intento de `SELECT * FROM public.request_cancellation_reasons` por parte de comercio o cadete autenticado devuelve 0 filas.
13. **Bypass de escritura directa:** Intento de `INSERT`, `UPDATE` o `DELETE` directo sobre `public.request_cancellation_reasons` por cliente autenticado es rechazado por PostgreSQL (`permission denied`).
14. **Invariante de estado republicado:** Tras `courier_cancel_match`, se comprueba en base de datos que `delivery_requests.status = 'published'`, `cancel_reason IS NULL`, y `get_request_cancellation_history` retorna el evento histórico persistido.
