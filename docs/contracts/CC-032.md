## Propuesto

### Decisiones de producto cerradas (NO reabrir)

- **1-A:** Crear una RPC de consulta y proyección segura `public.get_request_cancellation_history`, sin relajar la RLS ni abrir lectura directa sobre la tabla privada `public.request_cancellation_reasons`.
- **2-A:** Mostrar la cronología de cancelaciones de asignación en el **detalle del pedido** (`/merchant/requests/[id]` para el comercio y vista de viaje / actividad para el repartidor legitimado), incluso cuando la solicitud vuelve a `published`, distinguiendo visual y semánticamente «Cancelado por el repartidor» del estado `delivery_requests.status = 'cancelled'`.
- **3-A:** Categorías normalizadas y allowlist estricta; no exponer texto libre arbitrario ni datos privados a usuarios no administradores sin autorización expresa.

### 1. Firma exacta de la RPC en PostgreSQL

```sql
create or replace function public.get_request_cancellation_history(
  p_request_id uuid,
  p_limit integer default 50,
  p_before_created_at timestamptz default null,
  p_before_id uuid default null
)
returns jsonb
language plpgsql
security definer
stable
set search_path = public, pg_temp;
```

### 2. Estructura versionada de salida (`version: "1.0"`)

La función retorna un objeto `jsonb` con contrato estricto:

```json
{
  "version": "1.0",
  "requestId": "a0000000-0000-0000-0000-000000000001",
  "events": [
    {
      "id": "c0000000-0000-0000-0000-000000000001",
      "action": "courier_cancel_match",
      "actionLabel": "Cancelado por el repartidor",
      "category": "vehicle_breakdown",
      "categoryLabel": "Avería del vehículo",
      "createdAt": "2026-10-18T20:30:00.000Z",
      "actor": {
        "id": "b0000000-0000-0000-0000-000000000001",
        "role": "courier",
        "displayName": "Juan P."
      },
      "offerId": "d0000000-0000-0000-0000-000000000001",
      "rawReason": null
    }
  ],
  "pagination": {
    "limit": 50,
    "hasMore": false,
    "nextCursor": null
  }
}
```

#### Definición de tipos y nullabilidad real:

| Campo | Tipo | Nulable | Descripción / Regla |
|---|---|---|---|
| `version` | `text` | No | Versión del payload (`"1.0"`). |
| `requestId` | `uuid` | No | ID del pedido consultado. |
| `events[].id` | `uuid` | No | ID del registro en `request_cancellation_reasons`. |
| `events[].action` | `text` | No | Acción registrada (`'courier_cancel_match'`, `'report_no_show'`, `'cancel_request'`). |
| `events[].actionLabel` | `text` | No | Etiqueta en español es-AR (ej. `"Cancelado por el repartidor"`). |
| `events[].category` | `text` | No | Categoría normalizada (`vehicle_breakdown`, `pickup_issue`, `personal_emergency`, `traffic_or_distance`, `no_show`, `merchant_cancelled`, `other`). |
| `events[].categoryLabel` | `text` | No | Etiqueta amigable de la categoría en es-AR (ej. `"Avería del vehículo"`). |
| `events[].createdAt` | `timestamptz` | No | Fecha y hora exacta del evento en ISO 8601 UTC. |
| `events[].actor` | `object` | **Sí** | `null` si `actor_id` es `NULL` (perfil eliminado por `ON DELETE SET NULL`). |
| `events[].actor.id` | `uuid` | No | ID del perfil del actor. |
| `events[].actor.role` | `text` | No | Rol del actor (`'courier'`, `'merchant'`, `'admin'`). |

| `pagination.limit` | `integer` | No | Límite efectivo aplicado (acotado entre 1 y 100). |
| `pagination.hasMore` | `boolean` | No | `true` si existen más eventos anteriores para paginar. |
| `pagination.nextCursor` | `object` | **Sí** | `{ "beforeCreatedAt": "...", "beforeId": "..." }` o `null` si `hasMore = false`. |

### 3. Keyset pagination y ordenamiento determinístico

- **Orden canónico:** `ORDER BY created_at DESC, id DESC`.
- **Cláusula de cursor keyset:**
  ```sql
  where rcr.request_id = p_request_id
    and (
      p_before_created_at is null
      or (rcr.created_at, rcr.id) < (p_before_created_at, p_before_id)
    )
  ```
- **Límite acotado:** `v_effective_limit := least(greatest(coalesce(p_limit, 50), 1), 100);`.
- Se consulta `v_effective_limit + 1` registros para determinar de forma determinística `hasMore` y extraer el `nextCursor` sin penalización por `OFFSET` ni desalineación por inserciones concurrentes.
- El cursor exige que `p_before_created_at` y `p_before_id` se proporcionen juntos; si se envía uno solo, la RPC rechaza con `VALIDATION_ERROR`.

### 4. Alcance de consulta y autorización por actor

La RPC **no acepta** `p_merchant_id` ni `p_actor_id` como argumentos del cliente. La identidad, rol y pertenencia se derivan exclusivamente de `auth.uid()` y de las filas verificadas en la base de datos:

| Actor | Pertenencia y validación SQL | Alcance de eventos visibles | Respuesta si no pertenece |
|---|---|---|---|
| **Comercio dueño** | `v_request.merchant_id = auth.uid()` con `role = 'merchant'` y `app_private.is_active_operational_actor()`. | Ve **todos** los eventos de cancelación asociados a su pedido (`rcr.request_id = p_request_id`). | `NOT_FOUND` (no revela si el ID existe). |
| **Repartidor legitimado** | `rcr.actor_id = auth.uid()` con `role = 'courier'` y `app_private.is_active_operational_actor()`. Debe existir al menos un evento en este pedido donde él fue el actor. | Ve **únicamente sus propios eventos** (`rcr.actor_id = auth.uid()`). **Jamás lista cancelaciones de terceros repartidores.** | `NOT_FOUND` (no revela el pedido ni cancelaciones ajenas). |
| **Administrador** | `app_private.is_admin() = true`. | Ve **todos** los eventos del pedido, incluyendo `rawReason` para auditoría. | `NOT_FOUND` solo si el pedido realmente no existe. |
| **Comercio ajeno** | `v_request.merchant_id <> auth.uid()`. | Ninguno. | `NOT_FOUND`. |
| **Repartidor no participante** | No figura como `actor_id` en ningún evento de este pedido. | Ninguno. | `NOT_FOUND`. |
| **Usuario anónimo (`anon`)** | `auth.uid() IS NULL`. | Ninguno. | `UNAUTHENTICATED`. |
| **Consentimiento inactivo** | `consent_status <> 'active'` (salvo admin). | Ninguno. | `UNAUTHORIZED_ACTOR`. |

### 5. Allowlist de categorías y política de texto libre

Para cumplir con la Decisión 3-A, las reglas de privacidad D3 y los motivos establecidos en T-362, se establece un mapeo normalizado determinístico entre el motivo almacenado y las categorías autorizadas:

| Categoría (`category`) | Etiqueta segura (`categoryLabel`) | Criterio de clasificación del motivo original |
|---|---|---|
| `vehicle_breakdown` | `"Avería del vehículo"` | Texto contiene `averia`, `pinchadur`, `mecanic`, `moto`, `bici` o código `vehicle_breakdown`. |
| `pickup_issue` | `"Imprevisto en el retiro"` | Texto contiene `demora`, `cerrado`, `retiro`, `no puedo retirar`, o código `pickup_issue`. |
| `personal_emergency` | `"Emergencia personal"` | Texto contiene `emergencia`, `salud`, `personal`, o código `personal_emergency`. |
| `traffic_or_distance` | `"Problema de tránsito o distancia"` | Texto contiene `transito`, `distancia`, `trafico`, o código `traffic_or_distance`. |
| `no_show` | `"El repartidor no se presentó"` | Acción `report_no_show` o texto `no_show`. |
| `merchant_cancelled` | `"Cancelado por el comercio"` | Acción `cancel_request`. |
| `other` | `"Otro motivo"` | Motivo `otro`, texto libre que no coincide con las palabras clave anteriores o campo vacío. |

#### Política de visualización de texto libre:
- **Protección contra filtración de datos privados (D3):** Un repartidor podría ingresar inadvertidamente direcciones, teléfonos, datos de destinatarios o reclamos arbitrarios en el campo de texto libre al cancelar.
- Por diseño, la RPC asigna estrictamente `rawReason: null` para cualquier actor con rol `merchant` o `courier`. Comercios y repartidores visualizan **únicamente** la categoría normalizada y su etiqueta segura.
- Únicamente el `admin` recibe el valor de `rawReason` para trazabilidad de soporte e incidentes.

## Seguridad y permisos

- **RLS:**
  - `public.request_cancellation_reasons` conserva su RLS activa intacta.
  - La policy `request_cancellation_reasons_admin` permanece como la única política de SELECT directo sobre la tabla, restringida a `app_private.is_admin()`.
  - **No se agrega ninguna policy amplia** tipo `USING (true)` ni se crea lectura directa por RLS para `authenticated`.
- **Grants y revokes:**
  - Tabla `public.request_cancellation_reasons`: `revoke all from public, anon, authenticated; grant select to authenticated;` (restringido por RLS). Ningún usuario cliente tiene permisos de `insert`, `update` o `delete`.
  - RPC `public.get_request_cancellation_history`:
    ```sql
    revoke all on function public.get_request_cancellation_history(uuid, integer, timestamptz, uuid) from public, anon, authenticated;
    grant execute on function public.get_request_cancellation_history(uuid, integer, timestamptz, uuid) to authenticated;
    ```
  - El rol `anon` **no tiene permiso de ejecución**.
- **`security definer` y hardening:**
  - La función se declara con `SECURITY DEFINER` y `SET search_path = public, pg_temp`.
  - Todos los accesos a tablas y funciones están calificados con el esquema `public.` o `app_private.`.
  - Se ejecutan validaciones defensivas inmediatas: autenticación (`UNAUTHENTICATED`), formato de UUID y cursor (`VALIDATION_ERROR`), verificación de rol y consentimiento operacional mediante `app_private.is_active_operational_actor()` (`UNAUTHORIZED_ACTOR`), y comprobación de pertenencia estricta en PostgreSQL (`NOT_FOUND`).
- **Acceso directo frente a RPC (barrera de base de datos):**
  - Un usuario autenticado no administrador que ejecute un `SELECT` directo a `public.request_cancellation_reasons` recibe `0` filas debido a la RLS.
  - Un intento de `INSERT`, `UPDATE` o `DELETE` directo es bloqueado por PostgreSQL por ausencia de grants.
  - La RPC es la **única vía autorizada** para proyectar esta historia, y la RPC aplica filtros de pertenencia ineludibles por `auth.uid()`.
- **Prevención de fugas de información:**
  - Si un comercio consulta un pedido que no le pertenece, o un cadete consulta un pedido donde no tiene cancelaciones registradas, la respuesta es `NOT_FOUND` (error `P0001`), impidiendo adivinar o enumerar UUIDs de pedidos ajenos.

## Concurrencia e idempotencia

- **Locks y orden:**
  - La RPC es `STABLE` y realiza operaciones exclusivamente de lectura mediante snapshots MVCC de PostgreSQL.
  - No solicita locks de fila explícitos (`FOR UPDATE` ni `FOR SHARE`).
  - No interfiere ni genera bloqueos mutuos (deadlocks) con `app_private.request_cycle`, `app_private.match_offer`, ni con las transacciones de escritura de pedidos.
- **Idempotencia:**
  - Ejecutar la RPC repetidamente con los mismos argumentos devuelve el mismo resultado mientras no se confirmen nuevos eventos de cancelación.
  - No produce efectos secundarios en la base de datos, no muta registros, no emite eventos y no inserta en `audit_log`.
- **Carreras concurrentes relevantes:**
  1. *Lectura concurrente con `courier_cancel_match`:* MVCC garantiza aislamiento. Si la transacción de cancelación confirma antes de que inicie la consulta, el evento aparece inmediatamente en la primera posición; si confirma después, se reflejará en la siguiente consulta o refetch.
  2. *Inserción de nuevo evento durante paginación keyset:* Si el comercio está paginando eventos históricos y ocurre una nueva cancelación simultánea, el cursor `(created_at, id) < (cursor_created_at, cursor_id)` garantiza que los eventos más antiguos se sigan recuperando en orden estricto sin desplazamientos de índice ni registros duplicados o salteados.
  3. *Reoferta y nuevo match concurrente:* Que la solicitud pase de `published` a `matched` con otro repartidor no altera la visibilidad del evento histórico previo para el comercio dueño; la fila histórica permanece inmutable en `request_cancellation_reasons`.

## Motivo

La tarea T-365 resolvió la coherencia transaccional y el ciclo de ofertas (Frente I), pero dejó en evidencia que ni el comercio ni el repartidor disponen de un mecanismo seguro para consultar qué ocurrió con las asignaciones previas de un pedido.

Hoy, cuando un repartidor cancela una asignación (`courier_cancel_match`), el pedido regresa a `published` y el campo `delivery_requests.cancel_reason` se restablece a `NULL` para permitir nuevas ofertas. La información histórica del evento queda confinada en `public.request_cancellation_reasons`, cuya RLS solo permite lectura a administradores. Sin este CC, el comercio no puede comprender por qué su pedido volvió a estar disponible, ni puede auditar los motivos autorizados de los cadetes sin comprometer la privacidad o exponer texto libre arbitrario.

Este CC establece la RPC segura, determinística y tipada requerida para desbloquear T-373.

### Pruebas exigidas en la suite pgTAP (`supabase/tests/cc032_request_cancellation_history.sql`)

1. **Lectura legítima del comercio dueño:** Comercio dueño consulta su pedido con eventos de cancelación -> recibe estado 200, array de eventos con `actionLabel = 'Cancelado por el repartidor'`, categoría normalizada, nombre público del repartidor, y `rawReason = null`.
2. **Lectura legítima del repartidor participante:** Repartidor que canceló consulta el pedido -> recibe exclusivamente su propio evento de cancelación con su nombre y categoría normalizada, y `rawReason = null`.
3. **Aislamiento entre repartidores:** Repartidor consulta un pedido donde él canceló una asignación previa y otro repartidor canceló una asignación posterior -> la RPC retorna **únicamente** el evento del actor autenticado; el evento del tercer repartidor no aparece.
4. **Repartidor ajeno denegado:** Repartidor que nunca participó en el pedido consulta la RPC -> denegado con `NOT_FOUND` (no se confirma la existencia ni se listan eventos).
5. **Comercio ajeno denegado:** Comercio consulta un pedido perteneciente a otro comercio -> denegado con `NOT_FOUND`.
6. **Usuario anónimo denegado:** Invocación sin sesión autenticada (`auth.uid() IS NULL`) -> denegado con `UNAUTHENTICATED`.
7. **Guardia de consentimiento operacional:** Usuario con rol `merchant` o `courier` pero con `consent_status = 'pending'` o `'reconsent_required'` -> denegado con `UNAUTHORIZED_ACTOR`.
8. **Lectura administrativa completa:** Administrador (`is_admin() = true`) consulta cualquier pedido -> recibe todos los eventos históricos, incluyendo el campo `rawReason` con el texto original registrado.
9. **Eventos múltiples y rematches:** Pedido asignado a Cadete 1 -> cancela -> republicado a `published` -> asignado a Cadete 2 -> cancela -> republicado -> comercio dueño consulta y recibe ambos eventos ordenados estrictamente por `created_at DESC, id DESC`.
10. **Paginación keyset determinística:** Verificación de parámetros `p_limit`, `p_before_created_at`, `p_before_id`; desempate estricto por `id DESC`; verificación de flag `hasMore` y objeto `nextCursor`.
11. **Manejo de nulos y tolerancia a borrado de perfiles:** Registro histórico con `actor_id = NULL` (perfil borrado) o `offer_id = NULL` -> la RPC responde correctamente con `actor: null` y `offerId: null` sin lanzar excepción ni fabricar identidades sintéticas.
12. **Bypass de tabla directa (RLS):** Intento de `SELECT * FROM public.request_cancellation_reasons` por parte de comercio o cadete autenticado devuelve 0 filas.
13. **Bypass de escritura directa:** Intento de `INSERT`, `UPDATE` o `DELETE` directo sobre `public.request_cancellation_reasons` por cliente autenticado es rechazado por PostgreSQL (`permission denied`).
14. **Invariante de estado republicado:** Tras `courier_cancel_match`, se comprueba en base de datos que `delivery_requests.status = 'published'`, `cancel_reason IS NULL`, y `get_request_cancellation_history` retorna el evento histórico persistido.
