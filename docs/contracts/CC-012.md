## Propuesto (implementado en `cc/CC-012-incidents`)

### Dominio
- `INCIDENT_KINDS = ['no_show', 'payment_issue', 'damaged_goods', 'safety', 'other']` e `incidentKindSchema`: única
  fuente canónica. T-124 no puede mantener una lista paralela.
- `INCIDENT_DECISIONS = ['no_action', 'warning', 'preventive_suspension']` e `incidentDecisionSchema`.
- `incidentDescriptionHasContact`: 7 o más dígitos seguidos (admite espacios, puntos, guiones o paréntesis entre
  medio) o un correo. `Pagó con $ 2.000 y no tenía cambio para $ 500 del envío.` no se marca.
- `reportIncidentInputSchema`: `kind: incidentKindSchema` y `description` de 5 a 1000 caracteres sin datos de contacto.

### `report_incident` (migración `20260927120000_cc012_incidents_contract.sql`)
Implementación propia `SECURITY DEFINER`. Deja de usar `request_cycle`, cuya rama de incidentes queda sin
invocadores; la precedencia canónica se conserva:

1. `UNAUTHENTICATED` → `UNAUTHORIZED_ACTOR` si el rol no es comercio o repartidor. **El admin siempre recibe
   `UNAUTHORIZED_ACTOR`.** Sigue exigiendo consentimiento activo (CC-007).
2. `VALIDATION_ERROR`: `requestId` nulo, `kind` fuera de `INCIDENT_KINDS`, relato fuera de 5–1000 o con datos de
   contacto.
3. `NOT_FOUND`.
4. Participación: el comercio tiene que ser el dueño. El repartidor tiene que ser el de la oferta `accepted`, y solo
   después se evalúa su elegibilidad (`NOT_FOUND` → `COURIER_SUSPENDED` → `COURIER_NOT_APPROVED`).
5. Estado (D05-A): el comercio en `matched`, `in_transit` y `delivered`; el repartidor solo en `matched` e
   `in_transit`. Cualquier otro caso → `INVALID_STATE_TRANSITION`. En `delivered` con más de 24 h →
   `INCIDENT_WINDOW_EXPIRED`.
6. `RATE_LIMITED` (`max_incidents_per_min`).

Los códigos declarados no cambian.

### `admin_resolve_incident(p_incident_id uuid, p_decision text, p_reason text) → jsonb`
- Entrada `{ incidentId, decision, reason (trim 1–500) }`. Salida
  `{ incidentId, status: 'resolved' | 'dismissed', decision, courierId: uuid | null, withdrawnOffersCount }`.
- Precedencia: `app_private.assert_admin_aal2()` (`UNAUTHENTICATED` → `UNAUTHORIZED_ACTOR` → `AAL2_REQUIRED`) →
  `VALIDATION_ERROR` → `REASON_REQUIRED` → `NOT_FOUND` → `INVALID_STATE_TRANSITION` → operación.
- Solo resuelve incidentes `open` o `reviewing`; `resolved` o `dismissed` → `INVALID_STATE_TRANSITION`.
- Mapeo: `no_action → dismissed`, `warning → resolved`, `preventive_suspension → resolved`. `resolution` guarda
  `"<decision>: <motivo>"`; no hay tabla nueva.
- `preventive_suspension` (D06-A) **no recibe `courierId`**. En la misma transacción:
  1. bloquea el incidente;
  2. toma la oferta `accepted` de su solicitud (si no hay → `INVALID_STATE_TRANSITION`);
  3. bloquea al repartidor (inexistente → `NOT_FOUND`; ya suspendido → `INVALID_STATE_TRANSITION`);
  4. aplica los mismos efectos que `admin_suspend_courier`: `status = 'suspended'`, `available = false`,
     `deactivated_at = now()` y ofertas `pending` → `withdrawn`, con conteo;
  5. resuelve el incidente;
  6. registra la auditoría.
- Auditoría: `audit_log` con `action = 'admin_resolve_incident'`, `target_type = 'incident'` y
  `target_id = incidentId`.
  - `before`: `{ status }`.
  - `after`: `{ status, decision, reason, requestId, courierId, courierSuspended, withdrawnOffersCount }`.
  - Sin datos del destinatario.
- Cualquier error revierte suspensión, ofertas, incidente y auditoría. Está probado con una falla forzada en la
  auditoría.

### `admin_list_incidents(p_statuses text[], p_cursor_created_at timestamptz, p_cursor_id uuid, p_limit integer) → jsonb`
- Entrada `{ statuses (1–4 de INCIDENT_STATUSES), cursor?: { createdAt, id } | null, limit? (1–50, 20 por defecto) }`.
- Salida `{ items: [{ id, requestId, kind, description, status, resolution, createdAt, reporterId, reporterRole,
  reporterName }], nextCursor: { createdAt, id } | null }`.
- Keyset: `ORDER BY created_at DESC, id DESC`. Página siguiente:
  `created_at < c.createdAt OR (created_at = c.createdAt AND id < c.id)`. El cursor viaja con microsegundos (`.US`).
- `SECURITY DEFINER` con `assert_admin_aal2()`: `authenticated` no tiene `EXECUTE` sobre el preámbulo, así que una
  función `INVOKER` no podría invocarlo. Es solo lectura, igual que el resto de las RPC admin.
- Índice `incidents_status_created_cursor_idx (status, created_at DESC, id DESC)`.

### Tabla y RLS
- Normaliza a `'other'` los `kind` no canónicos y agrega `incidents_kind_valid`.
- Elimina `incidents_insert_authenticated` e `incidents_write_admin`, y revoca `INSERT`/`UPDATE`/`DELETE` sobre
  `incidents` a `anon` y `authenticated`.
- Conserva `incidents_select_reporter` e `incidents_select_admin`.
- Las únicas fronteras de escritura son `report_incident` y `admin_resolve_incident`.

### Server
- `adminResolveIncidentRpc` y `adminListIncidentsRpc` en `src/server/rpc/admin.ts`, validados con Zod en la frontera.
  Si el caller intenta mandar un `courierId`, no viaja a la RPC.
- `src/types/database.types.ts`: se agregan las dos funciones. La entrada se escribió a mano porque `pnpm db:types`
  no corre sin Supabase local; CI la regenera y compara (`git diff --exit-code`).

## Motivo

T-124 (bandeja A05, reporte desde C06/R07, resolución y suspensión cautelar) no puede cumplir su DoD con el contrato
vigente:
- el admin y el repartidor sobre `delivered` pueden reportar;
- la RLS permite saltarse la RPC;
- la resolución no está auditada ni exige aal2;
- la suspensión desde la UI permitía elegir el `courierId`;
- la paginación solo por `created_at` pierde o duplica filas con empates.

## Decisiones

- **D05-A:** matriz de reporte por actor y estado (arriba).
- **D06-A:** `preventive_suspension` es parte de `admin_resolve_incident`; el repartidor se deriva en Postgres.
- **D07-A:** un único contract-change de incidentes antes del GREEN de T-124.
- **D08:** `src/app/trips/[id]/page.tsx` es un cruce histórico de zona, pero no requiere visto bueno de P2 para una
  PR de Lautaro073 (aplica al retomar T-124).
