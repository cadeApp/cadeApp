# CC-038 — `admin_upsert_publication_plan` genera el código del plan

- **Issue:** #518 (label `contract-change`) · **Abre:** Lautaro073 (agente) · **Fecha:** 2026-10-22
- **Contrato afectado:** RPC `public.admin_upsert_publication_plan` (CC-029) · `src/domain/rpc-contracts.ts`
  (`adminUpsertPublicationPlanInputSchema`) · helper nuevo `app_private.publication_plan_code_base(text)`
- **Tareas bloqueadas:** T-411 (#517)
- **Depende de:** CC-029 (créditos de publicación y catálogo de planes)

## Actual

- `public.admin_upsert_publication_plan(p_plan_id uuid, p_code text, p_name text, p_kind text, p_monthly_credits
  integer, p_reference_price_ars integer, p_active boolean, p_sort integer)`
  (`supabase/migrations/20261017090000_t369_publication_credits.sql:1680-1756`):
  - exige `p_code` con `^[a-z0-9][a-z0-9_-]{1,39}$`; si falta o no cumple, `VALIDATION_ERROR`;
  - al crear, un código ya usado da `VALIDATION_ERROR`;
  - al editar, reescribe `code = v_code`: el código se puede cambiar.
- `adminUpsertPublicationPlanInputSchema` (`src/domain/rpc-contracts.ts:961`) exige `code` con la misma regex.
- El formulario «Nuevo plan» del admin (`src/features/admin/components/publication-plans-manager.tsx`) tiene el campo
  «Código», obligatorio: el admin tiene que inventar un identificador técnico.
- `publication_plans.code` es `text not null unique` con el check de la misma regex. Solo lo muestra la tabla del
  catálogo del admin; ninguna otra lectura ni RPC lo usa para decidir nada.

## Propuesto

La firma de la RPC **no cambia** (los grants, `database.types.ts` y los llamadores posicionales siguen valiendo). Cambia
la semántica de `p_code`:

- **Alta con `p_code` nulo o vacío** (lo que manda la app desde T-411): la base genera el código desde `p_name`:
  1. `app_private.publication_plan_code_base(p_name)`: pasa a minúsculas, saca tildes, diéresis, `ñ` y `ç`
     (`translate`, sin extensiones), reemplaza cada tramo de caracteres fuera de `[a-z0-9]` por un guion, recorta los
     guiones de los bordes y corta en 32 caracteres. Si queda con menos de 2 caracteres, usa `plan`.
     Ejemplos: «Plan Básico 20» → `plan-basico-20`; «Ñandú  Premium!!» → `nandu-premium`; «¡¡» → `plan`.
  2. Bajo `pg_advisory_xact_lock(hashtext('cc038:publication-plan-code'))`, si la base está libre la usa; si no, toma
     el mayor sufijo numérico existente de `base` o `base-N` (N de 1 a 7 dígitos) y usa `base-(N+1)`: el segundo
     «Plan Básico 20» queda `plan-basico-20-2`. Con la base de hasta 32 caracteres, el código cumple el check de la
     tabla (≤ 40); si un sufijo lo pasara, la RPC responde `INTERNAL_ERROR` sin escribir.
- **Alta con `p_code` no vacío** (compatibilidad con la UI vigente durante el rollout): igual que hoy, se valida la
  regex y la unicidad (`VALIDATION_ERROR`), bajo el mismo advisory lock.
- **Edición:** el código es **inmutable**. `p_code` nulo, vacío o igual al vigente lo conserva; distinto da
  `VALIDATION_ERROR` sin cambiar nada. El `update` ya no escribe `code`.
- Salida, errores, auditoría y el resto de las validaciones: sin cambios. La salida sigue devolviendo `code`.
- `adminUpsertPublicationPlanInputSchema` deja de tener `code` (el objeto no es estricto: una clave `code` extra se
  descarta). El wrapper manda `p_code: null`.

## Seguridad y permisos

- **RLS:** no cambia ninguna policy; `publication_plans` sigue con RLS sin acceso directo para clientes.
- **Grants y revokes:** la RPC conserva los suyos (`create or replace` con la misma firma). El helper nuevo lleva
  `revoke all on function app_private.publication_plan_code_base(text) from public, anon, authenticated` y ningún grant.
- **`security definer`**, `set search_path = public, pg_temp` y `assert_admin_aal2()` primero: sin cambios. El helper es
  `language sql immutable`, `set search_path = public, pg_temp`, sin acceso a tablas.
- **Acceso directo frente a RPC:** el código solo lo escribe la RPC; la tabla no tiene grants de escritura para clientes.
- **Datos que nunca devuelve:** sin cambios.

## Concurrencia e idempotencia

- Dos altas simultáneas con el mismo nombre se serializan por el advisory lock transaccional: la segunda calcula el
  sufijo después de que la primera confirma, así que nunca chocan con la unicidad de `code`. La edición no toma el
  lock porque no escribe el código.
- `unique (code)` sigue como respaldo.
- El alta no es idempotente (igual que hoy): un reintento crea otro plan con el siguiente sufijo.

## Privacidad / matriz de exposición

No cambia: el código del plan no es un dato personal y solo lo ve el admin.

## Compatibilidad, rollout y rollback

- **UI anterior contra el esquema nuevo:** la UI vigente manda `p_code` explícito al crear y el código vigente al
  editar: las dos cosas siguen funcionando. Solo fallaría si el admin cambiara el código de un plan existente durante
  la ventana entre `migrate` y `deploy` (`VALIDATION_ERROR`, sin cambiar nada).
- **Esquema anterior contra la UI nueva:** la UI nueva manda `p_code` nulo; la RPC vieja respondería
  `VALIDATION_ERROR`. Por eso la migración va en la misma PR y `migrate-*` corre antes de `deploy-*` en cada entorno.
- **Backfill:** no hace falta; los códigos existentes quedan como están.
- **Rollout ordenado:** una sola PR (T-411) con migración, contrato, UI y pruebas.
- **Condición para retirar la compatibilidad:** cuando la UI nueva esté en producción, un CC posterior puede quitar
  `p_code` de la firma. No se hace en T-411.
- **Rollback:** volver a crear la función de `20261017090000_t369_publication_credits.sql` y borrar el helper; los
  códigos generados cumplen el check y siguen siendo válidos.

## Decisiones de producto

- El código del plan es un identificador interno: lo genera el sistema desde el nombre y el admin no lo escribe —
  Lautaro073, 2026-10-22.
- El código es fijo después del alta y la tabla del catálogo lo sigue mostrando como referencia para distinguir planes
  con el mismo nombre — Lautaro073 (vía agente, con autorización explícita para decidir), 2026-10-22.

## Motivo

Lautaro073 (2026-10-22): «es algo que un admin no debería escribir, eso lo debería armar solo el sistema». Generarlo en
la base, bajo lock, garantiza un código válido y único sin depender del cliente.
