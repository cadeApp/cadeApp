## Actual

- `createDeliveryRequestAction` (`src/features/requests/actions.ts:21-208`) hace una secuencia de escrituras
  separadas: inserta `delivery_requests`, luego `delivery_request_contacts`, un drop, su contacto privado y recién
  después llama a `publish_request` (`actions.ts:195-198`). Si una escritura posterior falla, el error se devuelve
  sin una transacción que revierta el borrador ya creado.
- El flujo actual solo recibe una entrega mediante `createDeliveryRequestSchema`
  (`src/features/requests/schemas.ts:9-107`). La publicación existente recibe solo `requestId` y devuelve el
  resultado de la transición (`src/domain/rpc-contracts.ts:52-64`); no crea filas.
- `public.publish_request(uuid)` es una RPC `security definer` que delega en `app_private.request_cycle`
  (`supabase/migrations/20260925170000_cc007_consent_enforcement.sql:706-927`, redefinida por las migraciones de
  T-340). El helper toma `delivery_requests for update`, valida actor, estado, suscripción, zonas, distancia,
  rate limit, drops y contactos, y publica.
- CC-022 ya define `delivery_request_drops` y `delivery_request_drop_contacts`, sus RLS/grants y el límite
  `platform_settings.max_drops_per_request` (`supabase/migrations/20261009200000_t340_multi_drop.sql:6-281`).
  El modelo multi-drop existe; lo que falta es que el escritor de la UI pueda crearlo y publicarlo como una sola
  operación.

## Propuesto

### RPC pública

Crear, en una migración nueva, la firma explícita:

```sql
public.create_and_publish_multi_drop(p_payload jsonb) returns jsonb
```

`p_payload` debe ser un objeto JSON con exactamente estas claves y tipos; no se aceptan claves desconocidas ni
valores coercionados:

```json
{
  "requestId": "uuid estable generado por CreateRequestForm para esta intención de creación",
  "pickupZoneId": "uuid",
  "pickupAddress": "texto no vacío, máximo 200",
  "pickupLat": "number|null",
  "pickupLng": "number|null",
  "fixedPriceArs": "integer positivo|null",
  "autoAssign": "boolean",
  "drops": [
    {
      "dropoffZoneId": "uuid",
      "dropoffAddress": "texto no vacío, máximo 200",
      "dropoffLat": "number|null",
      "dropoffLng": "number|null",
      "recipientName": "texto no vacío, máximo 100",
      "recipientPhone": "texto no vacío, 8..30",
      "recipientConsentDeclared": true,
      "packageType": "package_type vigente",
      "recipientPaymentMethod": "cash|transfer|to_agree",
      "needsChange": "boolean",
      "cashChangeAmount": "integer positivo|null",
      "notes": "texto|null, máximo 500"
    }
  ]
}
```

Reglas de entrada:

- `drops.length` está entre 1 y `platform_settings.max_drops_per_request`; el límite se consulta en la base y no
  se hardcodea.
- Coordenadas vienen ambas o ninguna y deben estar dentro de Aguilares; si faltan, la RPC usa centroides como hoy.
- `cash` + `needsChange = true` exige monto positivo; cualquier otro medio o `needsChange = false` exige monto
  `NULL`. Cada drop cumple el `check` de CC-022.
- `autoAssign = true` exige `fixedPriceArs` positivo. El precio es por entrega; los totales posteriores siguen
  siendo derivados por la cantidad de drops, sin registrar pagos.
- `requestId` funciona como clave de idempotencia y también como `delivery_requests.id`. `CreateRequestForm` genera
  una sola clave con `crypto.randomUUID()` por intención de creación y la conserva en un `useRef` o estado estable.
  Doble clic, respuesta HTTP perdida, error de red y retry explícito del mismo payload reutilizan ese UUID. Si se
  necesita preservar el retry tras un reload, se persiste únicamente el UUID —nunca PII— en almacenamiento acotado
  a la pestaña y a esa intención. Al completar con éxito se limpia la clave; una solicitud realmente nueva genera
  otro UUID. Dos formularios independientes no comparten identificador.
- La Server Action valida con Zod el UUID recibido y lo pasa intacto al wrapper y a la RPC; nunca genera una clave
  nueva por invocación. `requestId` no es secreto ni autorización: `auth.uid()`, el rol merchant y la titularidad
  son la barrera. Un actor ajeno recibe `NOT_FOUND`, sin oráculo de existencia.
- Una edición de cualquier dato después de un resultado incierto no reutiliza silenciosamente el UUID con contenido
  diferente: la UI advierte el conflicto o inicia explícitamente una intención nueva con otro UUID.
- En un reintento del mismo comercio con payload canónico idéntico, la RPC devuelve la solicitud existente con
  `idempotent = true` y no publica ni notifica de nuevo. El mismo UUID con payload distinto devuelve
  `VALIDATION_ERROR`; un UUID perteneciente a otro comercio devuelve `NOT_FOUND`.

Respuesta exitosa:

```json
{
  "requestId": "uuid",
  "status": "delivery_request_status actual",
  "publishedAt": "ISO timestamp",
  "expiresAt": "ISO timestamp",
  "routeDistanceM": "integer|null",
  "fixedPriceArs": "integer|null",
  "autoAssign": "boolean",
  "dropsCount": "integer",
  "idempotent": "boolean"
}
```

En el primer éxito, `status` es `published` e `idempotent` es `false`. En un reintento posterior, `status` refleja el
valor actual de `delivery_requests.status` según el enum compartido —incluidos `matched`, `in_transit`, `delivered`,
`cancelled` o `expired` cuando corresponda— e `idempotent` es `true`. `publishedAt` conserva la publicación original;
`expiresAt`, `routeDistanceM`, `fixedPriceArs`, `autoAssign` y `dropsCount` son los valores originales o derivados
persistidos de la solicitud. El retry no vuelve a publicar ni emite otra notificación de creación.

La RPC ejecuta, en una única transacción y en este orden:

1. Inserta `delivery_requests` con `id = requestId`, `merchant_id = auth.uid()`, `pickup_zone_id`, `status = 'draft'`,
   `fixed_price_ars` y `auto_assign`. Los campos legacy de destino `dropoff_zone_id`, `package_type` y
   `recipient_payment_method` quedan `NULL`; `needs_change` conserva su default `false`; `notes` y
   `cash_change_amount` quedan `NULL`.
2. Inserta `delivery_request_contacts` con `request_id`, `pickup_address`, `pickup_lat` y `pickup_lng`. Las columnas
   legacy de destino `dropoff_address`, `dropoff_lat`, `dropoff_lng`, `recipient_name`, `recipient_phone` y
   `recipient_consent_declared` quedan `NULL`.
3. Inserta N `delivery_request_drops` con `position = 1..N`, zona, paquete, medio de pago y `needs_change`, y N
   `delivery_request_drop_contacts` con dirección/coordenadas, destinatario, teléfono, consentimiento, notas y monto
   exacto de cambio de cada entrega.
4. Llama a `app_private.request_cycle('publish_request', requestId)`. Como el request ya tiene N drops válidos, la
   rama mergeada de `request_cycle` no ejecuta el puente legacy, reservado para requests con cero drops.

Una excepción en cualquier validación, insert, límite o publicación aborta el conjunto y deja cero filas creadas.
La fuente de verdad de cada alta nueva son exclusivamente `delivery_request_drops` y
`delivery_request_drop_contacts`: jamás se copian datos del destino al padre ni al contacto legacy. La ruta legacy
existente de un drop + `publish_request` continúa vigente con su propio esquema, sin migrarse ni redefinirse en este
CC. Los lectores nuevos no usan columnas legacy como fallback.

## Seguridad y permisos

- `public.create_and_publish_multi_drop(jsonb)` será `security definer` con `set search_path = public, pg_temp`.
  Se hará `revoke all ... from public, anon, authenticated` y luego `grant execute ... to authenticated`.
- La función obtiene `auth.uid()`, exige perfil `merchant` con consentimiento activo y usa ese actor como
  `merchant_id`; nunca acepta un `merchant_id` desde el payload. Admin, courier, anónimo, merchant sin consentimiento
  y otro merchant son rechazados.
- La RPC nueva no otorga grants de inserción a clientes ni habilita acceso directo adicional a las tres tablas. La
  ruta legacy de borrador conserva los grants/RLS de CC-022 durante el rollout, pero el escritor nuevo escribe todo
  dentro de la RPC.
- `app_private.request_cycle` continúa siendo `security definer`, con `set search_path = public, pg_temp`, y
  permanece revocado para `public`, `anon` y `authenticated`. No se agrega ningún helper `app_private.*` ejecutable
  por clientes. Si la implementación extrae validaciones a un helper interno, deberá aplicar el mismo revoke total,
  validación defensiva y prueba de ejecución directa denegada antes del merge.
- `status`, `published_at`, `expires_at`, `accepted_offer_id`, `route_distance_m`, `drops_count` y los estados,
  distancias y timestamps de `delivery_request_drops` solo se modifican por la RPC pública o las RPC operativas ya
  existentes. La barrera PostgreSQL se conserva mediante grants por columna, RLS, triggers y las RPC; cada campo
  sensible tendrá un test de bypass directo.
- La RPC no escribe PII en `audit_log`, push, analytics, URL ni logs. El audit existente registra solo actor, acción,
  request id y estados; las notificaciones son best-effort y solo contienen el request id.
- Los contactos privados siguen bajo la matriz RLS de CC-022/CC-023: comercio dueño y admin pueden leerlos; el
  courier solo después del match; un courier no aceptado no puede leerlos ni por PostgREST ni por Realtime.

## Concurrencia e idempotencia

- En una creación nueva se valida actor y payload, se inserta el request con el `requestId` suministrado y se mantiene
  bloqueada esa fila durante todos los inserts hijos y la publicación. En conflicto de UUID se obtiene
  `delivery_requests` con `FOR UPDATE` antes de decidir si es retry propio, colisión ajena o contenido diferente.
- La igualdad canónica se reconstruye desde los valores originales persistidos, no desde un blob ni un hash público:
  `requestId`; zona, dirección y coordenadas de retiro; precio fijo y `autoAssign`; cantidad y `position = 1..N`; y,
  para cada posición, zona/dirección/coordenadas de destino, nombre, teléfono, consentimiento, paquete, medio de pago,
  `needsChange`, monto de cambio y notas. Se comparan padre + contacto de retiro + N drops + N contactos privados
  luego de aplicar las mismas normalizaciones de entrada —trim y representación de nulos— definidas por los schemas.
  Se excluyen estados operativos posteriores, distancias calculadas, timestamps y montos cobrables derivados.
- Todos los atributos canónicos son reconstruibles desde esas filas privadas y públicas originales. Si la
  implementación detecta que alguno deja de serlo, el backend se detiene y el CC se actualiza con una solución de
  persistencia privada antes de implementar; no se agrega un hash de PII a una columna pública ni se finge igualdad.
- Un retry propio con UUID y contenido canónico iguales devuelve el estado actual, `publishedAt` original e
  `idempotent = true`, aunque la solicitud ya esté `matched`, `in_transit`, `delivered`, `cancelled` o `expired`.
  No inserta hijos, no llama nuevamente a `request_cycle` y no duplica eventos ni notificaciones de creación.
- El mismo UUID propio con contenido distinto devuelve `VALIDATION_ERROR` sin mutaciones. Una colisión con una fila
  de otro merchant devuelve `NOT_FOUND` sin revelar su existencia. Dos UUID distintos representan intenciones
  independientes, sujetas al rate limit normal de publicación.
- Dos sesiones con el mismo UUID y contenido: una crea y publica; la otra espera el lock y luego toma la ruta
  idempotente. `request_cycle` conserva su orden de locks solicitud → oferta aceptada → courier; la RPC nueva no toma
  locks de oferta o courier antes de delegar. Un error de validación o publicación revierte inserts y efectos de esa
  llamada, dejando cero filas huérfanas.
- Las pruebas backend futuras cubren retries después de `published`, `matched`, `in_transit`, `delivered` y estados
  terminales aplicables; verifican estado actual, `publishedAt` original, un solo request y cero eventos de creación
  adicionales. También cubren diferencia de `notes` o consentimiento, colisión ajena, UUID distinto y dos sesiones
  simultáneas. El mutante «retry llama de nuevo a publish» debe fallar por el contador/evento de negocio, no por
  sintaxis o infraestructura.

Antes del match, ningún lector adicional se habilita por esta RPC. Después del match, los lectores existentes de
CC-022/CC-023 revelan los datos privados por `drop_contacts` según su actor. `requestId` es un identificador visible
y además la clave de idempotencia; no es secreto ni concede autorización. El payload original con PII no se publica
en feed, logs, analytics, URLs ni notificaciones.

## Compatibilidad, rollout y rollback

- **UI anterior contra el esquema nuevo:** sigue funcionando el escritor legacy de un drop y `publish_request`; no
  se modifica, migra ni redefine su esquema. Esa ruta continúa completando sus columnas legacy y deja que el puente
  cree exactamente un drop. Las altas nuevas por la RPC jamás duplican datos de destino en esas columnas.
- **UI nueva contra el esquema anterior:** no se despliega la UI multi-drop hasta que la migración con la RPC y sus
  grants estén aplicada en Develop; la UI debe fallar cerrada ante `undefined`/RPC ausente y no volver a una secuencia
  de inserts que simule atomicidad.
- **Backfill:** no aplica; la RPC solo crea solicitudes nuevas. CC-022/CC-023 ya proveen backfill de solicitudes
  históricas y limpieza legacy en el orden autorizado.
- **Gate 1 — contrato:** PR #332 documental aprobada y mergeada. Ese merge no crea, ejecuta ni despliega la RPC.
- **Gate 2 — backend:** PR separada de backend/RPC con una migración nueva `*_cc024_*.sql`, contratos Zod/fake,
  tipos generados, wrapper, pgTAP y prueba reproducible de dos sesiones; revisión independiente y merge autorizado.
- **Gate 3 — Develop:** `migrate-develop` en `SUCCESS` para el SHA integrado; luego prueba real de la RPC con 1 y N
  drops y compatibilidad del cliente legacy en Supabase Develop. Hasta completar este gate, la UI nueva permanece
  fail-closed y no puede declarar E2E verde para una función ausente.
- **Gate 4 — writer:** PR #330 actualizada mediante merge normal desde `develop`, sin rebase de historia compartida;
  `CreateRequestForm` y su Server Action usan la RPC desplegada, se ejecuta el E2E completo de
  publicar/ofertar/aceptar/completar 3 drops y se solicita una revisión independiente nueva.
- **Retiro de compatibilidad:** otro cambio contractual, cuando ningún cliente viejo escriba el flujo secuencial y
  los checkpoints legacy estén documentados en verde. Este CC no retira columnas ni puente.
- **Rollback:** antes del Gate 4 se puede revertir la migración backend y seguir con el escritor legacy. Después de
  crear solicitudes nuevas mediante la RPC, se revierte por forward-fix compatible; no se borran requests ni drops.

## Motivo

T-340 Paso 4 necesita publicar 1..N entregas sin dejar solicitudes, contactos o drops huérfanos si falla cualquier
validación o insert. La secuencia de `supabase.from(...).insert(...)` actual no puede garantizar rollback porque no
comparte una transacción con `publish_request`. El contrato de CC-022 ya define el modelo y sus invariantes; CC-024
formaliza la operación atómica que la UI debe consumir.
