# CC-028 — RPC transaccional para editar perfil de comercio (update_my_merchant_profile)

- **Issue:** #379 (label `contract-change`) · **Abre:** Persona 2 (agy) · **Fecha:** 2026-10-16
- **Contrato afectado:** RPC `public.update_my_merchant_profile(jsonb)`, `src/domain/rpc-contracts.ts`, `src/server/rpc/merchants.ts`, `src/types/database.types.ts`
- **Tareas bloqueadas:** T-358
- **Depende de:** CC-027 (MapPicker `showMarkerWhenEmpty`)

## Actual
En la implementación previa (`src/features/merchants/actions.ts:updateMerchantProfileAction`):
- Se realizaba una lectura inicial de `merchants` y `profiles`, seguida de dos `UPDATE` directos por tabla cliente.
- Si dos peticiones ocurrían simultáneamente, se perdían actualizaciones concurrentes o se sobrescribían campos no modificados (p. ej. sobreescritura de teléfono mientras se editaba la dirección).
- No existía atomicidad entre `profiles.display_name` y `merchants.business_name`.
- La actualización de campos opcionales no distinguía con exactitud entre campo ausente en el payload y borrado explícito mediante `null`.
- Se carecía de un registro auditable unificado en `public.audit_log` para cambios de perfil de comercio.

## Propuesto
Crear la función RPC `public.update_my_merchant_profile(p_patch jsonb)`:
```sql
create or replace function public.update_my_merchant_profile(
  p_patch jsonb
)
returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
```

### Semántica del Patch JSONB y Allowlist estricta
El parámetro `p_patch` debe ser un objeto JSON estrictamente validado:
- **Allowlist exhaustiva:** Solo se permiten las claves:
  `businessName`, `phone`, `defaultPickupAddress`, `defaultPickupZoneId`, `defaultPickupLat`, `defaultPickupLng`, `notes`.
- Cualquier clave desconocida o payload no-objeto / vacío `{}` es rechazado de inmediato con `VALIDATION_ERROR`.
- **Presencia de claves vs valor `null`:**
  - Si una clave **no está presente** en `p_patch`, la columna correspondiente en la base de datos **no se modifica**.
  - Si una clave **está presente con valor `null`**:
    - Para `notes`: se borran las notas (pasa a `null`).
    - Para `defaultPickupZoneId`: se desasocia el barrio por defecto (pasa a `null`).
    - Para `defaultPickupLat` y `defaultPickupLng`: se exige que ambas se envíen juntas en `null` (borrado explícito de la ubicación guardada). Un par asimétrico (lat nula y lng presente o viceversa) es rechazado con `VALIDATION_ERROR`.
    - Para `businessName`, `phone`, `defaultPickupAddress`: no se permite `null` ni cadenas vacías tras `trim()` (son campos obligatorios del comercio).
- **Validaciones de contenido:**
  - `businessName`: 1 a 100 caracteres, sin etiquetas HTML ni caracteres de control, al menos un alfanumérico. Se actualiza atómicamente en `profiles.display_name` y `merchants.business_name`.
  - `phone`: teléfono argentino válido de 10 dígitos nacionales (código de área sin 0 y número sin 15). Se guarda normalizado en `profiles.phone`.
  - `defaultPickupAddress`: 1 a 200 caracteres no vacíos.
  - `defaultPickupZoneId`: uuid existente en `public.zones(id)` o `null`.
  - `defaultPickupLat` / `defaultPickupLng`: si se especifican valores numéricos, deben pertenecer al área de servicio de Aguilares (`AGUILARES_BOUNDS`: lat entre -27.48 y -27.38; lng entre -65.645 y -65.58).
  - `notes`: longitud máxima de 500 caracteres, sin caracteres de control no permitidos.

### Concurrencia y Locks
- Se resuelven los actores a partir de `auth.uid()`.
- Se toman locks en orden global estricto:
  1. `select id, display_name, phone into v_old_profile from public.profiles where id = v_uid for update;`
  2. `select * into v_old_merchant from public.merchants where profile_id = v_uid for update;`
- Evita condiciones de carrera entre ediciones simultáneas de la misma cuenta y asegura transaccionalidad completa.

### Auditoría
- Antes de confirmar y retornar, se registra una fila en `public.audit_log`:
  - `actor_id`: `v_uid`
  - `action`: `'merchant_profile_update'`
  - `target_type`: `'merchant'`
  - `target_id`: `v_uid::text`
  - `before`: estado anterior (JSONB con los campos antes de actualizar)
  - `after`: estado posterior (JSONB con los campos actualizados)

### Respuesta canónica
Devuelve un objeto JSONB con el perfil completo actualizado:
```json
{
  "profileId": "uuid",
  "businessName": "Comercio Ejemplo",
  "phone": "3865123456",
  "defaultPickupAddress": "Calle 123",
  "defaultPickupZoneId": "uuid-o-null",
  "defaultPickupLat": -27.432,
  "defaultPickupLng": -65.616,
  "notes": "Notas opcionales o null"
}
```

## Seguridad y permisos
- **Identidad:** No se acepta `profile_id` en el payload. La identidad del comercio se toma exclusivamente de `auth.uid()`.
- **Rol:** Se valida que `profiles.role = 'merchant'` y que `profiles.consent_status = 'active'`. De lo contrario lanza `UNAUTHORIZED_ACTOR`.
- **`security definer`:** Ejecuta con search path congelado `set search_path = public, pg_temp`.
- **Grants y revokes:**
  - `revoke all on function public.update_my_merchant_profile(jsonb) from public, anon, authenticated;`
  - `grant execute on function public.update_my_merchant_profile(jsonb) to authenticated;`
- **Barrera de PostgreSQL contra actualización directa:**
  - `merchants_update_self` protege `subscription_status` y `paid_until` congelados por subselect sobre la fila previa.
  - Ningún cliente puede alterar estados de suscripción ni consentimientos a través de esta RPC ni por UPDATE directo.

## Concurrencia e idempotencia
- **Orden de locks:** `profiles` FOR UPDATE → `merchants` FOR UPDATE. Garantiza serialización estricta por comercio sin interbloqueos.
- **Idempotencia:** Reintentar el mismo payload con los mismos valores es idempotente y seguro; el resultado canónico refleja fielmente el estado final de las filas.

## Privacidad / matriz de exposición
- El comercio solo puede leer y actualizar su propia fila identificada por `auth.uid()`.
- Ningún otro actor (couriers ni comercios terceros) tiene acceso a invocar esta RPC sobre cuentas ajenas.

## Compatibilidad, rollout y rollback
- **Rollout:**
  1. Se despliega la migración de la RPC `update_my_merchant_profile` y sus tests pgTAP en esta PR del CC.
  2. Se expone el wrapper tipado en `src/server/rpc/merchants.ts` y contrato en `src/domain/rpc-contracts.ts`.
  3. En T-358, `updateMerchantProfileAction` migra del doble UPDATE cliente a la llamada de esta RPC.
- **Compatibilidad:** La policy `merchants_update_self` preexistente se mantiene para no romper consumidores en vuelo.
- **Rollback:** La RPC es nueva y append-only; puede revertirse con `drop function public.update_my_merchant_profile(jsonb);` si fuera necesario.
