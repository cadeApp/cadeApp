## Propuesto

### Columnas

```sql
alter table public.couriers
  add column application_submitted boolean not null default false,  -- envió la postulación
  add column submitted_at timestamptz,                               -- cuándo; null = fecha desconocida
  add constraint couriers_submitted_at_requires_application
    check (submitted_at is null or application_submitted);
```

- `application_submitted` es la **fuente de verdad** de «postulación enviada» y de «onboarding completo» del
  repartidor. `vehicle_type` vuelve a ser solo el vehículo.
- `submitted_at` es el momento del **primer** envío, con el reloj de la base. `null` con `application_submitted = true`
  es una postulación histórica de fecha desconocida.

### RPC `finalize_courier_application`

```sql
public.finalize_courier_application(
  p_courier_id uuid,
  p_dni_hmac text,
  p_vehicle_type public.vehicle_type,
  p_vehicle_plate text            -- null para walk/bike; se guarda como llega (la acción ya la normaliza)
) returns jsonb                   -- { "ok": true, "idempotent": false, "submittedAt": "…|null" }
```

- `security definer`, `volatile`, `set search_path = public, pg_temp`.
- `revoke all … from public, anon, authenticated; grant execute … to service_role`. Ningún cliente la puede
  llamar: el `dni_hmac` lo calcula el servidor con un secreto que el cliente no tiene, y `p_courier_id` sale de la
  sesión validada por la acción.
- Pasos, en este orden:
  1. `select … from couriers where profile_id = p_courier_id for update` (primer lock, el mismo orden que CC-025:
     `couriers` → `profiles` → `courier_documents`). Sin fila → `NOT_FOUND`.
  2. Bajo el lock: el perfil es `courier` (`UNAUTHORIZED_ACTOR`), `consent_status = 'active'`
     (`CONSENT_REQUIRED`) y el estado es `pending` o `approved` (`UNAUTHORIZED_ACTOR`).
  3. `p_dni_hmac ~ '^[0-9a-f]{64}$'`, `p_vehicle_type` no nulo y patente de hasta 20 caracteres (`VALIDATION_ERROR`).
  4. **Si ya está enviada** (`application_submitted = true`):
     - mismo `dni_hmac`, `vehicle_type` y `vehicle_plate` que la fila → `{ ok: true, idempotent: true,
       submittedAt }` sin escribir nada; un histórico devuelve `submittedAt: null` y sigue `null`;
     - cualquier dato distinto → `INVALID_STATE_TRANSITION`, sin escribir. Los cambios de vehículo posteriores van por
       `updateCourierVehicleAction` (hoy) o las RPC de CC-042; el DNI no se cambia.
  5. **Primer envío** (`application_submitted = false`): existen los cuatro documentos obligatorios del repartidor,
     uno vigente por tipo (`dni_front`, `dni_back`, `selfie`, `avatar`; `courier_id = p_courier_id`,
     `coalesce(is_current, true)`, `status in ('submitted', 'verified')`); si falta alguno o hay más de uno vigente del
     mismo tipo → `VALIDATION_ERROR`.
  6. Marca la transacción (`set_config('app.courier_application_finalize', 'on', true)`) y hace **un** `update` con
     `dni_hmac`, `vehicle_type`, `vehicle_plate`, `application_submitted = true` y `submitted_at = now()`. Si
     `dni_hmac` choca con el `unique` de otro repartidor → `DNI_ALREADY_REGISTERED` (captura `unique_violation` sobre
     `couriers_dni_hmac_key`).
  7. Devuelve `{ ok: true, idempotent: false, submittedAt }`.
- Solo la transición `false → true` fija la fecha. Nunca `coalesce(submitted_at, now())`.
- Errores (todos `P0001` con el código como mensaje): `NOT_FOUND`, `UNAUTHORIZED_ACTOR`, `CONSENT_REQUIRED`,
  `VALIDATION_ERROR`, `INVALID_STATE_TRANSITION`, `DNI_ALREADY_REGISTERED`. Ya existen en `src/domain/errors.ts`.

### `courierOnboardingAction`

El `update` final con `createAdminClient()` (`actions.ts:292-321`) se reemplaza por
`adminClient.rpc('finalize_courier_application', { p_courier_id: user.id, p_dni_hmac, p_vehicle_type,
p_vehicle_plate })`. El resto de la acción no cambia (consentimientos y `submit_courier_onboarding_documents`
siguen antes). Mapeo: `NOT_FOUND`, `UNAUTHORIZED_ACTOR` y `CONSENT_REQUIRED` → `UNAUTHORIZED_ACTOR` (como hoy);
`VALIDATION_ERROR`, `DNI_ALREADY_REGISTERED` e `INVALID_STATE_TRANSITION` se devuelven tal cual; lo demás →
`INTERNAL_ERROR`. La salida se parsea con Zod (`ok`, `idempotent`, `submittedAt`).

**Tipado:** la RPC aparece en `database.types.ts` porque el generador lista todas las funciones de `public`, pero
**no** entra en `RPC_CONTRACTS` de `src/domain` (que describe las RPC de los clientes de sesión) ni tiene wrapper en
`src/server/rpc`. Su único llamador es `courierOnboardingAction`, que ya es `server-only` y usa `createAdminClient()`.

### Trigger `couriers_guard_application`

`before insert or update on public.couriers for each row execute function app_private.couriers_guard_application()`:
- `insert` con `application_submitted = true` o `submitted_at` no nulo → `VALIDATION_ERROR`.
- `update` que cambie `application_submitted` o `submitted_at` → `VALIDATION_ERROR`, salvo que se cumplan **las dos**
  condiciones:
  1. `current_setting('app.courier_application_finalize', true) = 'on'` (la marca del paso 6), y
  2. `current_user` es el dueño de `finalize_courier_application`
     (`pg_get_userbyid(proowner)` de `'public.finalize_courier_application(uuid, text, public.vehicle_type, text)'::regprocedure`).
- Además, nunca se permite volver de `true` a `false` ni cambiar un `submitted_at` ya fijado.

**Alcance real de la barrera:** la marca de transacción **no es una credencial**: cualquier rol que pueda ejecutar
SQL puede fijar una variable personalizada. Lo que impide la escritura directa es la segunda condición:
- `anon` y `authenticated` (repartidor, comercio, admin `aal1` o `aal2`) escriben con `current_user` igual a su rol;
  aunque fijaran la marca, el trigger los rechaza. Por PostgREST además no pueden llamar a `set_config`
  (`pg_catalog` no está expuesto).
- `service_role` por PostgREST (seed, `createAdminClient()`) tampoco pasa: su `current_user` es `service_role`.
  Solo cambia el envío llamando a la RPC.
- El dueño de la función (`postgres`, que también corre las migraciones) y los superusuarios **sí** pueden saltarla:
  es el límite técnico de PostgreSQL y el mismo que tienen todas las barreras del repo. Ese acceso no lo tienen la
  app ni los agentes (AGENTS.md §6) y lo usa solo `migrate-*`.

### Lectores del «onboarding completo»

Pasan de `vehicle_type` a `application_submitted`:
- `parseOnboardingComplete` lee `application_submitted` para el repartidor: `true` → completo, `false` o sin fila →
  incompleto, columna ausente o tipo raro → `undefined` (se conserva el fail-open de T-334: un error de lectura no
  redirige);
- `updateSession`, `loginAction` y `updatePasswordAction` seleccionan `application_submitted`;
- `src/app/auth/confirm/route.ts` decide con `application_submitted`;
- `courier/profile/page.tsx` (`onboardingComplete`) y `courier/onboarding/vehicle/page.tsx` (modo edición);
- `updateCourierVehicleAction` exige `application_submitted = true` en vez de `vehicle_type` no nulo.

`add_courier_optional_document` (SQL) sigue con `vehicle_type is not null`: hoy es equivalente (las dos columnas se
escriben en la misma transacción y el backfill las alinea). Lo cambia CC-042 cuando el vehículo pueda existir antes del
envío (ver «Coordinación con CC-042»).

### Lectura

El admin lo lee por `couriers_select_admin` y por `admin_list_applicants` (CC-044); el repartidor ve el suyo por
`couriers_select_self`. No se agrega a ninguna RPC que vean comercios.

## Seguridad y permisos

- **RLS:** no cambia ninguna policy. Las columnas quedan bajo las policies de `couriers`.
- **Grants:** `finalize_courier_application`: `execute` solo para `service_role`. La tabla no tiene grants por
  columna; la barrera de `application_submitted` y `submitted_at` es el trigger.
- **Helper interno:** `app_private.couriers_guard_application()` es `security invoker` (necesita ver el
  `current_user` real), `set search_path = public, pg_temp`, `revoke all … from public, anon, authenticated`, sin
  `grant`. Solo lo invoca el trigger.
- **Matriz de escritura directa** (sin la RPC) de `application_submitted` o `submitted_at`:

  | Actor | Vía | Resultado |
  |---|---|---|
  | Repartidor (su fila) | `update` por PostgREST | `VALIDATION_ERROR` |
  | Repartidor | `rpc('finalize_courier_application')` | sin `execute` (`42501`) |
  | Admin `aal1` / `aal2` | `update` por PostgREST | `VALIDATION_ERROR` |
  | `service_role` | `update`/`insert`/`upsert` por PostgREST | `VALIDATION_ERROR` |
  | `authenticated` con la marca fijada a mano | `update` | `VALIDATION_ERROR` (no es el dueño) |
  | `service_role` | `rpc('finalize_courier_application')` | permitido, con las validaciones de la RPC |
  | Dueño / superusuario | SQL | puede (límite técnico; solo `migrate-*`) |

## Concurrencia e idempotencia

- **Locks:** la RPC toma `couriers … for update` primero y después lee `profiles` y `courier_documents`, el orden de
  CC-025. `submit_courier_onboarding_documents`, `replace_courier_document`, `add_courier_optional_document` y
  `admin_verify_document` toman el mismo lock de `couriers` primero, así que se serializan sin deadlocks nuevos.
- **Reintento idéntico:** `idempotent: true`, sin escribir y sin cambiar la fecha.
- **Reintento con datos distintos:** `INVALID_STATE_TRANSITION`, sin escribir.
- **Dos envíos a la vez:** el segundo espera el lock, ve `application_submitted = true` y cae en la rama de reintento.
- **Reemplazo de documento concurrente:** espera el lock; si entra antes, `replace_courier_document` deja un vigente
  del mismo tipo y la validación sigue pasando.

## Compatibilidad, rollout y rollback

- **Backfill (en la migración, idempotente):** `application_submitted = true` solo en las filas existentes con
  `vehicle_type is not null` (envíos históricos reales según T-334); `submitted_at` queda `null`. No se copia
  `profiles.created_at`, ni la fecha de un documento, ni `decided_at`. Se hace antes de crear el trigger.
- **Diagnóstico de históricos (PR587-H07):** la migración emite un `raise notice` con la **cantidad** de filas
  marcadas en el backfill a las que les falta alguno de los cuatro documentos vigentes (sin ids ni datos personales).
  Quedan marcadas igual (decisión D02-C: el envío ocurrió según la marca vigente); el número sirve para que
  Lautaro073 decida si revisarlas a mano. Limitación: el backfill no puede probar que esos envíos estuvieron completos.
- **UI anterior contra el esquema nuevo:** la app desplegada sigue haciendo el `update` final directo con
  `service_role` y sin tocar las columnas nuevas: el trigger lo deja pasar, pero esos envíos quedarían con
  `application_submitted = false`. Por eso la migración y el cambio de la acción van en la **misma** PR (T-421) y
  `migrate-*` corre inmediatamente antes del deploy de cada entorno; la ventana es la de un deploy.
- **Esquema anterior contra la UI nueva:** no ocurre (la migración se aplica antes del deploy).
- **Rollout:** T-421: migración, acción, lectores, seed y E2E juntos; después T-403 y T-404.
- **Condición para retirar la compatibilidad:** no aplica.
- **Rollback:** volver la acción y los lectores a `vehicle_type` (revert de T-421) y después `drop trigger`,
  `drop function app_private.couriers_guard_application()`, `drop function public.finalize_courier_application(...)`
  y `alter table public.couriers drop column submitted_at, drop column application_submitted`. Se pierden las fechas
  registradas desde el despliegue; ningún otro dato depende de ellas.

## Decisiones de producto

- La fecha de envío es real y del servidor; no se deduce de `profiles.created_at` ni de documentos (D02 = C) —
  Lautaro073, 2026-10-21 (PR #489).
- Las postulaciones previas quedan sin fecha («Sin fecha de envío»), sin backfill de fecha — Lautaro073, 2026-10-21.

## Motivo

T-403 muestra «Enviado: hace 2 h» y cuenta las postulaciones pendientes; T-404 muestra «Postulación enviada» en el
historial. Hoy no hay fecha de envío, «pendiente» incluye cuentas sin onboarding, y la marca `vehicle_type` deja de
servir cuando CC-042 permita crear el vehículo antes de los documentos.
