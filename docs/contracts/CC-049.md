## Propuesto

Una migración `supabase/migrations/20261112120000_cc049_push_subscriptions_hardening.sql`:

1. **Policies.** Se borra `push_subscriptions_all_self` y se crean:
   - `push_subscriptions_select_self`: `for select to authenticated using (user_id = auth.uid() and app_private.is_active_operational_actor())`;
   - `push_subscriptions_delete_self`: `for delete to authenticated using (user_id = auth.uid() and app_private.is_active_operational_actor())`.

   Sin policy de insert ni de update para clientes: la única escritura es `register_push_subscription`
   (`security definer`). `push_subscriptions_select_admin` no cambia.
2. **Grants.** `revoke all on public.push_subscriptions from anon`;
   `revoke insert, update, truncate, references, trigger on public.push_subscriptions from authenticated`.
   `authenticated` conserva `select` y `delete`, filtrados por las policies del punto 1. `service_role` no cambia.
3. **Allowlist de servicios push** en un helper interno
   `app_private.is_allowed_push_endpoint(p_endpoint text) returns boolean`, con `language sql`, `immutable`,
   `security invoker` y `set search_path = public, pg_temp`, más `revoke all … from public, anon, authenticated`.
   Devuelve `true` solo si el endpoint cumple **todas** estas reglas, en este orden:
   - empieza con `https://`;
   - el host termina en el primer `/`, `:` o fin de cadena, y no contiene `@`, `\`, `%`, `[`, `]` ni espacios
     (sin `userinfo`, sin escapes, sin IPv6 literal);
   - el puerto falta o es exactamente `:443`;
   - después del host y del puerto viene `/`;
   - el host en minúsculas, comparado entero (sin punto final), es `fcm.googleapis.com` (Chrome, Android, Opera),
     `updates.push.services.mozilla.com` (Firefox), `web.push.apple.com` (Safari) o
     `<etiqueta>.notify.windows.com`, con una sola etiqueta `[a-z0-9-]+` (Edge, `wns2-xxx.notify.windows.com`).

   La tabla de casos de §Impacto exacto (M01 de la revisión de #697) es la misma para SQL, dominio, fake y emisor.
4. **RPC `register_push_subscription`:** a las validaciones actuales se suma
   `or not app_private.is_allowed_push_endpoint(v_endpoint)`, con el mismo `VALIDATION_ERROR`. La firma, la salida, los
   códigos y la lógica de reasignación de CC-035 no cambian.
5. **Sin borrado de filas históricas (D5-C, H02 de la revisión de #697).** La migración **no borra**
   suscripciones existentes con host fuera de la lista: quedan en la tabla, el emisor no les envía (punto 7) y nadie
   puede crear filas nuevas así (puntos 1, 2 y 4). El saneamiento es una etapa posterior y aparte, fuera de T-432:
   - **inventario de solo lectura por conteos**, por ambiente, con autorización de Lautaro073 para leer cada base:
     `select case when app_private.is_allowed_push_endpoint(endpoint) then <servicio> else 'fuera_de_lista' end, count(*) … group by 1`.
     Nunca devuelve ni registra endpoint, claves ni `user_id`;
   - con ese resultado, Lautaro073 aprueba explícitamente los descartes, y recién entonces una segunda migración en
     otra PR borra las filas aprobadas.
6. **Dominio:** un helper puro `isAllowedPushEndpoint(endpoint: string): boolean` en `src/domain`, con las mismas
   reglas que el punto 3, y `registerPushSubscriptionInputSchema.endpoint` suma `.refine(isAllowedPushEndpoint)`. La
   salida y los códigos de error no cambian. El fake de dominio (`src/domain/testing/rpc-fake.ts`) aplica la misma
   regla.
7. **Emisor (`src/server/push/sender.ts`):**
   - **Filtro:** antes de enviar se descarta toda suscripción cuyo endpoint no pase `isAllowedPushEndpoint`. No hay
     request de red y cuenta en `failedCount`. **No se borra la fila** (D2-A): si la lista del código quedara
     desfasada de la de SQL, no se pierden suscripciones válidas.
   - **Forma del intento (H04):** `PushAttemptRecord` pasa a ser una unión discriminada:
     - intento enviado: `{ outcome: 'sent', endpoint: string, status: number, error?: string }`, con el mismo
       contenido que hoy más el discriminante;
     - intento bloqueado: `{ outcome: 'blocked', status: 0, error: 'ENDPOINT_NOT_ALLOWED' }`, **sin la propiedad
       `endpoint`**: la URL rechazada no se guarda, no se devuelve y no se registra.
     `SendPushResult.attempts` usa la unión; la respuesta de `/api/push/send` la expone igual. El único lector fuera
     del emisor (`src/features/announcements/actions.ts:66`) solo usa `attempts.length`.
   - **Plazo absoluto de 5000 ms con cancelación real (D4-B, H03):** el timeout de `web-push` es de inactividad del
     socket, así que `WebPushTransport` deja de usar `sendNotification`:
     - con `webpush.generateRequestDetails(subscription, payload, { TTL: 300 })` arma método, URL, headers y cuerpo
       cifrado con VAPID (sin dependencias nuevas);
     - hace la request con `node:https.request` y arranca un temporizador absoluto de `PUSH_TIMEOUT_MS` (5000) **al
       crearla**. Al vencer llama a `request.destroy()`: aborta el socket aunque el servidor siga mandando datos;
     - limpia el temporizador al resolver y al fallar;
     - **no sigue redirecciones:** un 3xx es un fallo con su código, sin pedir otra URL;
     - 2xx es éxito; 404 y 410 borran la suscripción, como hoy; un timeout o un error de red es un fallo
       (`failedCount`) que no borra.
     El transporte recibe por constructor la función de request y el plazo, para que las pruebas usen un servidor
     local y un plazo corto. Producción usa `https.request` y 5000 ms.
   - Se conservan las tandas paralelas de `PUSH_BATCH_SIZE` (CC-040).

## Seguridad y permisos

- **RLS:** sin insert ni update de clientes. Select y delete solo de filas propias con consentimiento activo (la
  condición actual). La del admin no cambia.
- **Grants y revokes:** puntos 1 y 2. `anon` sin ningún privilegio sobre la tabla.
- **`security definer` / `invoker`:**
  - `register_push_subscription` sigue `security definer` con `set search_path = public, pg_temp` y `execute` solo
    para `authenticated`;
  - el helper nuevo es `security invoker` e `immutable`, sin `execute` para clientes. Lo llama la RPC (y, en la etapa
    posterior, el inventario por conteos de §Propuesto 5), y no lee tablas.
- **Acceso directo frente a RPC:** `user_id`, `endpoint`, `p256dh`, `auth`, `platform` y `last_seen_at` solo cambian por
  la RPC. La barrera es la ausencia de grant y de policy de insert y update. Tests de bypass: insert directo, update de
  cada columna y truncate como `authenticated` dan `42501`.

## Concurrencia e idempotencia

- No hay operación transaccional nueva. La RPC conserva los locks y el reintento por `unique_violation` de CC-035; la
  validación del host corre antes de cualquier lock.
- **Reintentos:** registrar dos veces el mismo endpoint permitido sigue devolviendo `created: false`. Un endpoint no
  permitido da `VALIDATION_ERROR` siempre, sin escribir ni auditar.
- **Emisor:** el plazo absoluto no cambia el orden ni la idempotencia del envío (push best-effort, `AGENTS.md` §2).
  Un envío abortado por plazo puede haber llegado al servicio; no se reintenta.

## Compatibilidad, rollout y rollback

- **UI actual contra el esquema nuevo:**
  - el registro ya usa la RPC, y la baja y el estado usan `delete`/`select` propios: siguen funcionando;
  - un cliente viejo que insertara directo recibiría `42501`, pero la app no lo hace.
- **Backfill:** ninguno. Las filas históricas fuera de la lista se conservan (D5-C) y el emisor no les envía.
- **Rollout:**
  1. una sola migración más el código del emisor y del dominio, en la misma PR. El emisor nuevo contra el esquema
     viejo solo filtra de más, nunca de menos;
  2. el saneamiento de filas históricas es una etapa posterior (§Propuesto 5).
- **Rollback:** restaurar `push_subscriptions_all_self`, los grants y la RPC anterior. No se pierde ningún dato,
  porque la migración no borra filas.

- **Pruebas exigidas:**
  - **Bypass y privilegios (H01): dos barreras, cada una con su prueba y su mutación.**
    - **Grants:** `has_table_privilege('authenticated', 'public.push_subscriptions', …)` es `false` para `INSERT`,
      `UPDATE`, `TRUNCATE`, `REFERENCES` y `TRIGGER`, y `true` para `SELECT` y `DELETE`. `anon` no tiene ninguno.
      Mutación: restaurar el grant de insert/update → fallan esas aserciones aunque la RLS siga cerrada.
    - **RLS:** en una subtransacción que se revierte se conceden temporalmente insert y update a `authenticated`.
      Como dueño se intenta un insert directo (debe fallar con `42501` por RLS) y un update de cada columna (debe
      cambiar 0 filas). Los resultados se guardan en variables y las aserciones van afuera, para no revertir el
      contador de pgTAP. Al final se verifica que el grant revocado sigue revocado. Mutación: una policy permisiva de
      insert/update → el probe de RLS falla.
    - **Truncate:** como `authenticated` da `42501`, en un caso aparte.
    - **Select y delete:** funcionan sobre la fila propia; la ajena no se ve ni se borra.
    - `has_function_privilege`: `anon` y `authenticated` sin `execute` sobre `app_private.is_allowed_push_endpoint`.
  - **Allowlist en SQL:** la RPC aplica la tabla de casos. Los aceptados se registran; los rechazados dan
    `VALIDATION_ERROR` sin escribir ni auditar.
  - **Preservación de filas históricas en la primera aplicación (H02, D5-C).** Va en el modo estándar de
    `cc035_concurrency.mjs`, el que CI ya invoca, y corre una sola vez (no en los modos de mutación):
    1. restaura la base efímera de CI a la última migración anterior a CC-049:
       `pnpm supabase db reset --version 20261111120000 --no-seed`;
    2. **antes de aplicar CC-049 por primera vez**, siembra como owner, con un perfil existente, una suscripción con
       host permitido (E01) y otra fuera de la lista (E08), y guarda sus ids y valores;
    3. aplica la migración real con `pnpm supabase migration up`;
    4. exige que las dos filas existan con los mismos valores (`id`, `user_id`, `endpoint`, `p256dh`, `auth`,
       `platform`), no solo el conteo;
    5. deja la base como la encontró con `pnpm supabase db reset` completo (con seed), para no afectar a los runners
       que siguen.

    Mutación: en una copia aislada de la migración se agrega un `delete` de las filas no permitidas. Con la misma
    precondición la preservación da RED; con la migración sana, GREEN. Re-aplicar la migración sobre una base ya
    migrada no sirve como prueba, y tampoco una pgTAP que ejecute ella misma un `delete`.
  - **Dominio:** la tabla de casos sobre `isAllowedPushEndpoint` y sobre el `inputSchema`.
  - **Emisor:**
    - una suscripción con host no permitido no llega al transporte y produce
      `{ outcome: 'blocked', status: 0, error: 'ENDPOINT_NOT_ALLOWED' }`, sin la clave `endpoint`
      (`Object.hasOwn(attempt, 'endpoint') === false`), sin borrado y con `failedCount`;
    - en `route.test.ts` de `/api/push/send`, el intento bloqueado viaja sin la clave `endpoint`;
    - se conservan las tandas de 10, el borrado por 404/410 y la forma de los intentos enviados.
  - **Transporte (D4-B, H03), contra un servidor local** con plazo corto inyectado:
    - una respuesta que gotea un byte cada pocos ms más allá del plazo se aborta al vencer, aunque el socket nunca
      quede inactivo;
    - una conexión que nunca responde se aborta al vencer;
    - 2xx es éxito; 404 y 410 borran; un 3xx es un fallo con su código y no se pide la URL de `Location`;
    - el temporizador se limpia al resolver y al fallar (sin timers pendientes);
    - un abort por plazo es un fallo que no borra la suscripción.
  - **RED antes de la migración:** el insert directo y el endpoint arbitrario pasan.
  - **Mutaciones aisladas:**
    - grant de insert/update restaurado → fallan las aserciones de privilegios;
    - policy permisiva de insert/update → falla el probe de RLS;
    - sin la llamada al helper en la RPC → la RPC acepta un host arbitrario;
    - helper sin anclar el host → acepta el sufijo engañoso;
    - emisor sin el filtro → el transporte recibe el host no permitido;
    - transporte sin el temporizador absoluto (solo timeout de socket) → falla el caso de respuesta que gotea.
