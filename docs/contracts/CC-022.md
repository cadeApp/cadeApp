## Actual

- Una solicitud tiene **un solo destino**:
  - en `delivery_requests`: `dropoff_zone_id`, `package_type`, `recipient_payment_method`, `needs_change`,
    `cash_change_amount`, `notes`, `approx_distance_m` y `route_distance_m`;
  - en `delivery_request_contacts`, con `request_id` como clave: `dropoff_address`, `dropoff_lat`, `dropoff_lng`,
    `recipient_name`, `recipient_phone` y `recipient_consent_declared`, más los datos de retiro.
- **Alta:** `createDeliveryRequestAction` (`src/features/requests/actions.ts`) inserta el borrador en
  `delivery_requests` y `delivery_request_contacts` y después llama a `publish_request(p_request_id)`.
- La oferta (`offers.amount_ars`) es el precio de ese único envío.
- Estados (§5.1): `matched → in_transit` (`mark_picked_up`), `in_transit → delivered` (`mark_delivered`) y
  `matched → published` por «no llegó» (`report_no_show`). No existe el estado de una entrega individual.
- **Distancia:** `public.calculate_route_distance(p_pickup_lat, p_pickup_lng, p_dropoff_lat, p_dropoff_lng,
  p_pickup_zone_id, p_dropoff_zone_id, p_pickup_zone_name, p_dropoff_zone_name)`:
  - es una RPC pública punto a punto, `security definer`, con `execute` para `authenticated` (CC-019);
  - usa Haversine × 1,30, redondeado a 0,5 km (D15);
  - cae al centroide de la zona si falta un pin;
  - devuelve `NULL` si no se puede calcular (T-330).
- **Settings del admin:** las claves aceptadas están fijadas en:
  - `PLATFORM_SETTING_KEYS` (`src/domain/schemas/index.ts`);
  - `adminUpdateSettingInputSchema` (`src/domain/rpc-contracts.ts`);
  - la función SQL `admin_update_setting`;
  - `PlatformSettingsSnapshot` y `getPlatformSettings` (`src/features/admin/{types,queries}.ts`);
  - el schema, copy y formulario del panel A04 (`src/features/admin/{schemas.ts,components/platform-settings-form.tsx}`,
    `src/app/(admin)/admin/settings/page.tsx`).

## Propuesto

### 1. Esquema

```sql
-- Datos NO sensibles de cada entrega: los ve el repartidor antes de ofertar.
create table public.delivery_request_drops (
  id uuid primary key default gen_random_uuid(),
  request_id uuid not null references public.delivery_requests(id) on delete cascade,
  position smallint not null check (position >= 1),
  dropoff_zone_id uuid not null references public.zones(id),
  package_type public.package_type not null,
  recipient_payment_method public.recipient_payment_method not null,
  needs_change boolean not null default false,
  cash_change_amount integer null,
  approx_distance_m integer null,        -- tramo anterior → esta entrega, redondeado a 0,5 km
  status text not null default 'pending' check (status in ('pending', 'delivered', 'failed')),
  delivered_at timestamptz null,
  failed_reason text null,
  unique (request_id, position),
  check ((status = 'delivered') = (delivered_at is not null)),
  check ((status = 'failed') = (failed_reason is not null))
);

-- Datos sensibles de cada destinatario (D3), incluidas las indicaciones.
create table public.delivery_request_drop_contacts (
  drop_id uuid primary key references public.delivery_request_drops(id) on delete cascade,
  dropoff_address text not null,
  dropoff_lat double precision null,
  dropoff_lng double precision null,
  recipient_name text not null,
  recipient_phone text not null,
  recipient_consent_declared boolean not null,
  notes text null                        -- indicaciones de esta entrega: nunca en una tabla visible antes de aceptar
);

alter table public.delivery_requests
  add column drops_count smallint not null default 1 check (drops_count >= 1);
```

- **Fuente de verdad:** si una solicitud tiene filas en `delivery_request_drops`, los destinos salen **solo** de
  `delivery_request_drops` + `delivery_request_drop_contacts`. Nunca se mezclan con las columnas legacy.
  `delivery_request_contacts` sigue guardando el retiro (`pickup_address`, `pickup_lat` y `pickup_lng`).
- **Columnas legacy de destino:**
  - son `dropoff_zone_id`, `package_type`, `recipient_payment_method`, `needs_change`, `cash_change_amount` y
    `notes` de `delivery_requests`, y las de destino de `delivery_request_contacts`;
  - la migración las vuelve **nullable**;
  - el escritor nuevo no las completa;
  - no hay trigger espejo;
  - solo las lee el puente de §5;
  - un CC posterior las elimina (§10).
- **`drops_count`:** lo fija `publish_request` con la cantidad de entregas y nunca lo cambia el comercio (§2).

### 2. Permisos, RLS y campos RPC-only

`status`, `delivered_at` y `failed_reason` de `delivery_request_drops` solo los cambian las RPC. La barrera es real en
PostgreSQL, no solo un texto de policy.

- **Grants por columna:**
  - `revoke insert, update on delivery_request_drops from authenticated`;
  - `grant insert (request_id, position, dropoff_zone_id, package_type, recipient_payment_method, needs_change,
    cash_change_amount)` a `authenticated`;
  - `grant update (position, dropoff_zone_id, package_type, recipient_payment_method, needs_change,
    cash_change_amount)` a `authenticated`.

  Un `insert` o `update` directo que intente escribir `status`, `delivered_at`, `failed_reason`, `approx_distance_m`
  o `request_id` falla con `permission denied`. Al insertar, `status` toma el default `pending` y
  `delivered_at`/`failed_reason` quedan en `NULL`.
- **RLS sobre `delivery_request_drops`:**
  - **select:** igual que `delivery_requests`:
    - comercio dueño;
    - repartidor aprobado, sobre solicitudes `published` no vencidas o donde es el aceptado;
    - admin.
  - **insert / update / delete del comercio:** solo si es dueño de la solicitud y la solicitud está en `draft`. El
    `with check` exige además `status = 'pending' and delivered_at is null and failed_reason is null`, como segunda
    barrera.
- **RLS sobre `delivery_request_drop_contacts`:**
  - **select:** igual que `delivery_request_contacts`: comercio dueño, repartidor aceptado
    (`app_private.is_courier_assigned_to_request`) y admin;
  - **escritura del comercio:** solo con la solicitud en `draft`.
- **`delivery_requests_update_merchant`:** suma `drops_count` a las columnas congeladas, que tienen que ser iguales al
  valor previo en cualquier estado.
- **Las RPC** de §6 corren como `security definer` y son las únicas que mutan `status`, `delivered_at` y
  `failed_reason`.

### 4. Tope configurable

`platform_settings.max_drops_per_request`: entero ≥ 1, con valor inicial `5`. Se suma a **todo** el contrato de
settings del admin:

- `PLATFORM_SETTING_KEYS` y `platformSettingKeySchema` (`src/domain/schemas/index.ts`);
- `adminUpdateSettingInputSchema` / `OutputSchema` (`src/domain/rpc-contracts.ts`), con
  `{ key: 'max_drops_per_request', value: z.number().int().min(1) }`;
- SQL `admin_update_setting`: valida entero ≥ 1 y responde `INVALID_SETTING_VALUE` con 0, negativos o decimales;
  registra en `audit_log` como el resto;
- `PlatformSettingsSnapshot`, `getPlatformSettings` y el wrapper `src/server/rpc/admin.ts`;
- el schema del formulario, el copy y `PlatformSettingsForm` (A04, `/admin/settings`).

El admin lo cambia desde `/admin/settings` sin deploy. `publish_request` lee el valor vigente en cada llamada, sin
cachearlo.

### 5. `publish_request`: puente de compatibilidad y validaciones

Firma sin cambios. Orden nuevo, después de actor, titularidad y estado `draft` (pasos vigentes):

1. **Puente legacy, solo si la solicitud tiene CERO drops.**
   - Si el modelo legacy de un solo destino está **completo**, materializa en la misma transacción
     `delivery_request_drops` `position = 1` y su `delivery_request_drop_contacts`, copiando los valores legacy.
   - «Completo» significa: `dropoff_zone_id`, `package_type` y `recipient_payment_method` no nulos, y en
     `delivery_request_contacts` `dropoff_address`, `recipient_name` y `recipient_phone` no vacíos y
     `recipient_consent_declared = true`.
   - `delivery_requests.notes` se copia a `drop_contacts.notes` y queda en `NULL` en la fila legacy, para no
     exponerlo en el feed.
   - Si el legacy está incompleto, responde `MISSING_REQUIRED_FIELDS`, como hoy.
   - **Si ya existen drops, el puente no corre** y las columnas legacy se ignoran.
   - Un reintento no duplica: en el segundo llamado ya hay drops, o la solicitud ya no está en `draft` y responde
     `INVALID_STATE_TRANSITION`.
2. Validaciones nuevas, antes de `OFFER_BELOW_MINIMUM` (CC-021) y `RATE_LIMITED`:
   1. al menos un drop → `MISSING_REQUIRED_FIELDS`;
   2. `count(drops) > max_drops_per_request` vigente → `DROP_LIMIT_EXCEEDED` (nuevo);
   3. cada drop con zona activa y pin dentro de Aguilares → `INVALID_ZONE` / `OUT_OF_BOUNDS_AGUILARES`;
   4. `position` consecutivas desde 1 → `VALIDATION_ERROR`;
   5. cada drop con su fila en `drop_contacts` completa y consentimiento declarado → `MISSING_REQUIRED_FIELDS`.
3. Fija `drops_count` y calcula la distancia (§7).
4. La salida suma `dropsCount`.

### 6. Estados por entrega

La solicitud mantiene su máquina de estados (§5.1). Se agrega el estado por entrega:

| Transición | Quién | Regla |
|---|---|---|
| entrega `pending → delivered` | repartidor aceptado, solicitud `in_transit` | `mark_drop_delivered(p_drop_id)` |
| entrega `pending → failed` | repartidor aceptado, solicitud `in_transit` | `mark_drop_failed(p_drop_id, p_reason)`; motivo obligatorio (`REASON_REQUIRED`) |
| solicitud `in_transit → delivered` | automática, dentro de la RPC que marca la última entrega | cuando ninguna entrega queda `pending`, **aunque todas hayan quedado `failed`** |

- **Precedencia de las dos RPC nuevas:**
  1. actor (`UNAUTHENTICATED` → `UNAUTHORIZED_ACTOR`);
  2. elegibilidad del repartidor (`NOT_FOUND` → `COURIER_SUSPENDED` → `COURIER_NOT_APPROVED`);
  3. parámetros (`VALIDATION_ERROR` / `REASON_REQUIRED`);
  4. lock `delivery_requests for update` y después `delivery_request_drops for update` (`NOT_FOUND`);
  5. pertenencia a la oferta `accepted` (`UNAUTHORIZED_ACTOR`);
  6. idempotencia;
  7. estado (`INVALID_STATE_TRANSITION` si la solicitud no está `in_transit` o la entrega no está `pending`).
- **Idempotencia:** marcar `delivered` una entrega que ya está `delivered`, o `failed` una que ya está `failed`,
  devuelve éxito con `idempotent: true` y sin eventos. Pasar de `delivered` a `failed` (o al revés) responde
  `INVALID_STATE_TRANSITION`.
- **Concurrencia:** las dos RPC toman primero el lock de la solicitud. Así, dos marcas concurrentes de las últimas
  entregas se serializan y el cierre automático a `delivered` ocurre exactamente una vez.
- **`mark_delivered(p_request_id)`:** se mantiene por compatibilidad solo si `drops_count = 1`; marca la única entrega
  y la solicitud. Con `drops_count > 1` responde `INVALID_STATE_TRANSITION`.
- **`report_no_show`** (`matched → published`, el repartidor no llegó al local) no cambia: aplica a toda la solicitud.
  `report_incident` sigue siendo por solicitud.
- **`allDropsFailed`** es un valor **derivado** de los estados de las entregas (`drops_count > 0` y todas `failed`).
  No hay columna mutable en `delivery_requests`. El admin lo ve en el detalle a partir de las entregas.
- **Eventos:** entrega marcada (Realtime al comercio). La solicitud que pasa a `delivered` dispara los eventos
  actuales. Un éxito idempotente no emite nada.

### 7. Distancia sin romper la RPC pública

- **`public.calculate_route_distance` conserva** firma, permisos, fórmula y semántica.
- **Helper privado del segmento:** se extrae el cálculo de un segmento a `app_private.route_segment_distance(...)`,
  con la misma fórmula D15 (Haversine × 1,30 y redondeo a 500 m, mínimo 500 m) y el mismo fallback al centroide.
  - Permisos: `security definer`, `set search_path = public, pg_temp`,
    `revoke all … from public, anon, authenticated` y sin `grant` a clientes.
  - Lo usan la RPC pública (que devuelve lo mismo que hoy) y `publish_request`.
- **Multi-drop:** la ruta canónica es retiro → `position 1` → `position 2` → … → `N`.
  - Cada tramo se redondea por separado y se guarda en `delivery_request_drops.approx_distance_m`.
  - `delivery_requests.route_distance_m` es la **suma de los tramos ya redondeados**, para que coincida con lo que se
    muestra por tramo.
  - El fallback al centroide se aplica por tramo.
  - Si un tramo no se puede calcular según las reglas de T-330, ese tramo queda en `NULL` y el total queda en `NULL`.
    No se suma un total parcial.
- **Con un drop,** el resultado es idéntico al de hoy.

### 8. Precio, cobro y orden: decisiones resueltas (Lautaro073, 2026-10-05)

- **Precio por entrega.** `offers.amount_ars` y `delivery_requests.fixed_price_ars` (CC-021) son por entrega. El piso
  `min_offer_ars` se aplica por entrega.
  - `totalAmountArs = amountArs × drops_count` es el total **cotizado originalmente** del viaje. Se calcula en
    lectura y no se guarda.
  - Lo exponen las salidas de `submit_offer`, `take_request`, `accept_offer` y las vistas. `amountArs` sigue siendo el
    monto por entrega.
  - `take_request` (CC-021) no cambia su idempotencia ni sus locks; solo suma `totalAmountArs`.
- **Todas las entregas fallan.** La solicitud pasa igual a `delivered`, porque el viaje operativo terminó. No se crea
  un estado global `failed`. `allDropsFailed` es derivado (§6).
- **Entrega fallida.** Una entrega `failed` no genera importe a cobrar al destinatario.
  - Si una vista necesita mostrarlo, deriva `collectibleAmountArs = amountArs × cantidad de entregas delivered`.
  - No se guarda ningún registro de pagos ni se afirma que se cobró: cadeApp no procesa pagos (D14).
  - «Avisar a mi cliente» manda un mensaje por destinatario con su propio monto.
- **Orden.** `position` lo define el comercio y es el orden **canónico** para estimar la ruta (§7).
  - El repartidor puede marcar cualquier entrega `pending` como `delivered` o `failed`, sin exigir secuencia.
  - Si entrega en otro orden, la distancia guardada no se recalcula.

### 9. Migración y backfill

- Crea las tablas, grants, policies, el helper de distancia, la columna `drops_count`, el setting y las RPC nuevas o
  actualizadas.
- Por cada solicitud existente crea su drop `position = 1` y su `drop_contacts`, copiando las columnas legacy:
  - `status` es `delivered` (con `delivered_at` de la solicitud) si la solicitud está `delivered`, y `pending` en
    cualquier otro caso;
  - `delivery_requests.notes` se copia a `drop_contacts.notes` y queda en `NULL` en la fila legacy, lo que cierra la
    exposición previa para esas filas.
- La migración es idempotente: no crea un segundo drop si ya existe uno.

### 10. Compatibilidad, rollout y rollback

**Orden de rollout, cada paso desplegable por separado:**

1. Esquema + puente de §5 + backfill. La UI actual (un destino) sigue creando y publicando sin cambios.
2. Lectores: el feed, las ofertas, el viaje, el historial, «Avisar a mi cliente» y el admin leen drops. Dejan de leer
   las columnas legacy de destino y `delivery_requests.notes`.
3. Escritor: el formulario multi-drop con «Agregar otra entrega». **No se habilita antes de que el paso 2 esté
   desplegado.**
4. Retiro del puente y de las columnas legacy: con **otro CC**, cuando ningún lector ni escritor las use.

- **UI vieja contra el esquema nuevo:** soportada por el puente durante los pasos 1–3.
- **UI nueva contra el esquema viejo:** no se soporta. El paso 3 exige la migración aplicada; el orden de deploy lo
  garantiza (`migrate-develop` antes del deploy).
- **Rollback:** antes del paso 3, revertir la UI no rompe nada porque el puente sigue. Después del paso 3, las
  solicitudes con N > 1 drops no se pueden representar en el modelo legacy, así que no hay rollback del esquema.
  Se avanza con un arreglo hacia adelante.

- `DOMAIN_ERROR_CODES` suma `DROP_LIMIT_EXCEEDED`, con su mensaje en `src/lib/error-messages.ts`: «Superaste la

- `rpc-contracts.ts`:

  - `publish_request` suma `DROP_LIMIT_EXCEEDED`;

- El fake replica el puente, el tope, los estados, el cierre automático y la idempotencia.

## Motivo

T-340 (#258). Lautaro073 (2026-10-05): un local quiere que un mismo repartidor retire varios pedidos y los lleve a
destinos distintos, publicados como un único anuncio con «Agregar otra entrega». El contrato actual modela un solo
destino por solicitud, en columnas de `delivery_requests` y en una fila de `delivery_request_contacts` por solicitud,
y no tiene estado por destino.
