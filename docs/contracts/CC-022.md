# CC-022 — Varias entregas por solicitud

- **Issue:** #261 (label `contract-change`) · **Abre:** Lautaro073 · **Fecha:** 2026-10-05
- **Contrato afectado:**
  - tablas nuevas `public.delivery_request_drops` y `public.delivery_request_drop_contacts`, con sus policies;
  - columnas de destino de `public.delivery_requests`;
  - `platform_settings.max_drops_per_request`;
  - RPC `publish_request`, `submit_offer`, `take_request` (CC-021), `accept_offer`, `mark_delivered` y
    `report_no_show`;
  - RPC nuevas `mark_drop_delivered` y `mark_drop_failed`;
  - `calculate_route_distance`;
  - `src/domain/rpc-contracts.ts`, `src/domain/errors.ts`, fake de dominio y `src/types/database.types.ts`.
- **Tareas bloqueadas:** T-340 (#258)
- **Depende de:** CC-021 (#260)

## Actual

- Una solicitud tiene **un solo destino**:
  - en `delivery_requests`: `dropoff_zone_id`, `package_type`, `recipient_payment_method`, `needs_change`,
    `cash_change_amount`, `notes`, `approx_distance_m` y `route_distance_m`;
  - en `delivery_request_contacts`, con `request_id` como clave: `dropoff_address`, `dropoff_lat`, `dropoff_lng`,
    `recipient_name`, `recipient_phone` y `recipient_consent_declared` (más los datos de retiro).
- La oferta (`offers.amount_ars`) es el precio de ese único envío.
- Estados (§5.1): `matched → in_transit` (`mark_picked_up`), `in_transit → delivered` (`mark_delivered`) y
  `matched → published` por «no llegó» (`report_no_show`). No existe el estado de una entrega individual.
- La distancia se calcula en el servidor entre el retiro y el destino, Haversine × 1,30, redondeada a 0,5 km (D15).

## Propuesto

### 1. Esquema

```sql
-- Datos no sensibles de cada entrega (los ve el repartidor antes de ofertar, como hoy el destino de la solicitud).
create table public.delivery_request_drops (
  id uuid primary key default gen_random_uuid(),
  request_id uuid not null references public.delivery_requests(id) on delete cascade,
  position smallint not null check (position >= 1),
  dropoff_zone_id uuid not null references public.zones(id),
  package_type public.package_type not null,
  recipient_payment_method public.recipient_payment_method not null,
  needs_change boolean not null default false,
  cash_change_amount integer null,
  notes text null,
  approx_distance_m integer null,       -- tramo anterior → esta entrega, redondeado a 0,5 km
  status text not null default 'pending' check (status in ('pending', 'delivered', 'failed')),
  delivered_at timestamptz null,
  failed_reason text null,
  unique (request_id, position)
);

-- Datos sensibles de cada destinatario (D3): misma RLS que delivery_request_contacts.
create table public.delivery_request_drop_contacts (
  drop_id uuid primary key references public.delivery_request_drops(id) on delete cascade,
  dropoff_address text not null,
  dropoff_lat double precision null,
  dropoff_lng double precision null,
  recipient_name text not null,
  recipient_phone text not null,
  recipient_consent_declared boolean not null
);

alter table public.delivery_requests add column drops_count smallint not null default 1 check (drops_count >= 1);
```

- **Fuente de verdad:** los destinos viven en `delivery_request_drops` y `delivery_request_drop_contacts`.
  `delivery_request_contacts` conserva solo el retiro (`pickup_address`, `pickup_lat` y `pickup_lng`).
- **Columnas de destino de `delivery_requests`** (`dropoff_zone_id`, `package_type`, `recipient_payment_method`,
  `needs_change`, `cash_change_amount` y `notes`) y las de destino de `delivery_request_contacts`: quedan
  **deprecadas**.
  - Durante T-340 un trigger las mantiene como espejo de la entrega `position = 1`, para no romper a los lectores
    mientras se migran.
  - Un CC posterior las elimina cuando ningún lector las use.
  - Ninguna lectura nueva puede usarlas.
- **`drops_count`:** lo fija `publish_request` (cantidad de entregas en el borrador) y no cambia después.
- **Migración de datos:** cada solicitud existente recibe una entrega `position = 1`, copiada de sus columnas y
  contactos actuales. Su `status` sale del estado de la solicitud: `delivered` si la solicitud está `delivered`,
  `pending` en cualquier otro caso.

### 2. RLS

- **`delivery_request_drops`:** select igual que `delivery_requests`:
  - comercio dueño;
  - repartidor, sobre solicitudes `published` no vencidas o donde es el aceptado;
  - admin.
  
  Insert, update y delete del comercio dueño solo mientras la solicitud está en `draft`. Las transiciones de
  `status`, `delivered_at` y `failed_reason` solo las hacen las RPC.
- **`delivery_request_drop_contacts`:** copia exacta de las policies de `delivery_request_contacts`. El select queda
  para el comercio dueño, el repartidor aceptado (`app_private.is_courier_assigned_to_request`) y el admin. Escritura
  del comercio solo en `draft`. Entra en la matriz RLS.

### 3. Tope

`platform_settings.max_drops_per_request`, entero ≥ 1, con valor inicial `5`. Se edita con la RPC de settings del admin
existente (validación `INVALID_SETTING_VALUE`).

### 4. Precio

- `offers.amount_ars` y `delivery_requests.fixed_price_ars` (CC-021) significan **precio por entrega**. El piso
  `min_offer_ars` se aplica por entrega.
- **Total del viaje:** `amount_ars × drops_count`. Se calcula en lectura y no se guarda.
  - Las salidas de `submit_offer`, `take_request`, `accept_offer` y las vistas lo exponen como `totalAmountArs`.
  - `amountArs` sigue siendo el monto por entrega.
- **«Avisar a mi cliente»:** cada destinatario recibe un mensaje con su propio monto, el de su entrega.

### 5. `publish_request`

Validaciones nuevas, después del paso 7 de la precedencia vigente (contacto, zonas y bordes) y antes de
`OFFER_BELOW_MINIMUM` (CC-021) y `RATE_LIMITED`:

1. al menos una entrega → `MISSING_REQUIRED_FIELDS`;
2. `count(drops) > max_drops_per_request` → nuevo `DROP_LIMIT_EXCEEDED`;
3. cada entrega con zona activa y pin dentro de Aguilares → `INVALID_ZONE` / `OUT_OF_BOUNDS_AGUILARES`;
4. `position` consecutivas desde 1 → `VALIDATION_ERROR`.

Además:

- **Distancia:** `calculate_route_distance` recorre retiro → entrega 1 → … → entrega N. Guarda el tramo en cada
  `approx_distance_m` de entrega y la suma redondeada en `delivery_requests.route_distance_m`. Mantiene la regla
  NULL de T-330 si falta un punto.
- La salida suma `dropsCount`.

### 6. Estados

La solicitud mantiene su máquina de estados (§5.1). Se agrega el estado por entrega:

| Transición | Quién | Regla |
|---|---|---|
| entrega `pending → delivered` | repartidor aceptado, solicitud `in_transit` | RPC nueva `mark_drop_delivered(p_drop_id)` |
| entrega `pending → failed` | repartidor aceptado, solicitud `in_transit` | RPC nueva `mark_drop_failed(p_drop_id, p_reason)`, motivo obligatorio (`REASON_REQUIRED`) |
| solicitud `in_transit → delivered` | automática | cuando ninguna entrega queda `pending` y al menos una quedó `delivered` |
| solicitud `in_transit → delivered` con todas `failed` | automática | **decisión abierta 1** |

- `mark_delivered(p_request_id)` se mantiene por compatibilidad, solo si `drops_count = 1`. Marca la única entrega y
  la solicitud. Con `drops_count > 1` responde `INVALID_STATE_TRANSITION`.
- `report_no_show` (`matched → published`, «el repartidor no llegó al local») no cambia: aplica a toda la solicitud,
  porque el retiro es uno solo.
- `report_incident` sigue siendo por solicitud. El texto puede nombrar la entrega; no se agrega `drop_id` en esta
  versión.
- Precedencia de errores de las dos RPC nuevas:
  1. actor (`UNAUTHENTICATED` → `UNAUTHORIZED_ACTOR`);
  2. elegibilidad del repartidor (`NOT_FOUND` → `COURIER_SUSPENDED` → `COURIER_NOT_APPROVED`);
  3. pertenencia a la oferta `accepted` (`UNAUTHORIZED_ACTOR`);
  4. parámetros (`VALIDATION_ERROR` / `REASON_REQUIRED`);
  5. entrega (`NOT_FOUND`);
  6. estado (`INVALID_STATE_TRANSITION` si la solicitud no está `in_transit` o la entrega no está `pending`).
- **Eventos:** entrega marcada (Realtime al comercio). La solicitud `delivered` dispara los mismos eventos que hoy.

### 7. Feed y privacidad (D3)

Antes de aceptar, el repartidor ve por cada entrega solo:

- barrio;
- distancia aproximada del tramo;
- tipo de paquete;
- medio de pago (con cambio si aplica).

También ve un resumen (por ejemplo «3 entregas: 2 mediano, 1 grande») y el total. No ve direcciones, nombres,
teléfonos ni coordenadas: eso vive en `delivery_request_drop_contacts` y lo ve solo el aceptado. Sin mapa antes de
aceptar (D15).

### 8. Dominio

- `DOMAIN_ERROR_CODES` suma `DROP_LIMIT_EXCEEDED`, con mensaje «Superaste la cantidad máxima de entregas por envío».
- `rpc-contracts.ts`:
  - suma `mark_drop_delivered` y `mark_drop_failed`;
  - agrega `dropsCount` y `totalAmountArs` en las salidas;
  - `publish_request` suma `DROP_LIMIT_EXCEEDED`.
- El fake replica las reglas y la transición automática a `delivered`.

## Decisiones abiertas para la revisión

1. **Todas las entregas `failed`.** Recomendado: la solicitud pasa igual a `delivered` (el viaje terminó) con una
   marca `all_drops_failed` visible para el admin, para no inventar un estado nuevo. Alternativa: estado nuevo
   `failed`, que exige tocar §5.1, `request_cycle` y todas las vistas de historial.
2. **Pago de una entrega `failed`.** El destinatario que no estuvo no pagó, así que el repartidor cobra solo las
   entregas `delivered`. Recomendado: solo informativo en la vista del viaje, sin lógica de cobro (cadeApp no procesa
   pagos, D14).
3. **Orden de las entregas.** Recomendado: lo fija el comercio y el repartidor no lo cambia en esta versión; puede
   entregar en otro orden, porque `mark_drop_delivered` no exige secuencia.

## Motivo

T-340 (#258). Lautaro073 (2026-10-05): un local quiere que un mismo repartidor retire varios pedidos y los lleve a
destinos distintos, publicados como un único anuncio con «Agregar otra entrega». El contrato actual modela un solo
destino por solicitud, en columnas de `delivery_requests` y en una fila de `delivery_request_contacts` por solicitud,
y no tiene estado por destino.
