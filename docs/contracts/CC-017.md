# CC-017 — Permitir zonas activas sin centroide verificado

- **Issue:** #189 (label `contract-change`) · **Abre:** Lautaro073 · **Fecha:** 2026-10-02
- **Contrato afectado:** tabla `public.zones`, semántica de `getActiveZones()` y fallback de distancia de solicitudes
- **Tareas bloqueadas:** T-326 (#190); transitivamente T-313 (#45) y T-314 (#46)

## Actual

`public.zones` define:

```sql
constraint zones_centroid_pair
  check ((centroid_lat is null) = (centroid_lng is null)),
constraint zones_centroid_lat_bounds
  check (centroid_lat is null or centroid_lat between -27.4550 and -27.4100),
constraint zones_centroid_lng_bounds
  check (centroid_lng is null or centroid_lng between -65.6400 and -65.5950),
constraint zones_active_centroid
  check (not active or centroid_lat is not null)
```

Por lo tanto, toda zona `active=true` necesita un centroide.

El seed vigente contiene una única zona general:

```text
Aguilares · centroid_lat=-27.431480 · centroid_lng=-65.614660 · active=true
```

`getActiveZones()` ya modela `centroidLat/centroidLng` como nullable y el onboarding de comercio ya sabe operar cuando el centroide es null, pero el constraint impide que ese estado exista para una zona activa real.

En creación de solicitudes, si no llegan coordenadas explícitas, la action intenta calcular distancia con los centroides de las zonas. Si alguno falta, la implementación actual deja `route_distance_m` / `approx_distance_m` en null y continúa la creación.

## Propuesto

### 1. Zona activa sin centroide

Permitir:

```text
active=true
centroid_lat=null
centroid_lng=null
```

Eliminar únicamente `zones_active_centroid`.

Se preservan:
- `zones_centroid_pair`: nunca una coordenada suelta;
- bounds de lat/lng cuando el centroide existe;
- unicidad de `name`;
- RLS y permisos actuales.

### 2. Semántica normativa de `centroid = null`

Una zona activa sin centroide significa:

> **zona/barrrio seleccionable por nombre, sin fallback geográfico verificado.**

No significa centro de Aguilares, no habilita coordenadas sintéticas y no debe provocar que ningún consumidor invente lat/lng.

### 3. Onboarding de comercio

Si el barrio elegido tiene centroide null:
- `defaultPickupZoneId` se persiste normalmente;
- no se rellenan `defaultPickupLat/defaultPickupLng` a partir del barrio;
- el mapa usa su fallback general vigente;
- el usuario puede fijar pin/GPS o continuar con dirección manual conforme a T-323.

### 4. Creación de solicitudes

Si faltan coordenadas explícitas y uno o ambos barrios seleccionados no tienen centroide:
- la solicitud NO falla por ese motivo;
- `route_distance_m` y `approx_distance_m` pueden quedar null;
- no se reemplaza el centroide faltante por `AGUILARES_CENTER` ni por otra coordenada inventada.

Cuando ambos centroides existen, el fallback de distancia actual se conserva.

### 5. Datos T-326 y centroides cartográficos derivados

T-326 podrá insertar barrios reales como `active=true` con ambos centroides null cuando no exista una posición suficientemente sustentada.

El plano municipal 2015 aportado para T-326 permite además una segunda clase de dato válida:

> **centroide cartográfico derivado**: coordenada WGS84 obtenida al georreferenciar la geometría del barrio representada en el plano municipal contra puntos de control reales de Aguilares.

Un centroide derivado es aceptable únicamente si la evidencia T-326 documenta:
- archivo/plano fuente e identidad/hash;
- puntos de control utilizados y sus coordenadas WGS84;
- transformación aplicada (afín/proyectiva u otra justificada);
- error/residuales de control;
- polígono o punto representativo extraído para el barrio;
- validación visual de que la coordenada resultante cae dentro del barrio correcto.

Si la geometría es ambigua, el barrio es multipartito, la transformación local no es confiable o el punto derivado cae fuera del área atribuida, el centroide debe quedar `NULL`.

No se considera válido:
- geocodificar solo el nombre del barrio;
- copiar `AGUILARES_CENTER`;
- copiar el centroide general de otra zona;
- mover manualmente un pin “a ojo” sin evidencia de georreferenciación.

La ausencia de un centroide derivado confiable nunca impide que el barrio exista como zona activa.

## Motivo

T-326 necesita poblar `zones` con barrios reales de Aguilares para el onboarding del comercio.

El PDF municipal aportado contiene el plano por barrios con numeración y geometría urbana suficiente para intentar una georreferenciación reproducible. Eso permite derivar centroides cartográficos aproximados con trazabilidad, sin tratarlos como centroides oficiales.

Usar el punto general de Aguilares para todos los barrios seguiría falseando el dato. La alternativa aceptada es: **derivar con método documentado o dejar NULL**.

## Impacto

- ¿Toca alguna decisión D1–D14 del master plan o algo que ve el usuario? **Sí.** Un barrio puede recentrar aproximadamente si posee un centroide cartográfico derivado con evidencia; de lo contrario queda sin centroide. Lautaro073 decidió priorizar datos trazables: **centroide derivado del plano municipal o NULL; nunca coordenadas inventadas**.
- ¿Debilita un chequeo de seguridad (RPC, RLS, storage)? **No.**
- Migración necesaria: **sí**, para eliminar `zones_active_centroid`.
- Fake de dominio a actualizar: **no cambia tipo**; `ZoneOption` ya admite centroides null.
- Tests a actualizar/crear:
  - `supabase/tests/cc017_zones_without_centroid.sql`;
  - regresión en `src/features/requests/actions.test.ts` para zona sin centroide y ausencia de pin;
  - cualquier test estructural que afirme la existencia de `zones_active_centroid`.
- RLS: **sin cambios**.
- RPC: **sin cambios**.
