# CC-013 — Generación de `database.types.ts` independiente de la plantilla del generador

- **Issue:** #125 (label `contract-change`) · **Abre:** Lautaro073 (Claude Code) · **Fecha:** 2026-09-29
- **Contrato afectado:** generación de `src/types/database.types.ts` (`tools/db-types.mjs`). El archivo de tipos
  no cambia.
- **Tareas bloqueadas:** T-300 (#96)
- **Origen:** run `migrate` 36535421202 sobre `staging` `08b4b4d` (promoción #124): paso «Detect committed types
  drift against staging» en rojo.

## Actual
Dos checks comparan `src/types/database.types.ts` con `git diff --exit-code`, pero con generadores distintos:

| Check | Comando | Generador | Plantilla |
|---|---|---|---|
| `ci.yml` → `db-tests` (todo PR y push) | `pnpm db:types --local` | pg-meta del CLI contra la base local | sin `__InternalSupabase`, helpers sin paréntesis |
| `migrate.yml` → `migrate-staging` | `pnpm db:types` (`--project-id`) | servidor de Supabase | agrega `__InternalSupabase: { PostgrestVersion: "14.5" }` y envuelve entre paréntesis el condicional de `Tables`, `TablesInsert`, `TablesUpdate`, `Enums` y `CompositeTypes` |

Con el mismo esquema, ningún archivo commiteado satisface a los dos: el actual (blob `51a224d`) pasa `db-tests` y
falla `migrate-staging`. La salida remota (blob `caa03af`, reconstruida del diff del run) haría lo contrario.

## Propuesto
`tools/db-types.mjs` exporta `normalizeGeneratedTypes(source)` y la aplica a la salida del CLI antes de escribir:

1. quita el bloque de 5 líneas `// Allows to automatically instantiate createClient…` / `__InternalSupabase: {
   PostgrestVersion: "…" }`;
2. quita los paréntesis de `extends (X extends {` … `: never) = never,` en los helpers.

Es idempotente sobre la plantilla local, así que `db-tests` genera exactamente lo mismo que hoy. Con los archivos
reales: `normalizeGeneratedTypes(caa03af) === 51a224d` byte a byte. El script además deja de ejecutarse al
importarse (corre solo si se lo invoca directo), para poder probar la función.

## Motivo
T-300 necesita `migrate-staging` verde de punta a punta. El check tiene que comparar esquema, no versión del
generador. Se descartó commitear la salida remota (primer intento de CC-013, `d52c4e7`): rompe `db-tests`.

## Impacto
- ¿Toca alguna decisión D1–D14 del master plan o algo que ve el usuario? **no**.
- ¿Debilita un chequeo de seguridad (RPC, RLS, storage)? **no**. Los dos checks de drift quedan igual y siguen
  detectando cualquier diferencia de tablas, columnas, vistas, funciones, enums o tipos compuestos (probado en
  `tools/db-types.test.ts`). Lo único que se descarta es metadata de la plantilla, que el archivo commiteado ya no
  tenía, así que `supabase-js` infiere igual que hoy.
- Migración necesaria: no · Fake de dominio a actualizar: no · Tests: nuevo `tools/db-types.test.ts`.
- Si Supabase vuelve a cambiar la plantilla remota, el drift reaparece en `migrate-staging` con un diff de plantilla
  y hay que ampliar `normalizeGeneratedTypes`.
