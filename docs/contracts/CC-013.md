# CC-013 — `database.types.ts` generado con la plantilla remota (staging)

- **Issue:** #<n> (label `contract-change`) · **Abre:** Lautaro073 (Claude Code) · **Fecha:** 2026-09-29
- **Contrato afectado:** `src/types/database.types.ts` (tipos generados; sin cambios de esquema ni de RPC)
- **Tareas bloqueadas:** T-300 (#96)
- **Origen:** run `migrate` 36535421202 sobre `staging` `08b4b4d` (promoción #124): paso «Detect committed types
  drift against staging» en rojo.

## Actual
`src/types/database.types.ts` (blob `51a224d`) se generó con el typegen local: no trae el bloque
`__InternalSupabase` y los helpers `Tables`, `TablesInsert`, `TablesUpdate`, `Enums` y `CompositeTypes` escriben
los tipos condicionales de sus parámetros sin paréntesis (`extends X extends {…} ? … : never = never`).

`migrate-staging` regenera los tipos con `pnpm db:types`, que con `SUPABASE_PROJECT_REF` llama a
`supabase gen types typescript --project-id <ref>` contra el proyecto remoto, y compara con `git diff --exit-code`.
La salida remota usa la plantilla nueva, así que el check falla aunque el esquema sea idéntico.

## Propuesto
El archivo queda exactamente como lo genera staging (blob `caa03af`, el `index 51a224d..caa03af` del diff del run):

- agrega, al principio de `Database`:
  ```ts
  // Allows to automatically instantiate createClient with right options
  // instead of createClient<Database, { PostgrestVersion: 'XX' }>(URL, KEY)
  __InternalSupabase: {
    PostgrestVersion: "14.5"
  }
  ```
- envuelve entre paréntesis el condicional de los parámetros de tipo de los cinco helpers
  (`extends (X extends {…} ? … : never) = never`).

Ninguna tabla, columna, vista, función, enum ni tipo compuesto cambia. El archivo se reconstruyó aplicando el diff del
log del run al blob `51a224d` (sin correr comandos contra Supabase) y `git hash-object` da `caa03af`.

## Motivo
T-300 necesita `migrate-staging` verde de punta a punta. El único paso rojo es este drift de plantilla. El comentario
de `migrate.yml` define que, después de aplicar las migraciones, staging es la verdad: el archivo commiteado se alinea
a esa salida y el check no se toca.

## Impacto
- ¿Toca alguna decisión D1–D14 del master plan o algo que ve el usuario? **no**.
- ¿Debilita un chequeo de seguridad (RPC, RLS, storage)? **no**. El check de drift queda igual.
- Migración necesaria: no · Fake de dominio a actualizar: no · Tests a actualizar: ninguno.
- `PostgrestVersion` le indica a `supabase-js` la versión de PostgREST para inferir tipos de consultas. Con el archivo
  nuevo, `pnpm typecheck` y `pnpm lint` pasan sin cambios en el código.
- Quien regenere los tipos tiene que hacerlo contra el proyecto remoto (`pnpm db:types` con `SUPABASE_PROJECT_REF`),
  no contra una base local, o el drift vuelve.
