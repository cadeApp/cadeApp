# CC-008 — Proyección mínima post-matched para datos de contacto e identidad (comercio y cadete)

- **Issue:** #21 (T-115, decisión D03 / 2-A) · **Abre:** Persona P2 (agy) · **Fecha:** 2026-09-25
- **Contrato afectado:** Esquema / RPC / RLS (`delivery_requests`, `delivery_request_contacts`, `profiles`, `couriers`, o función RPC de viaje `get_trip_details`)
- **Tareas bloqueadas:** T-115 (#21)

## Actual
1. `delivery_requests` almacena `merchant_id`, `pickup_zone_id`, `dropoff_zone_id`, `package_type`, `recipient_payment_method`, etc. No tiene dirección de retiro ni datos de entrega directos (viven en `delivery_request_contacts`). Tampoco tiene columna `code` (por decisión D04, el código visual se deriva del UUID).
2. `delivery_request_contacts` almacena `recipient_name`, `recipient_phone`, `dropoff_address`, `pickup_address`. No almacena `merchant_phone` ni notas especiales (`delivery_notes`).
3. Las tablas `profiles` y `couriers` contienen datos sensibles (documentos, historial, estado operativo) protegidos por RLS.
4. No existe una proyección segura post-`matched` que exponga de forma cruzada y atómica:
   - Al comercio: nombre del cadete, teléfono de WhatsApp (`wa.me`), tipo de vehículo, patente y avatar seguro.
   - Al cadete: nombre del comercio, teléfono del comercio para coordinación, además de los datos de entrega del destinatario.

## Propuesto
1. Implementar una función RPC o vista segura `get_trip_details(p_request_id uuid)` con `SECURITY DEFINER` que:
   - Valide que el actor (`auth.uid()`) sea el comercio dueño (`merchant_id`) o el repartidor asignado (`accepted_offer.courier_id`).
   - Verifique que la solicitud esté en estado `matched`, `in_transit` o `delivered` (post-match).
   - Proyecte de forma mínima y controlada:
     - Datos del viaje: `id`, `code` (derivado de UUID: `REQ-<primeros 8 caracteres>`), `status`, `pickup_address`, `dropoff_address`, `recipient_name`, `recipient_phone`, `recipient_payment_method`, `needs_change`, `cash_change_amount`, `amount_ars` (de la oferta aceptada).
     - Datos del cadete (visible para el comercio): `courier_name`, `courier_phone`, `vehicle_type`, `vehicle_plate`, `avatar_url`.
     - Datos del comercio (visible para el cadete): `merchant_name`, `merchant_phone`.
2. Mantener cerradas por RLS las tablas completas de `profiles` y `couriers` (D03), evitando fugas de PII o accesos excesivos.

## Motivo
T-115 implementa las vistas C06 (comercio) y R07 (repartidor). Para coordinar el viaje y ejecutar la acción "Avisar a mi cliente" se requieren datos de contacto cruzados (teléfono del cadete para el comercio y teléfono del comercio para el cadete), garantizando que ningún dato se filtre antes de `matched` (D3, D15) y respetando las políticas de RLS.
