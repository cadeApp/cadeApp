  - Wrapper de servidor: `src/server/rpc/push-subscriptions.ts` (nuevo).

## Actual

Verificado en `origin/develop@54bbdcd7`:

1. `public.push_subscriptions` (`supabase/migrations/20260922031435_schema_v1.sql:165`) tiene `endpoint text not null
   unique` y `user_id` del dueño.
2. La policy `push_subscriptions_all_self` (`20260925170000_cc007_consent_enforcement.sql:312`) solo permite filas con
   `user_id = auth.uid()` en `using` y en `with check`.
3. `POST /api/push/subscriptions` (`src/app/api/push/subscriptions/route.ts:41-50`) hace
   `upsert({ user_id, endpoint, … }, { onConflict: 'endpoint' })` con el cliente de sesión.
4. El endpoint push es único por navegador y origen, no por cuenta. Si el navegador ya tiene una fila con el mismo
   endpoint de **otra** cuenta, el `ON CONFLICT DO UPDATE` choca con la RLS y la ruta responde 500 (`Database error`).
5. El logout (`src/features/auth/actions.ts:367-370`) borra las suscripciones del usuario con el cliente admin, pero es
   best-effort. Una sesión que expira sin logout, o un borrado que falla, deja la fila de la cuenta anterior y la
   siguiente cuenta en ese navegador no puede suscribirse.

## Propuesto

```sql
public.register_push_subscription(p_payload jsonb) returns jsonb
-- security definer, set search_path = public, pg_temp
-- revoke all from public, anon, authenticated; grant execute to authenticated
```

Entrada:

```json
{ "endpoint": "https://…", "p256dh": "base64url", "auth": "base64url", "platform": "web" }
```

Salida (nunca devuelve el dueño anterior):

```json
{ "subscriptionId": "uuid", "created": true, "reassigned": false }
```

Validaciones, en este orden:

1. Sin sesión → `UNAUTHENTICATED`; `app_private.is_active_operational_actor()` falso → `UNAUTHORIZED_ACTOR` (la misma
   condición que la policy actual).
2. `endpoint` con esquema `https://` y hasta 2048 caracteres; `p256dh` y `auth` en base64url (`^[A-Za-z0-9_-]+$`,
   hasta 256 caracteres); `platform` nulo o `'web'` → si no, `VALIDATION_ERROR`.
3. `select id, user_id from public.push_subscriptions where endpoint = … for update`:
   - sin fila → `insert` con `user_id = auth.uid()`; `created: true`;
   - fila propia → actualiza claves, `platform` y `last_seen_at`; `created: false`, `reassigned: false`;
   - fila de otra cuenta → la reasigna (`user_id = auth.uid()`, claves nuevas, `last_seen_at = now()`) y escribe
     `audit_log` (`action = 'push_subscription_reassigned'`, `target_type = 'push_subscription'`, `before =
     {user_id}`, `after = {user_id}`); `reassigned: true`. Nunca se audita el endpoint ni las claves.
4. Una carrera de `insert` concurrente del mismo endpoint (`unique_violation`) se reintenta una vez por el camino de
   la fila existente.

## Seguridad y permisos

- **RLS:** sin cambios. Los clientes siguen sin poder leer ni escribir filas ajenas; la RPC es la única vía que cambia
  el dueño de un endpoint.
- **Grants:** `revoke all on function public.register_push_subscription(jsonb) from public, anon, authenticated;`
  `grant execute … to authenticated;`.
- **`security definer`** con `set search_path = public, pg_temp`; sin helpers nuevos.
- **Riesgo aceptado:** quien conozca el endpoint de otra persona puede reasignarlo y esa persona deja de recibir push en
  ese navegador. El endpoint es una URL de capacidad que solo conoce el navegador suscripto, no se loguea ni se expone
  en ninguna lectura, y el push es best-effort (AGENTS.md §2): nunca es la única forma de enterarse. Quien reasigna no
  recibe nada de la otra cuenta, porque las claves de cifrado pasan a ser las suyas.
- **Ruta:** `POST /api/push/subscriptions` pasa a llamar la RPC con el cliente de sesión; el `upsert` directo se retira
  (T-383). El `DELETE` sigue igual.

## Concurrencia e idempotencia

- **Locks:** solo la fila de `push_subscriptions` por `endpoint` (`FOR UPDATE`); no toma locks de `couriers`,
  `merchants` ni `profiles`. Sin deadlocks con otras RPC.
- **Reintentos:** la misma cuenta y el mismo endpoint actualizan la fila sin duplicarla ni auditar.
- **Carreras:** dos cuentas registran el mismo endpoint a la vez: el lock o la `unique_violation` serializan; queda una
  sola fila, del último commit, con una auditoría por reasignación. El envío (`src/server/push/sender.ts`) lee por
  `user_id` y tolera que la fila cambie de dueño entre lectura y envío (best-effort).
- **Prueba exigida en la PR de implementación:** pgTAP con los casos de abajo; la carrera de dos sesiones se cubre con
  `supabase/tests/integration/cc035_concurrency.mjs` (dos sesiones PostgreSQL reales, barreras deterministas, sin
  `sleep`): una sola fila final, sin `40P01`, y la mutación RED de quitar el reintento ante `unique_violation` deja la
  suite en rojo. Esta PR no afirma esa evidencia.

## Compatibilidad, rollout y rollback

- **Ruta vieja contra el esquema nuevo:** sigue con el `upsert` y su falla conocida; nada empeora.
- **Ruta nueva contra el esquema viejo:** no se despliega antes de la migración; T-383 empieza con la RPC en Develop.
- **Backfill:** ninguno.
- **Rollout:** 1) PR de implementación del CC. 2) T-383: la ruta llama la RPC y se suma el E2E de dos cuentas.
- **Rollback (forward-only):** antes de T-383, `drop function if exists` en una migración nueva. Después, primero se
  vuelve a desplegar la ruta con `upsert` y recién después el `drop`.

## Decisiones de producto

- El navegador pertenece a la cuenta logueada: al suscribirse, el endpoint se reasigna a esa cuenta y la anterior deja
  de recibir push en ese navegador — Lautaro073, 2026-10-20 (decisión en automático con la opción recomendada).
- Que el logout borre las suscripciones de **todos** los dispositivos del usuario
  (`src/features/auth/actions.ts:369`) queda fuera de este CC; se registra como nota en T-383.

## Motivo

#444 (QA staging, 2026-10-20) mostró que la falla del alta push no tiene forma de recuperarse si el endpoint quedó de
otra cuenta. No fue la causa de ese reporte (allí fallaba `pushManager.subscribe`), pero el bug es real y no se puede
resolver sin RPC porque la RLS impide tocar la fila ajena.
