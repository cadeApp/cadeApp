## Actual

Verificado en `origin/develop@54bbdcd7`:

1. `supabase/migrations/20261016210000_cc025_courier_document_replacement.sql:64` revoca `insert, update, delete`
   sobre `public.courier_documents` para `public, anon, authenticated`. Solo escriben las RPC.
2. `replace_courier_document` (mismo archivo, `:89`) exige un documento vigente del tipo: sin él, `NOT_FOUND`
   (`:225`). Con uno vigente que no esté `rejected`, `INVALID_STATE_TRANSITION` (`:242`). CC-025 lo declara así:
   «Si no existe documento previo vigente: rechaza con `NOT_FOUND` (el alta inicial debe ocurrir por el onboarding)».
3. `submit_courier_onboarding_documents` (CC-025 Subetapa B0) da de alta el lote inicial del onboarding; no está
   pensada para sumar un documento suelto después.
4. `couriers.license_status` y `couriers.insurance_status` son `document_review_status` con default `'none'`
   (`supabase/migrations/20260922031435_schema_v1.sql:55-56`).
5. La política de Storage `courier_docs_insert_own_folder` (`supabase/migrations/20260922051650_rls_v1.sql:492`) ya
   permite al repartidor subir a `courier/<auth.uid()>/…` en el bucket privado `courier-docs`.
6. UI: `src/features/courier-onboarding/components/courier-profile-view.tsx:97-98` muestra «No cargado» para `none` y
   la acción de carga (`DocumentReplacementCard`) solo aparece con `rejected` (`:235-239`).

Resultado: un repartidor que no cargó la licencia o el seguro en el onboarding no tiene forma de cargarlos después.

## Propuesto

```sql
public.add_courier_optional_document(p_payload jsonb) returns jsonb
-- security definer, set search_path = public, pg_temp
-- revoke all from public, anon; grant execute to authenticated
```

Entrada (`jsonb`):

```json
{ "kind": "license|insurance", "storagePath": "courier/<auth.uid()>/<kind>_<timestamp>.<ext>", "idempotencyKey": "uuid opcional" }
```

Salida:

```json
{ "documentId": "uuid", "kind": "license", "status": "submitted", "isCurrent": true, "idempotent": false }
```

Validaciones, en este orden (mismos códigos y forma que `replace_courier_document`):

1. Sin sesión → `UNAUTHENTICATED`. Perfil distinto de `courier` o consentimiento no `active` → `UNAUTHORIZED_ACTOR`.
2. `kind` distinto de `license` o `insurance` → `VALIDATION_ERROR` (DNI, selfie y avatar siguen por el onboarding y
   por `replace_courier_document`).
3. `storagePath` con prefijo literal `courier/<auth.uid()>/<kind>_`, sufijo `^[0-9]+[.](png|jpe?g|webp|pdf)$`, sin
   `..` ni `/` en el sufijo; `idempotencyKey` con formato UUID si viene → si no, `VALIDATION_ERROR`.
4. Lock `couriers` `FOR UPDATE` (sin fila → `NOT_FOUND`; `rejected` o `suspended` → `UNAUTHORIZED_ACTOR`), luego
   `profiles` `FOR SHARE` con revalidación de rol y consentimiento.
5. Idempotencia por `idempotencyKey` (misma clave y mismo path → devuelve el documento con `idempotent: true`; misma
   clave y otro path → `VALIDATION_ERROR`).
6. Documento vigente del mismo `kind` (`FOR UPDATE`):
   - mismo `storagePath` y `submitted` → `idempotent: true` (reintento sin clave);
   - cualquier otro vigente (`submitted`, `verified` o `rejected`) → `INVALID_STATE_TRANSITION`. Un rechazado se
     reemplaza con `replace_courier_document`.
7. El objeto tiene que existir en `storage.objects` (`bucket_id = 'courier-docs'`) → si no, `NOT_FOUND`.
8. Inserta la fila vigente en `submitted` (`is_current = true`, `rejection_code = null`), pone
   `couriers.<kind>_status = 'submitted'` y escribe `audit_log` (`action = 'add_courier_optional_document'`, sin PII:
   ids, `kind`, estado y clave de idempotencia).

No cambia `couriers.status` ni `doc_level`. El nivel de documentación solo sube cuando el admin verifica con
`admin_verify_document`, que ya opera sobre cualquier documento vigente en `submitted`.

## Seguridad y permisos

- **RLS:** sin cambios. La tabla sigue sin `insert/update/delete` para clientes; el repartidor sigue leyendo solo sus
  documentos vigentes (`courier_documents_select_self`).
- **Grants:** `revoke all on function public.add_courier_optional_document(jsonb) from public, anon;`
  `grant execute … to authenticated;`. La función valida rol, consentimiento y estado adentro.
- **`security definer`** con `set search_path = public, pg_temp`. No usa helpers `app_private` nuevos.
- **Acceso directo frente a RPC:** el `insert` directo sigue revocado (barrera de privilegios de tabla, `42501`). El
  estado `submitted` y la vigencia los fija la RPC; nunca `verified` (no hay autoaprobación).
- **Storage:** sin cambios; el path se valida contra `auth.uid()` y el objeto tiene que existir.

## Concurrencia e idempotencia

- **Locks y orden:** `couriers FOR UPDATE` → `profiles FOR SHARE` → `courier_documents FOR UPDATE`, el mismo orden
  que `replace_courier_document`, `submit_courier_onboarding_documents` y `admin_verify_document`. Sin deadlocks nuevos.
- **Reintentos:** misma `idempotencyKey` y mismo path, o sin clave con el mismo path ya vigente en `submitted`,
  devuelven `idempotent: true` sin duplicar filas ni auditoría.
- **Carreras:**
  - dos altas simultáneas del mismo `kind`: la segunda espera el lock de `couriers` y luego ve el vigente →
    `INVALID_STATE_TRANSITION` (o `idempotent` si es el mismo path); `courier_documents_unique_current` es la segunda
    barrera;
  - alta concurrente con una suspensión del admin: el lock de `couriers` serializa; si el admin suspende primero, la
    alta da `UNAUTHORIZED_ACTOR`.

## Compatibilidad, rollout y rollback

- **UI vieja contra el esquema nuevo:** no llama la RPC nueva; nada cambia.
- **UI nueva contra el esquema viejo:** no se despliega antes de la migración; T-376 empieza después de que CI aplique
  la migración en Develop.
- **Backfill:** ninguno.
- **Rollout:** 1) PR de implementación del CC: migración, contrato, fake, tipos, wrapper y pgTAP; CI la aplica en
  Develop al mergear. 2) T-376: UI del perfil, señal en admin y E2E, recién con la RPC desplegada en Develop.
- **Rollback:** `drop function public.add_courier_optional_document(jsonb)`; los documentos ya dados de alta quedan
  como cualquier documento vigente y el admin los puede seguir revisando.

## Decisiones de producto

- Solo `license` e `insurance` admiten alta posterior; DNI, selfie y avatar siguen por onboarding y reemplazo —
  Lautaro073, 2026-10-20.
- Pueden hacerlo repartidores `pending` y `approved`; `rejected` y `suspended` no — Lautaro073, 2026-10-20.
- El alta queda «En revisión» (`submitted`) y no cambia `doc_level` ni el estado del repartidor hasta que el admin
  verifique — Lautaro073, 2026-10-20.
- El admin ve que un repartidor aprobado tiene un documento opcional en revisión (T-376) — Lautaro073, 2026-10-20.
