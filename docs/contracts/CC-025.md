- **Tareas bloqueadas:** T-356 (#343, PR #358)

## Actual (antes de CC-025)

- **Esquema de `courier_documents`** (`supabase/migrations/20260922031435_schema_v1.sql:70-81`):
  Tiene PK `id`, `courier_id`, `kind`, `storage_path` (unique), `status`, `uploaded_at`, `purge_after`, `purged_at`.
  No posee columna de vigencia ni restricción de unicidad activa por `(courier_id, kind)`. Múltiples filas del mismo `kind` pueden coexistir sin un criterio unívoco de cuál es la vigente.
  No posee columna de motivo de rechazo público.
- **RLS de inserción** (`supabase/migrations/20260922051650_rls_v1.sql:251-258`):
  `courier_documents_insert_self` permite insertar a cualquier usuario autenticado con `courier_id = auth.uid()` y `status = 'submitted'`, sin verificar si ya existía un documento previo ni su estado (`rejected` o `verified`). Un cliente puede invocar directamente `insert` por API y saltarse cualquier validación de Server Action (PR358-H01).
- **RPC `admin_verify_document`** (`supabase/migrations/20260924013700_rpc_admin_v1.sql:174-260`):
  Recibe `p_document_id uuid`, `p_decision text`, `p_reason text default null`.
  Solo verifica `status = 'submitted'` y `purged_at is null`, pero no valida si el documento es el vigente (PR358-H02).
  Persiste `p_reason` únicamente en `audit_log.after->>'reason'`. Al ser `audit_log` de acceso exclusivo para administradores, el repartidor no tiene forma segura de conocer el motivo del rechazo sin exponer texto libre interno o requerir privilegios elevados.
- **Lecturas en aplicación** (`src/app/(courier)/courier/profile/page.tsx:68-70`, `src/features/admin/queries.ts:214-251`):
  El perfil del repartidor usa `docs.find((d) => d.kind === ...)` sobre un conjunto sin orden determinista de vigencia.
  Admin devuelve un listado ordenado por `uploaded_at asc` que mezcla versiones históricas con vigentes.
- **Purga de archivos** (`src/server/cron/sweep.ts:118-173`):
  Purga objetos de `courier-docs` cuando `purge_after <= now()` y `purged_at is null`.

## Propuesto

### 1. Esquema `courier_documents` y versión vigente única

En la **Fase A** (`supabase/migrations/20261015153311_cc025_expand_courier_documents.sql`, PR #374) se añaden tres columnas a `public.courier_documents`:
1. `is_current boolean not null default true`: Indica si el registro es la versión vigente activa para ese repartidor y tipo de documento.
2. `rejection_code text`: Código de catálogo seguro del motivo de rechazo (o `null`).
3. `idempotency_key text`: Clave UUID opcional de idempotencia por intento de reemplazo.

Durante la ventana de transición (Fases A, B0 y B), rigió el guard temporal `courier_documents_expansion_guard check (is_current = true and rejection_code is null and idempotency_key is null)`.

En la **Fase C** (`supabase/migrations/20261016210000_cc025_courier_document_replacement.sql`, PR #364) se retira `courier_documents_expansion_guard`, se ejecuta el backfill determinista de versiones históricas y se aplican las restricciones finales:

Restricción de unicidad parcial de vigencia en PostgreSQL:
```sql
create unique index courier_documents_unique_current
  on public.courier_documents (courier_id, kind)
  where (is_current = true);
```
Esta restricción garantiza a nivel de base de datos que jamás pueden existir dos documentos vigentes para el mismo `(courier_id, kind)`.

Restricción de unicidad parcial de idempotencia en PostgreSQL:
```sql
create unique index courier_documents_unique_idempotency
  on public.courier_documents (courier_id, kind, idempotency_key)
  where (idempotency_key is not null);
```

Check de catálogo seguro para `rejection_code`:
```sql
constraint courier_documents_rejection_code_check check (
  rejection_code is null or rejection_code in (
    'illegible',
    'expired',
    'data_mismatch',
    'wrong_type',
    'incomplete',
    'other_safe'
  )
)
```

### 2. Catálogo de rechazo seguro (Decisión 1C)

Se desacopla estrictamente la comunicación al repartidor de la nota interna del administrador:
- `rejection_code` (público / seguro para el courier): Enum/string con claves controladas:
  - `illegible`: "Documento borroso, ilegible o cortado."
  - `expired`: "Documento vencido o no vigente."
  - `data_mismatch`: "Los datos no coinciden con la identidad declarada."
  - `wrong_type`: "El archivo no corresponde al tipo de documento solicitado."
  - `incomplete`: "Documento incompleto (falta frente o dorso)."
  - `other_safe`: "Requiere nueva carga para verificación administrativa."
- `reason` (nota interna administrativa): Se mantiene exclusivamente en `public.audit_log (after->>'reason')` para trazabilidad y auditoría interna de administradores. Jamás se expone en `courier_documents`, ni en URLs, ni se proyecta hacia la UI del repartidor.

### 3. RPC pública `replace_courier_document` (Decisión 4C)

Firma explícita en PostgreSQL:
```sql
public.replace_courier_document(p_payload jsonb) returns jsonb
```

Entrada JSON:
```json
{
  "kind": "dni_front|dni_back|selfie|avatar|license|insurance",
  "storagePath": "courier/<auth.uid()>/<kind>_<timestamp>.<ext>",
  "idempotencyKey": "uuid opcional"
}
```

Reglas y comportamiento transaccional:
1. `SECURITY DEFINER` con `set search_path = public, pg_temp`.
2. Valida actor autenticado (`auth.uid()`) con rol `courier` y `consent_status = 'active'` en `profiles` (`UNAUTHENTICATED` / `UNAUTHORIZED_ACTOR`).
3. Valida formato canónico de `storagePath` (PR364-R06):
   - Comparación literal estricta de prefijo: `courier/<auth.uid()>/<kind>_` (`left(storagePath, length(expected_prefix)) = expected_prefix` o `starts_with`). No se utiliza `LIKE` con comodín `_` para evitar que nombres como `licenseX...` o `dniXfront_...` sean aceptados indebidamente.
   - Validación estricta de sufijo: el remanente posterior al prefijo debe cumplir `^[0-9]+[.](png|jpe?g|webp|pdf)$` (numérico entero para timestamp seguido de extensión aprobada para documentos), sin secuencias de escape `..` ni barras intermedias `/`.
   - Verifica la existencia física incondicional del objeto exacto en `storage.objects` (`bucket_id = 'courier-docs'`) previo a la promoción en DB; si no existe, falla con `NOT_FOUND` (PR364-H01).
4. Toma lock transaccional ordenado unificado en todo el sistema (PR364-H02 / B0-H03 / B0-H04):
   - Primero bloquea `couriers where profile_id = auth.uid() for update`. Si no existe la fila en `couriers`, rechaza con `NOT_FOUND`. Si `couriers.status in ('rejected', 'suspended')`, rechaza con `UNAUTHORIZED_ACTOR`.
   - Segundo revalida `profiles where id = auth.uid() for share` bajo el lock para detectar cambios concurrentes de rol o revocación de consentimiento (`UNAUTHORIZED_ACTOR`).
   - Tercero bloquea el documento vigente en `courier_documents` con `for update`.
5. Idempotencia persistida vía `idempotencyKey` (PR364-H07):
   - Si se incluye `idempotencyKey`, se valida formato UUID canónico.
   - Si ya existe un registro con esa misma clave para `(courier_id, kind)`:
     - Si el `storagePath` coincide, retorna éxito idempotente (`idempotent = true`) con el estado actual (incluso si fue verificado por admin) sin duplicar filas ni eventos en `audit_log`.
     - Si el `storagePath` difiere, rechaza con `VALIDATION_ERROR`.
6. Si no existe documento previo vigente: rechaza con `NOT_FOUND` (el alta inicial debe ocurrir por el onboarding).
7. Si el documento vigente actual tiene `status = 'submitted'` y el `storage_path` coincide con el del payload (fallback sin clave): devuelve éxito idempotente con `idempotent = true`.
8. Si el documento vigente actual tiene `status <> 'rejected'`: rechaza con `INVALID_STATE_TRANSITION` (no se permite reemplazar documentos aprobados o en revisión).
9. Desactiva el documento vigente anterior:
   - `is_current = false`.
   - `purge_after = coalesce(purge_after, now() + interval '30 days')` (Decisión B / D8: 30 días de retención histórica desde el reemplazo/obsolescencia antes de la purga física).
10. Inserta la nueva versión en `courier_documents`:
    - `status = 'submitted'`.
    - `is_current = true`.
    - `rejection_code = null`.
    - `idempotency_key = v_idempotency_key`.
    - `purge_after = null`, `purged_at = null`.
11. Sincroniza en `couriers`:
    - Si `kind = 'license'` -> `update public.couriers set license_status = 'submitted' where profile_id = auth.uid()`.
    - Si `kind = 'insurance'` -> `update public.couriers set insurance_status = 'submitted' where profile_id = auth.uid()`.
12. Registra auditoría inmutable en `public.audit_log` con acción `'replace_courier_document'`, IDs de documento anterior y nuevo, tipo, clave y estados, sin PII.
13. Retorna JSON:
```json
{
  "documentId": "uuid",
  "kind": "license",
  "status": "submitted",
  "replacedDocumentId": "uuid",
  "isCurrent": true,
  "idempotent": false
}
```

### 4. Ajuste en RPC `admin_verify_document` (PR358-H02 / PR364-H02)

Firma actualizada (retrocompatible mediante parámetros por defecto):
```sql
public.admin_verify_document(
  p_document_id uuid,
  p_decision text,
  p_reason text default null,
  p_rejection_code text default null
) returns jsonb
```
Reglas añadidas:
1. Lock unificado consistente (PR364-H02): identifica `courier_id`, toma lock `for update` sobre `couriers(profile_id)` primero, y luego toma lock `for update` sobre `courier_documents(id)` revalidando estado bajo el bloqueo.
2. Verifica que el documento objetivo tenga `is_current = true`. Si `is_current = false`, rechaza con `INVALID_STATE_TRANSITION` (impide que un administrador decida sobre una versión obsoleta).
3. Si `p_decision = 'rejected'`:
   - Exige `p_reason` no vacío (nota interna de auditoría).
   - Valida `p_rejection_code` contra el catálogo seguro (si es nulo, asigna por defecto `'other_safe'`).
   - Actualiza `courier_documents set status = 'rejected', rejection_code = v_rejection_code where id = p_document_id`.
   - Registra en `audit_log`: `reason` y `rejection_code`.
4. Si `p_decision = 'verified'`:
   - Actualiza `courier_documents set status = 'verified', rejection_code = null where id = p_document_id`.

## Seguridad y permisos

- **RLS y permisos en `courier_documents` (PR364-H03 / PR364-H04 / PR364-R07 / Decisión A):**
  - **Revocación total de inserciones y mutaciones directas (Decisión A, 2026-10-16):**
    `revoke insert, update, delete on table public.courier_documents from public, anon, authenticated;`.
    Ningún usuario cliente por API REST (ni courier, ni admin, ni anónimo) puede realizar INSERT, UPDATE ni DELETE directo sobre la tabla (mientras `service_role` conserva privilegios para tareas técnicas como `src/server/cron/sweep.ts`). Toda inserción o modificación de documentos se ejecuta de manera centralizada y transaccional a través de las RPCs `submit_courier_onboarding_documents` (alta inicial completa en bloque) y `replace_courier_document` (reemplazo individual de documentos rechazados), cerrando de raíz cualquier bypass REST inicial o secundario (SQLSTATE 42501).
  - Se eliminan las políticas permisivas `courier_documents_write_admin` heredada de `rls_v1` y `courier_documents_insert_self` (PR364-R07).
  - `courier_documents_select_admin`: Permite al admin autenticado consultar documentos vigentes e históricos para revisión y auditoría.
  - `courier_documents_select_self` (PR364-H04): El repartidor **SOLO puede consultar sus documentos vigentes** (`coalesce(is_current, true) = true`). Los documentos históricos reemplazados quedan completamente invisibles para el courier.
- **Grants y revokes:**
  - `revoke all on function public.submit_courier_onboarding_documents(jsonb) from public, anon; grant execute on function public.submit_courier_onboarding_documents(jsonb) to authenticated;`
  - `revoke all on function public.replace_courier_document(jsonb) from public, anon; grant execute on function public.replace_courier_document(jsonb) to authenticated;`
  - `admin_verify_document`: mantiene execute exclusivo para `authenticated` con verificación interna AAL2 (`app_private.assert_admin_aal2()`).
- **`security definer`:**
  - `submit_courier_onboarding_documents`, `replace_courier_document` y `admin_verify_document` son `security definer` con `set search_path = public, pg_temp`.

## Concurrencia e idempotencia

- **Locks y orden unificado (PR364-H02 / B0-H03 / B0-H04):**
  1. `couriers where profile_id = v_courier_id for update`
  2. `profiles where id = v_courier_id for share` (en las RPCs de courier `submit_courier_onboarding_documents` y `replace_courier_document` para revalidar rol y consentimiento activo bajo el lock del courier)
  3. `courier_documents where ... for update`
  Este orden es estrictamente uniforme entre `submit_courier_onboarding_documents`, `replace_courier_document`, `admin_verify_document` y `admin_decide_courier`, erradicando el riesgo de espera circular / deadlock (SQLSTATE 40P01).
  *Estado de verificación de concurrencia (H02):* Verificado en CI efímero mediante arneses multi-sesión (`supabase/tests/integration/cc025_concurrency.mjs` y `supabase/tests/integration/cc025_b0_concurrency.mjs`):
  - Escenario 1: `admin_verify_document` retiene lock, `replace_courier_document` concurrente espera y resuelve limpiamente con `INVALID_STATE_TRANSITION` (0 deadlocks 40P01, 1 documento vigente final).
  - Escenario 2: `replace_courier_document` retiene lock, `admin_verify_document` concurrente espera y resuelve con `INVALID_STATE_TRANSITION` (0 deadlocks 40P01, 1 auditoría registrada).
  - Escenario 3: `submit_courier_onboarding_documents` (B0) y `replace_courier_document` / `admin_verify_document` operan bajo el mismo orden de locks sin deadlocks y respetando el índice único parcial `courier_documents_unique_current`.
  - Control de mutación RED -> GREEN: la alteración de la función SQL real en `20261016210000_cc025_courier_document_replacement.sql` para invertir el orden de locks (`courier_documents FOR UPDATE` antes que `couriers FOR UPDATE`) produce un deadlock real PostgreSQL `40P01` bajo el mismo arnés multi-sesión (RED verificado), y la restauración de la migración restablece 0 deadlocks (GREEN verificado).
- **Idempotencia (PR364-H07):**
  Deduplicación persistida vía `idempotency_key` (UUID canónico). Repeticiones con la misma clave y mismo path retornan `idempotent = true` sin alterar filas ni duplicar auditoría, incluso si el documento fue posteriormente verificado por el administrador.
- **Onboarding atómico vía RPC B0 (PR #381 y PR #376):**
  `submitCourierOnboarding` en `src/features/courier-onboarding/actions.ts` delega la validación y escritura de los 4 documentos base en la RPC transaccional `public.submit_courier_onboarding_documents(p_documents)` usando el cliente autenticado (`rpcClient.rpc('submit_courier_onboarding_documents', { p_documents: documentEntries })`) y protege el `update` posterior de `couriers` con `.eq('profile_id', user.id).in('status', ['pending', 'approved'])`. Tras aplicar la Fase C, `submit_courier_onboarding_documents` convive íntegramente con `courier_documents_unique_current` mientras cualquier intento de inserción directa por REST API queda terminantemente bloqueado a nivel de privilegios de tabla (`42501 permission denied for table courier_documents`, Decisión A / PR364-R07).
- **Backfill y retención histórica (PR364-H06):**
  La migración `20261016210000_cc025_courier_document_replacement.sql` retira primero `courier_documents_expansion_guard` y asigna `purge_after = now() + interval '30 days'` a registros históricos obsoletados sin fecha de purga (Decisión B), impidiendo la purga prematura de archivos subidos hace más de 30 días.
  *Estado de verificación de backfill (H06):* Verificado mediante runner real pre-migración (`supabase/tests/integration/cc025_backfill.mjs`): restablece la base al estado previo a la Fase C (`20261016033941`), siembra registros duplicados antiguos con `uploaded_at` de hace 90 días, aplica `20261016210000_cc025_courier_document_replacement.sql` y valida que `is_current = false`, `purge_after > now() + interval '29 days'` e integridad de índices, incluyendo mutación RED -> GREEN sobre el SQL real de la migración.
