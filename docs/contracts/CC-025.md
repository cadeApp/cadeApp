# CC-025 — Rechazo seguro y reemplazo transaccional de documentos del repartidor

- **Issue:** #363 (label `contract-change`) · **Abre:** Lautaro073 · **Fecha:** 2026-10-15
- **Contrato afectado:** Tabla `public.courier_documents` (esquema, vigencia única, catálogo de rechazo seguro, RLS), RPC `public.replace_courier_document(jsonb)` (nueva), RPC `public.admin_verify_document(uuid, text, text, text)` (revisada), `src/domain/rpc-contracts.ts`, `src/types/database.types.ts`, `src/server/rpc/admin.ts`, `src/server/rpc/courier.ts`.
- **Tareas bloqueadas:** T-356 (#343, PR #358)
- **Depende de:** CC-023 (columnas privadas courier), mergeado en `origin/develop`.

## Actual

- **Esquema de `courier_documents`** (`supabase/migrations/20260922031435_schema_v1.sql:70-81`):
  Tiene PK `id`, `courier_id`, `kind`, `storage_path` (unique), `status`, `uploaded_at`, `purge_after`, `purged_at`.
  No posee columna de vigencia ni restricción de unicidad activa por `(courier_id, kind)`. Múltiples filas del mismo `kind` pueden coexistir sin un criterio unívoco de cuál es la vigente.
  No posee columna de motivo de rechazo público.
- **RLS de inserción** (`supabase/migrations/20260922051650_rls_v1.sql:251-258`):
  `courier_documents_insert_self` permite insertar a cualquier usuario autenticado con `courier_id = auth.uid()` y `status = 'submitted'`, sin verificar si ya existía un documento previo ni su estado (`rejected` o `verified`). Un cliente puede invocar directamente `insert` por API y saltarse cualquier validación de Server Action (PR358-H01).
- **RPC `admin_verify_document`** (`supabase/migrations/20260924013700_rpc_admin_v1.sql:174-260`):
  Recibe `p_document_id uuid`, `p_decision text`, `p_reason text default null`.
  Solo verifica `status = 'submitted'` y `purged_at is null`, pero no valida si el documento es el vigente (PR358-H02).
  Persiste `p_reason` únicamente en `audit_log.after->>'reason'`. Al ser `audit_log` de acceso exclusivo para administradores, el repartidor no tiene forma segura de conocer el motivo del rechazo sin exponer texto libre interno o requerir privilegios elevados.
- **Lecturas en aplicación** (`src/app/(courier)/courier/profile/page.tsx:68-70`, `src/features/admin/queries.ts:214-251`):
  El perfil del repartidor usa `docs.find((d) => d.kind === ...)` sobre un conjunto sin orden determinista de vigencia.
  Admin devuelve un listado ordenado por `uploaded_at asc` que mezcla versiones históricas con vigentes.
- **Purga de archivos** (`src/server/cron/sweep.ts:118-173`):
  Purga objetos de `courier-docs` cuando `purge_after <= now()` y `purged_at is null`.

## Propuesto

### 1. Esquema `courier_documents` y versión vigente única

Se añaden dos columnas a `public.courier_documents`:
1. `is_current boolean not null default true`: Indica si el registro es la versión vigente activa para ese repartidor y tipo de documento.
2. `rejection_code text`: Código de catálogo seguro del motivo de rechazo (o `null`).

Restricción de unicidad parcial en PostgreSQL:
```sql
create unique index courier_documents_unique_current
  on public.courier_documents (courier_id, kind)
  where (is_current = true);
```
Esta restricción garantiza a nivel de base de datos que jamás pueden existir dos documentos vigentes para el mismo `(courier_id, kind)`.

Check de catálogo seguro para `rejection_code`:
```sql
constraint courier_documents_rejection_code_check check (
  rejection_code is null or rejection_code in (
    'illegible',
    'expired',
    'data_mismatch',
    'wrong_type',
    'incomplete',
    'other_safe'
  )
)
```

### 2. Catálogo de rechazo seguro (Decisión 1C)

Se desacopla estrictamente la comunicación al repartidor de la nota interna del administrador:
- `rejection_code` (público / seguro para el courier): Enum/string con claves controladas:
  - `illegible`: "Documento borroso, ilegible o cortado."
  - `expired`: "Documento vencido o no vigente."
  - `data_mismatch`: "Los datos no coinciden con la identidad declarada."
  - `wrong_type`: "El archivo no corresponde al tipo de documento solicitado."
  - `incomplete`: "Documento incompleto (falta frente o dorso)."
  - `other_safe`: "Requiere nueva carga para verificación administrativa."
- `reason` (nota interna administrativa): Se mantiene exclusivamente en `public.audit_log (after->>'reason')` para trazabilidad y auditoría interna de administradores. Jamás se expone en `courier_documents`, ni en URLs, ni se proyecta hacia la UI del repartidor.

### 3. RPC pública `replace_courier_document` (Decisión 4C)

Firma explícita en PostgreSQL:
```sql
public.replace_courier_document(p_payload jsonb) returns jsonb
```

Entrada JSON:
```json
{
  "kind": "dni_front|dni_back|selfie|avatar|license|insurance",
  "storagePath": "courier/<auth.uid()>/<kind>_<timestamp>.<ext>",
  "idempotencyKey": "uuid opcional"
}
```

Reglas y comportamiento transaccional:
1. `SECURITY DEFINER` con `set search_path = public, pg_temp`.
2. Valida actor autenticado (`auth.uid()`) con rol `courier` en `profiles`.
3. Valida formato canónico de `storagePath`:
   - Debe iniciar estrictamente con `courier/` || `auth.uid()` || `/`.
   - No puede contener secuencias `..`.
   - Debe contener el prefijo del `kind` especificado.
   - Si la tabla `storage.objects` contiene o no registros, verifica la existencia física incondicional del objeto exacto en el bucket `courier-docs` previo a la promoción en DB; si no existe, falla con `NOT_FOUND` (PR364-H01).
4. Toma lock transaccional `for update` ordenado unificado en todo el sistema: primero sobre `couriers where profile_id = auth.uid()` y luego sobre el documento en `courier_documents` (PR364-H02).
5. Idempotencia persistida vía `idempotencyKey` (PR364-H07):
   - Si se incluye `idempotencyKey`, se valida formato UUID canónico.
   - Si ya existe un registro con esa misma clave para `(courier_id, kind)`:
     - Si el `storagePath` coincide, retorna éxito idempotente (`idempotent = true`) con el estado actual (incluso si fue verificado por admin) sin duplicar filas ni eventos en `audit_log`.
     - Si el `storagePath` difiere, rechaza con `VALIDATION_ERROR`.
6. Si no existe documento previo vigente: rechaza con `NOT_FOUND` (el alta inicial debe ocurrir por el onboarding).
7. Si el documento vigente actual tiene `status = 'submitted'` y el `storage_path` coincide con el del payload (sin clave): devuelve éxito idempotente con `idempotent = true`.
8. Si el documento vigente actual tiene `status <> 'rejected'`: rechaza con `INVALID_STATE_TRANSITION` (no se permite reemplazar documentos aprobados o en revisión).
9. Desactiva el documento vigente anterior:
   - `is_current = false`.
   - `purge_after = coalesce(purge_after, now() + interval '30 days')` (Decisión B / D8: 30 días de retención histórica desde el reemplazo/obsolescencia antes de la purga física).
10. Inserta la nueva versión en `courier_documents`:
    - `status = 'submitted'`.
    - `is_current = true`.
    - `rejection_code = null`.
    - `idempotency_key = v_idempotency_key`.
    - `purge_after = null`, `purged_at = null`.
11. Sincroniza en `couriers`:
    - Si `kind = 'license'` -> `update public.couriers set license_status = 'submitted' where profile_id = auth.uid()`.
    - Si `kind = 'insurance'` -> `update public.couriers set insurance_status = 'submitted' where profile_id = auth.uid()`.
12. Registra auditoría inmutable en `public.audit_log` con acción `'replace_courier_document'`, IDs de documento anterior y nuevo, tipo, clave y estados, sin PII.
13. Retorna JSON:
```json
{
  "documentId": "uuid",
  "kind": "license",
  "status": "submitted",
  "replacedDocumentId": "uuid",
  "isCurrent": true,
  "idempotent": false
}
```

### 4. Ajuste en RPC `admin_verify_document` (PR358-H02 / PR364-H02)

Firma actualizada (retrocompatible mediante sobrecarga o parámetros por defecto):
```sql
public.admin_verify_document(
  p_document_id uuid,
  p_decision text,
  p_reason text default null,
  p_rejection_code text default null
) returns jsonb
```
Reglas añadidas:
1. Lock unificado consistente (PR364-H02): identifica `courier_id`, toma lock `for update` sobre `couriers(profile_id)` primero, y luego toma lock `for update` sobre `courier_documents(id)` revalidando estado bajo el bloqueo.
2. Verifica que el documento objetivo tenga `is_current = true`. Si `is_current = false`, rechaza con `INVALID_STATE_TRANSITION` (impide que un administrador decida sobre una versión obsoleta).
3. Si `p_decision = 'rejected'`:
   - Exige `p_reason` no vacío (nota interna de auditoría).
   - Valida `p_rejection_code` contra el catálogo seguro (si es nulo, asigna por defecto `'other_safe'`).
   - Actualiza `courier_documents set status = 'rejected', rejection_code = v_rejection_code where id = p_document_id`.
   - Registra en `audit_log`: `reason` y `rejection_code`.
4. Si `p_decision = 'verified'`:
   - Actualiza `courier_documents set status = 'verified', rejection_code = null where id = p_document_id`.

## Seguridad y permisos

- **RLS y permisos en `courier_documents` (PR364-H03 / PR364-H04 / PR364-R02):**
  - **Revocación de mutaciones directas:** `revoke update, delete on table public.courier_documents from public, anon, authenticated;`. Ningún usuario por REST API (ni courier ni admin) puede hacer UPDATE ni DELETE directo sobre la tabla. Toda modificación de estado, vigencia y códigos se ejecuta exclusivamente a través de las RPCs `replace_courier_document` y `admin_verify_document` (con verificación AAL2 y auditoría). En PostgreSQL, `ON CONFLICT DO UPDATE` exige el privilegio `UPDATE` sobre la tabla incluso si no hay colisión, por lo que `authenticated` tiene estrictamente prohibido invocar `upsert` directo.
  - Se elimina la política permisiva `courier_documents_write_admin` heredada de `rls_v1`.
  - `courier_documents_select_admin`: Permite al admin autenticado consultar documentos vigentes e históricos para revisión y auditoría.
  - `courier_documents_select_self` (PR364-H04): El repartidor **SOLO puede consultar sus documentos vigentes** (`coalesce(is_current, true) = true`). Los documentos históricos reemplazados quedan completamente invisibles para el courier.
  - `courier_documents_insert_self` (PR358-H01 / PR364-H05 / PR364-R02): Permite únicamente la inserción inicial durante el onboarding cuando no existe un documento vigente del mismo tipo. Exige que `status = 'submitted'`, `is_current = true`, `rejection_code is null` y `idempotency_key is null` (PR364-R02), impidiendo que un actor inyecte claves de idempotencia o altere estados mediante inserción directa.
- **Grants y revokes:**
  - `revoke all on function public.replace_courier_document(jsonb) from public, anon;`
  - `grant execute on function public.replace_courier_document(jsonb) to authenticated;`
  - `admin_verify_document`: mantiene execute exclusivo para `authenticated` con verificación interna AAL2 (`app_private.assert_admin_aal2()`).
- **`security definer`:**
  - Tanto `replace_courier_document` como `admin_verify_document` son `security definer` con `set search_path = public, pg_temp`.

## Concurrencia e idempotencia

- **Locks y orden unificado (PR364-H02):**
  1. `couriers where profile_id = v_courier_id for update`
  2. `courier_documents where id = v_doc_id for update`
  Este orden es estrictamente uniforme entre `replace_courier_document`, `admin_verify_document` y `admin_decide_courier`, erradicando el riesgo de espera circular / deadlock (SQLSTATE 40P01).
  *Estado de verificación de concurrencia:* La infraestructura de pgTAP en CI opera en sesión única serial y no admite conexiones simultáneas interactivas. Sin Docker local ni ejecución sobre Supabase remoto (prohibido por §6), la prevención de deadlocks está asegurada por el orden idéntico de adquisición de bloqueos en ambas funciones SQL. Se documenta como PENDIENTE de prueba multisesión viva hasta contar con un arnés habilitado para concurrencia real.
- **Idempotencia (PR364-H07):**
  Deduplicación persistida vía `idempotency_key` (UUID canónico). Repeticiones con la misma clave y mismo path retornan `idempotent = true` sin alterar filas ni duplicar auditoría, incluso si el documento fue posteriormente verificado por el administrador.
- **Onboarding compatible y carrera 23505 (PR364-H05 / PR364-R01):**
  `submitCourierOnboarding` en `src/features/courier-onboarding/actions.ts`:
  1. Realiza `.select('kind, storage_path, status, is_current')` previo para verificar si ya existen documentos vigentes coincidentes (cero escrituras en reintentos limpios).
  2. Utiliza `.insert()` autorizado (eliminando `.upsert()` para respetar la revocación de `UPDATE` bajo SQLSTATE 42501).
  3. Ante carrera simultánea de dos peticiones concurrentes de onboarding donde una obtiene error `23505` (violación del índice único), relee las versiones vigentes: solo retorna éxito si todos los kinds requeridos existen con idéntico `storage_path` y estados coherentes; si los paths difieren o faltan kinds, rechaza con `VALIDATION_ERROR`.
- **Backfill y retención histórica (PR364-H06):**
  La migración asigna `purge_after = now() + interval '30 days'` a registros históricos huérfanos sin fecha de purga (Decisión B), impidiendo la purga prematura de archivos subidos hace más de 30 días.
  *Impedimento en pgTAP:* Supabase CLI ejecuta todas las migraciones antes de correr la suite de pgTAP, impidiendo inyectar un fixture en la base previa a la migración sin alterar el runner. El comportamiento del algoritmo de rank-and-update se valida en pgTAP reproduciendo la consulta exacta de la migración sobre datos con `uploaded_at` de 90 días atrás.

## Compatibilidad, rollout y rollback

- **Rollout compatible:**
  1. Migración SQL: agrega `is_current`, `rejection_code` e `idempotency_key` a `courier_documents`, crea índice único parcial, revoca UPDATE directo, actualiza RLS, crea `replace_courier_document` y actualiza `admin_verify_document`.
  2. Backfill (PR364-H06): garantiza que para duplicados previos, la versión más reciente en `uploaded_at` conserve `is_current = true`, y las anteriores queden con `is_current = false` y `purge_after = now() + interval '30 days'` (Decisión B confirmada, evitando purgas prematuras de archivos subidos hace >30 días).
  3. Código cliente: `courierOnboardingAction` actualizado con comprobación previa idempotente (PR364-H05).
  4. La nueva UI de T-356 invocará `replace_courier_document` para el reemplazo.
- **Rollback:**
  Migración reversible (`drop function replace_courier_document`, revertir políticas y remover columnas si fuera estrictamente necesario).
