# CC-037 — RPC `admin_list_trips`: lista paginada de viajes con sus problemas

- **Issue:** #506 (label `contract-change`) · **Abre:** Lautaro073 (agente) · **Fecha:** 2026-10-22
- **Contrato afectado:** RPC nueva `public.admin_list_trips` · `src/domain/rpc-contracts.ts` (entrada `admin_list_trips`)
  · `src/types/database.types.ts` · índices nuevos en `delivery_requests`, `request_cancellation_reasons` e `incidents`
- **Tareas bloqueadas:** T-410 (#505)
- **Depende de:** CC-012 (incidentes y `admin_list_incidents`), CC-022 (multi-drop)

## Actual

- El admin no tiene ninguna lectura de solicitudes ni de viajes en la UI. Las rutas de `src/app/(admin)/admin/` son
  postulantes, comercios, repartidores, incidentes, parámetros y auditoría.
- Las piezas existen y el admin ya las puede leer por RLS:
  - `delivery_requests`: `delivery_requests_select_admin` (`app_private.is_admin()`);
  - `delivery_request_drops`: `drops_select_admin` (`supabase/migrations/20261009200000_t340_multi_drop.sql:160`);
  - `request_cancellation_reasons`: `request_cancellation_reasons_admin`, con `grant select` a `authenticated`
    (`supabase/migrations/20260924010124_rpc_requests_v1.sql:14-19`);
  - `incidents`: `incidents_select_admin`; `offers`: `offers_select_admin`.
- Qué queda registrado de cada problema:
  - entrega no realizada: `delivery_request_drops.status = 'failed'` y `failed_reason` (`mark_drop_failed`, sin fila
    en `audit_log`);
  - repartidor que suelta el viaje: `request_cancellation_reasons.action = 'courier_cancel_match'` con su motivo;
  - no-show reportado por el comercio: `action = 'report_no_show'` (`reason = 'no_show'`);
  - cancelación: `delivery_requests.status = 'cancelled'`, más una fila `action = 'cancel_request'` si hubo motivo
    (`supabase/migrations/20261017090000_t369_publication_credits.sql:1222-1232`);
  - incidentes: `incidents` por `request_id`.
- El patrón de lista admin paginada en la base es `admin_list_incidents`
  (`supabase/migrations/20260927120000_cc012_incidents_contract.sql:282-388`): `security definer`, `stable`,
  `assert_admin_aal2()`, keyset `created_at desc, id desc` con cursor `{ createdAt, id }`, límite 1–50.
- Índices: `delivery_requests_merchant_idx (merchant_id, created_at desc)`; ninguno por `created_at, id` para listar
  todas las solicitudes, ni por `request_id` en `request_cancellation_reasons` o `incidents`.
  `delivery_request_drops` ya tiene `unique (request_id, position)`.

## Propuesto

```sql
public.admin_list_trips(
  p_filter text,                        -- 'problems' | 'all'
  p_cursor_created_at timestamptz default null,
  p_cursor_id uuid default null,
  p_limit integer default null          -- 1..50, por defecto 20
) returns jsonb
```

- Lista las solicitudes con `status <> 'draft'`, ordenadas por `created_at desc, id desc`, con keyset igual a
  `admin_list_incidents`.
- `p_filter = 'problems'` deja solo las que tienen al menos un problema: alguna entrega `failed`, alguna fila de
  `request_cancellation_reasons` con `action in ('courier_cancel_match', 'report_no_show')`, `status = 'cancelled'` o
  algún incidente. El filtro se evalúa en la base, antes de ordenar y limitar.
- Salida:

```json
{
  "items": [{
    "id": "uuid",
    "code": "REQ-1A2B3C4D",
    "status": "delivered",
    "createdAt": "2026-10-22T04:41:00.000000Z",
    "publishedAt": "…|null", "deliveredAt": "…|null", "cancelledAt": "…|null",
    "merchantId": "uuid", "merchantName": "Comercio",
    "courierId": "uuid|null", "courierName": "Repartidor|null",
    "dropsCount": 2, "deliveredDrops": 1, "failedDrops": 1,
    "courierReleases": 0, "noShowReports": 0, "cancelled": false,
    "incidents": 0, "openIncidents": 0
  }],
  "nextCursor": { "createdAt": "…", "id": "uuid" } | null
}
```

- `code` usa la misma fórmula que `get_trip_details`: `'REQ-' || upper(substr(id::text, 1, 8))`.
- `merchantName` es `merchants.business_name`, o `profiles.display_name` si está vacío.
- `courierName` es el `display_name` del repartidor de la oferta `accepted` vigente, o `null`.
- `dropsCount`, `deliveredDrops` y `failedDrops` salen de `delivery_request_drops`. Una solicitud legacy sin drops
  devuelve `dropsCount = 1` y cuenta como entregada si `status = 'delivered'`.
- Errores: `UNAUTHENTICATED`, `UNAUTHORIZED_ACTOR` y `AAL2_REQUIRED` (los de `assert_admin_aal2`, en ese orden), y
  `VALIDATION_ERROR` si `p_filter` no es `problems` ni `all`, el cursor está incompleto o `p_limit` no está entre 1 y 50.
- Índices de soporte, creados con `if not exists`:
  - `delivery_requests_admin_cursor_idx on delivery_requests (created_at desc, id desc) where status <> 'draft'`;
  - `request_cancellation_reasons_request_idx on request_cancellation_reasons (request_id, action)`;
  - `incidents_request_idx on incidents (request_id)`.

El detalle de un viaje (`/admin/trips/[id]`) **no** necesita RPC nueva: lo lee T-410 por RLS del admin, con lecturas en
paralelo de `delivery_requests`, `delivery_request_drops` (sin contactos), `request_cancellation_reasons`, `offers`,
`incidents` y los perfiles, igual que el detalle de incidentes (`src/features/incidents/queries.ts`).

## Seguridad y permisos

- **RLS:** no cambia ninguna policy.
- **Grants y revokes:** `revoke all on function public.admin_list_trips(text, timestamptz, uuid, integer) from public,
  anon, authenticated; grant execute … to authenticated`. La autorización real la hace `assert_admin_aal2()` dentro
  de la función.
- **`security definer`**, `stable`, `set search_path = public, pg_temp`. Corre como dueño para hacer los conteos sin
  depender de cada policy, pero solo después de `assert_admin_aal2()`; un no admin o un admin sin `aal2` recibe el
  error antes de leer nada.
- **Helpers internos:** no agrega helpers `app_private.*`.
- **Acceso directo frente a RPC:** la RPC es de solo lectura; no escribe ni congela campos.
- **Datos que nunca devuelve:** nada de `delivery_request_contacts` ni `delivery_request_drop_contacts` (dirección,
  nombre, teléfono, pin, indicaciones y monto exacto de cambio). No devuelve los motivos en la lista; el detalle los
  lee por RLS del admin.

## Concurrencia e idempotencia

No aplica: es una lectura `stable` sin locks ni efectos. Un reintento devuelve la página vigente.

## Compatibilidad, rollout y rollback

- **Versión anterior de la UI contra el esquema nuevo:** la RPC y los índices son aditivos; la UI vieja no los usa.
- **Esquema anterior contra la UI nueva:** la pantalla `/admin/trips` llama a la RPC; si la migración no está aplicada
  devuelve error y la página muestra su estado de error. Por eso la migración y la UI van en la misma PR de T-410 y la
  migración se aplica (`migrate-*`) antes del deploy de cada entorno, como en cada promoción.
- **Backfill:** no hace falta; la RPC lee el estado actual.
- **Rollout ordenado:** una sola PR (T-410) con migración, contrato, UI y pruebas. `migrate` corre antes de `deploy` en
  staging y producción.
- **Condición para retirar la compatibilidad:** no aplica.
- **Rollback:** `drop function public.admin_list_trips(...)` y los tres índices; ningún dato depende de ellos.

## Decisiones de producto

- La sección se llama «Viajes», abre con el filtro «Con problemas» y tiene «Todos»; muestra los problemas como
  etiquetas por tipo y lleva al detalle del viaje — Lautaro073 (vía agente, con autorización explícita para decidir),
  2026-10-22.
- Se considera problema: entrega no realizada, repartidor que suelta el viaje, no-show, cancelación e incidente. Una
  solicitud vencida sin oferta no es un problema del viaje — Lautaro073 (vía agente), 2026-10-22.

## Motivo

Lautaro073 pidió (2026-10-22) que el admin vea los problemas de los viajes: hoy ninguno se ve en el panel (las entregas
fallidas ni siquiera en Auditoría). Filtrar «Con problemas» exige combinar cuatro tablas; hacerlo en el cliente obliga
a traer todas las solicitudes y no pagina. La RPC filtra y pagina en la base con el patrón ya probado de
`admin_list_incidents`.

  - E2E `e2e/specs/admin-trips.spec.ts`.
- **Pruebas exigidas:**
  - pgTAP de autorización: sin sesión recibe `UNAUTHENTICATED`; comercio y repartidor reciben `UNAUTHORIZED_ACTOR`;
    un admin `aal1` recibe `AAL2_REQUIRED`; un admin `aal2` recibe la página;
  - pgTAP de privilegios: `execute` solo para `authenticated`, nada para `anon` ni `public`;
  - pgTAP del filtro: una solicitud de cada tipo de problema (entrega `failed`, `courier_cancel_match`,
    `report_no_show`, `cancelled`, incidente) aparece en `problems`; una entregada sin problemas y una vencida sin
    ofertas no; los borradores no aparecen en ningún filtro;
  - pgTAP de conteos: `dropsCount`, `deliveredDrops`, `failedDrops`, `courierReleases`, `noShowReports`, `incidents`
    y `openIncidents` correctos, incluida una legacy sin drops;
  - pgTAP de paginación: keyset estable con empates de `created_at`, `nextCursor` `null` en la última página, y
    `VALIDATION_ERROR` para filtro inválido, cursor incompleto y límite fuera de 1–50;
  - pgTAP de privacidad: la salida no tiene claves de contacto (`recipient*`, `dropoff_address`, `pin`, `phone`,
    `cash_change_amount`);
  - E2E del admin con MFA: la sección «Viajes» lista un viaje con una entrega no realizada en «Con problemas» y su
    detalle muestra el motivo.
