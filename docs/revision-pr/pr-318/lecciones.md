## Ronda 4 — Auditar la clase entera de lectores, no solo la migración

- **H03 — contrato REST vs wrapper TypeScript:** el schema de server action puede incluir `requestId` para revalidar rutas, pero una RPC PostgreSQL por entrega no debe recibirlo si su firma solo acepta `p_drop_id`. Los fakes del dominio no garantizan coincidencia con los parámetros PostgREST. Agregar spies de argumentos EXACTOS en `src/server/rpc/requests.test.ts`.
- **H04 — compatibilidad de respuesta ≠ dependencia de tabla legacy:** CC-022 permite devolver campos escalares legacy de `get_trip_details` para el cliente antiguo, pero el rollout a Paso 3 exige que NO se lean columnas `delivery_requests.notes/cash_change_amount` como fuente. Derivarlas de la primera entrega del `drops[]` autorizado.
- **H05/H06 — clase incompleta:** agregar `dropsCount` no implementa un feed de N drops. Hay que migrar juntos consulta pública, SSE, DTO, oferta, detalle, vista, mapa, historial/admin y WhatsApp por destinatario. El peligro de mantener una sola entrega es que el test de una entrega PASS, aunque otras N no existan en la respuesta.
- **H07 — fixtures pgTAP comparten estado en un archivo:** cada bloque test puede usar UUIDs estáticos, pero no puede reutilizar PK de otro fixture ejecutado dentro de la misma transacción. La prueba quedó RED por `duplicate key`, no por una regresión productiva que se estaba buscando.
- **H08 — `pnpm test` local no sustituye CI con coverage:** la ampliación del fake creó ramas sin ejercitar; el resultado `pnpm test` GREEN del autor no cubre los umbrales `unit` reales del CI. Añadir cobertura comportamental sin excluir archivos ni bajar thresholds.
- **H09 — RED auténtico sobre el comportamiento que falta:** el RED adversarial del Gate 0 R3 fue sobre el cliente viejo y ya se cerró; no prueba que las nuevas suites de N drops fallen cuando se borra un drop o se desprotege un contacto. Exigir casos N y de privacidad con fixtures reales y mutantes falsables (de forma efímera, nunca SQL remoto Develop). Evitar `as any` porque suprime precisamente el control que se está auditando.
- **Decisión A expresamente elegida por Lautaro073:** ampliar `get_trip_details` con array `drops[]` ordenado, manteniendo campos escalares de respuesta derivados del primer elemento. Centralizar la autorización post-match; no expandir tareas a Paso 3/4, que luego realizará Kira tras gates independientes.

**Limitación de evidencia R4:** se inspeccionaron 12 marcadores por lectura fuente, y se leyeron fallos CI reproducibles de pgTAP y coverage en el SHA exacto. No se ejecutaron mutations SQL/E2E reales desde el revisor ni se afirma que los demás hallazgos se hayan reproducido en runtime.
