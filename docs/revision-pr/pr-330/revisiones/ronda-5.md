## PR330-H09 — NUEVO ALTO BLOQUEANTE
`src/features/requests/actions.ts:52` mantiene `const requestId = data.requestId ?? crypto.randomUUID()`. El schema del formulario `src/features/requests/schemas.ts:92` declara `requestId` **opcional** por la arquitectura React Hook Form (el navegador adjunta UUID en `onSubmit`). Sin embargo, **CC-024:78–85 establece que la Server Action no genera ID por invocación**. En la implementación actual, una llamada al endpoint sin `requestId` se acepta y crea un UUID fresco por llamada; si el consumidor pierde la respuesta y reintenta, no puede reutilizar esa clave ni garantizar idempotencia. El formulario actual sí envía UUID, por lo que no se afirma duplicación visible en producción: es una vulneración comprobable del contrato para esa otra clase de entradas.
**Corrección mínima:** en Server Action, tras `safeParse`, exigir `data.requestId`; si es `undefined`, devolver `VALIDATION_ERROR` sin llamar `rpc` ni `crypto.randomUUID()`. Dejar `createDeliveryRequestSchema` como está para que React Hook Form admita datos de formulario sin campo oculto. Cambiar `validFormInput` de `actions.test.ts` para incluir UUID fijo en pruebas positivas; agregar test negativo específico «requestId ausente» con actor válido, `VALIDATION_ERROR`, cero RPC y cero INSERT. RED dirigido: reintroducir `?? crypto.randomUUID()` temporalmente en la acción con el test inalterado y mock RPC válido: debe fallar la expectativa `rpc not called` o `VALIDATION_ERROR`, no por falla de setup; restaurar y GREEN. No inventar otra estrategia de idempotencia.
