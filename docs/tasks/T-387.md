## Objetivo

El bucket `courier-docs` (10 MiB = 10.485.760 bytes, `application/pdf` incluido), las RPC de CC-025 y CC-033 (sufijo `.pdf`) y
`getDocumentExtension` ya aceptan PDF, pero la UI ofrece solo fotos, comprime todo como imagen y el visor del admin
usa `<img>`, que no muestra un PDF. Con esta tarea el repartidor puede subir la **licencia o el seguro** como PDF
(registro inicial, alta desde el perfil y reemplazo de un rechazado), y el admin lo ve con el visor auditado y lo valida o rechaza con
el flujo existente.

## Reconciliación de contratos

No aplica: no hay CC nuevo. CC-025 y CC-033 están mergeados y ya admiten `.pdf` en el path; el bucket ya admite
`application/pdf` con 10 MiB. La RPC del registro inicial (`submit_courier_onboarding_documents`) valida solo el prefijo del path, así que también acepta `.pdf`. Esta tarea no cambia esquema, RPC, RLS, tipos generados ni `src/domain/**`.

- [ ] **Registro inicial, alta desde el perfil y reemplazo de licencia o seguro aceptan PDF:** el selector ofrece

- [ ] **Una sola preparación del archivo** (validación y compresión solo para fotos) compartida por los tres caminos,
      sin duplicar la lógica en cada componente.
- [ ] **El PDF no pasa por la compresión de imágenes:** se sube tal cual, con `contentType: application/pdf` y path

- [ ] **Validación del lado del cliente antes de subir:**

  - un archivo que dice ser PDF pero no empieza con `%PDF-` se rechaza;

## Regla de pruebas

La evidencia RED tiene que fallar por el comportamiento real que falta. Está prohibido fabricar RED o GREEN:
- comentando código;
- adulterando expectations;
- agregando ramas `if (test)`;
- usando mocks que eviten el camino de producción;
- debilitando una aserción solo para que pase CI.

Una **mutación** que rompe a propósito la regla para demostrar que el test la protege es válida si es local,
temporal, restaurada y sin commit, y se registra en la bitácora con la mutación exacta y las líneas resumen de RED y
GREEN. Mutaciones que quiten un control de seguridad con evidencia E2E: solo con el workflow `e2e-mutation` (T-347).

## Notas para quien retome

Decisiones tomadas en la ficha (2026-10-20, Lautaro073):
- **Alcance (revisión de la PR #470, decisión 1 C):** los tres caminos de carga de licencia y seguro, con una preparación compartida. Solo licencia y seguro, porque son los documentos que el repartidor suele tener en PDF (póliza,
  licencia digital). DNI y selfie siguen siendo fotos, porque el admin los compara con la persona.
- **Tipo de contenido:** lo decide el servidor por la extensión del path que ya validaron las RPC (`png|jpe?g|webp|pdf`),
  así el cliente no puede forzar que el visor trate una imagen como PDF ni al revés.
- **Visor de PDF:**
  - se usa `<iframe>` sin `sandbox`, porque el visor de PDF de Chromium no funciona en un `iframe` con `sandbox`; el
    PDF se sirve desde el dominio de Supabase Storage, de otro origen, así que no accede a la app;
  - la URL vence a los 60 s, como hoy;
  - el enlace a otra pestaña cubre los navegadores que no embeben PDF, como los móviles.
- **DNI, selfie y avatar (revisión de la PR #470, decisión 2 C):** la UI sigue ofreciendo solo fotos y no se
  cambian contratos; el visor muestra embebido cualquier PDF que el backend ya admita.
- **Firma del PDF:** se chequean los primeros 5 bytes (`%PDF-`) además del MIME que informa el navegador, que depende
  de la extensión del archivo.
