## Origen

En la PR #320 (T-340), el run `e2e-preview` [38340200745](https://github.com/cadeApp/cadeApp/actions/runs/38340200745)
dejó chromium sin fallos, y por primera vez desde el merge de T-340 corrió el proyecto `global-settings`:

- `subscription.global-settings.spec.ts:159` («DoD 2: con el piloto encendido la solicitud sí se publica») falla ×3
  en `page.waitForURL(..., { timeout: 10000 })` después del submit.
- `t340-legacy-checkpoint.spec.ts:71` es flaky con el mismo síntoma (pasa al tercer intento).

Logs de Supabase Develop de esas corridas (solo lectura):

1. El server action termina en ~2,5 s: insert, contacto, `publish_request` 200 (~290 ms) y aviso a repartidores.
2. El destino devuelto es `/merchant/requests`, cuya página solo redirige a `/merchant/dashboard`.
3. Antes de que el dashboard lea `delivery_requests`, se ve tres veces en serie la cadena
   `auth/v1/user` → `profiles` → `merchants`, con llamadas sueltas de hasta 2,2–2,3 s.
4. Total entre el click y la carga: 8,5–10,5 s.

No es un problema de datos ni de los fixtures de T-340.

## Objetivo

Que publicar una solicitud desde la UI lleve al comercio a su destino final **sin navegaciones intermedias**, con la
latencia medida antes y después, sin debilitar ninguna verificación de autenticación, rol, consentimiento u
onboarding y **sin cambiar timeouts de los E2E**.

## Plan

1. **Medir antes (RED de referencia):** registrar en la bitácora el run 38340200745 y, sobre el código actual, la
   secuencia de navegaciones y de llamadas a Supabase entre el click en «Publicar solicitud» y la primera lectura de
   `delivery_requests` del dashboard (Playwright: `page.on('request')`/`response` en una corrida E2E; Supabase:
   `edge_logs` de esa ventana, solo lectura).
2. **Eliminar el salto:** si la medición confirma que `/merchant/requests` agrega una navegación y una pasada extra
   por el middleware, `createDeliveryRequestAction` pasa a devolver el destino final `/merchant/dashboard`. El alias
   `/merchant/requests` **se conserva** (lo usan la navegación, `revalidatePath` y los guards).
3. **Medir después (GREEN):** misma medición sobre el código de esta tarea: una navegación menos, una cadena
   auth → perfil → comercio menos y tiempo menor, con los números en la bitácora.
4. **Lecturas duplicadas (análisis):** documentar en la bitácora qué lecturas de autenticación y onboarding se repiten
   por request entre middleware, layout y página, con la propuesta de deduplicación medida. Cualquier cambio en
   `src/middleware.ts`, `src/features/auth/**` o páginas `(merchant)` requiere una autorización explícita de
   Lautaro073 registrada en esta ficha antes de implementarlo. `React.cache` no comparte caché con el middleware ni
   entre requests HTTP; no se usa como primera solución sin medirlo.
