## Origen

El mismo flake del page object compartido apareció tres veces en `e2e-preview`, siempre en el primer intento y
siempre verde en `retry #1`:

| Issue | Run | Caso |
|---|---|---|
| #245 | `37160321196` | `main-flow.spec.ts` — T-303 Flujo 5 |
| #249 | `37181721851` | `subscription.global-settings.spec.ts` — T-306 DoD 2 |
| #250 | `37184438349` | `authorization.spec.ts` — T-305 «Un pending recibe el error del servidor…» |

En los tres casos el error es `TimeoutError: page.waitForURL: Timeout 30000ms exceeded` en
`e2e/pages/login.page.ts:37`: después del click, la URL nunca salió de `/login`. Lautaro073 lo pidió como tarea
aparte el 2026-10-04: depender del retry esconde una carrera real.

## Causa probable (a confirmar en la fase RED)

`LoginForm` es un componente cliente con inputs controlados (`useState`) y `onSubmit` con `preventDefault()`.
`BasePage.goto` espera `load`, pero Next 15 + React 18 hidrata en modo concurrente y puede terminar **después** de
`load`. `LoginPage.login()` hace `fill` → `fill` → `click` sin esperar la hidratación, y cada test arranca con un
contexto nuevo sin caché de chunks. Si las acciones caen antes de que React hidrate el formulario:

- **click antes de hidratar:** el submit es nativo (GET `/login`, los inputs no tienen `name`), la página recarga
  vacía y la URL no cambia nunca;
- **fill antes de hidratar y click después:** el DOM muestra los valores, pero el estado de React queda en `''`;
  `loginAction` devuelve `VALIDATION_ERROR`, el formulario muestra el error genérico y se queda en `/login`.

Los dos caminos terminan en el mismo timeout de 30 s. Al reintentar, los chunks ya están calientes en el CDN y la
carrera desaparece.

## Objetivo

Que `LoginPage.login()` no dependa de la suerte:

1. esperar a que React hidrate el formulario (el `<form>` tiene su `onSubmit` de React) **antes** de completar los
   campos;
2. confirmar que los campos quedaron con los valores ingresados;
3. después del click, esperar a que pase una de dos cosas: la URL sale de `/login` (éxito) o aparece un error del
   formulario (`authCopy.login.errorInvalidCredentials` o `errorGeneric`). Con error, fallar **de inmediato** con el
   texto de la alerta, sin esperar 30 s.

## Decisiones

- **No se sube ningún timeout** ni se debilita una aserción: la espera de navegación sigue en 30 s. La espera de
  hidratación es una condición nueva, no un tiempo fijo.
- **Señal de hidratación:** React 18 adjunta `__reactProps$<id>` a cada nodo que hidrata. Se considera hidratado
  cuando las props del `<form>` tienen `onSubmit` de tipo función. Es un detalle interno de React, se encapsula en
  `e2e/helpers/hydration.ts` y no se toca código productivo para agregar marcadores.
- **Spec de regresión sin backend:** `e2e/specs/login.spec.ts` retiene los chunks `/_next/static/chunks/**` para
  que el formulario quede sin hidratar, y aborta el POST del Server Action, así que no llama a Supabase Auth ni usa
  credenciales ni fixtures de seed. Entra solo al proyecto `chromium` (T-331).
- **Ejecución local permitida:** `pnpm dev` con el `.env` local existente (sin leerlo ni imprimirlo) y
  `pnpm exec playwright test e2e/specs/login.spec.ts --project=chromium` con
  `PLAYWRIGHT_TEST_BASE_URL=http://localhost:3000`, solo para iterar sobre este spec. No se corre el resto de la
  suite local (usa la service role). La evidencia de cierre es `e2e-preview` en CI.
