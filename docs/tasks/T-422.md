# T-422 — CI: e2e-preview contra un build en el runner, sin Vercel Preview por PR

- **Zona / dueño:** P1 · **Issue:** #608 · **Fase:** Fase 4 — costo de Vercel, pedido de Lautaro073 (2026-11-04)
- **Dependencias (mergeadas en develop):** T-327, T-329, T-331, T-347
- **Contratos a leer:** `.github/workflows/e2e-preview.yml`, `.github/workflows/e2e-preview-target.mjs`,
  `.github/workflows/e2e-mutation.yml` (build en el runner) y `docs/runbooks/e2e-preview.md`.

## Objetivo

El ciclo 13/10–13/11 de Vercel va en US$ 34,65 de minutos de CPU de build: `cadeapp-develop` hizo 1107 deploys en 3
semanas, uno por cada push a cualquier rama, y el E2E de cada PR (`e2e-preview`) los necesita porque prueba contra
el Preview. El tráfico de los E2E cuesta ~US$ 4.

Con esta tarea `e2e-preview` arranca cuando termina el CI de la PR (`workflow_run`), hace el build del SHA exacto en
el runner (como `e2e-mutation`) y corre los mismos proyectos de Playwright contra `http://localhost:3100`. El repo es
público, así que los minutos de Actions no se cobran. Después del primer GREEN, Vercel solo construye `develop`.

## Reconciliación de contratos

Sin cambios de esquema, RPC ni `src/**`. Cambia el disparador del gate y dónde corre la app; el contexto del commit
status (`e2e-preview`), los proyectos de Playwright, la serialización y el bloqueo por migraciones quedan igual.

## Diseño

- **Disparador:** `workflow_run` de `CI` con `types: [completed]`. Corre con el workflow de la rama por defecto, así
  que la PR no puede reescribir el gate (la misma garantía que daba el `repository_dispatch` de Vercel).
- **Resolvedor** (`e2e-preview-target.mjs`, sin secretos ni Environment): solo `event == pull_request` y
  `conclusion == success`; el `head_sha` tiene que ser el head de exactamente una PR interna abierta contra
  `develop`; las PR de forks no reciben nada; las que tocan `supabase/migrations/**` quedan en
  `BLOCKED / REQUIRES DEVELOP MIGRATION`. Se elimina el control del proyecto de Vercel, la URL del payload y el
  descarte de avisos duplicados (cada fin de CI es una sola corrida).
- **E2E:** checkout del SHA resuelto, verificación de Supabase Develop y un único step con secretos que hace
  `pnpm build`, `pnpm start -H 127.0.0.1 -p 3100`, health check 200 y los proyectos `chromium` y `global-settings`.
  La salida del servidor queda en `RUNNER_TEMP` y no se sube.
- **Google Maps:** el build usa una clave falsa; `map-privacy` intercepta todas las llamadas a Google.

## Proceso (decisión de Lautaro073)

Lautaro073 pidió reducir el costo de Vercel (2026-11-04). En el panel ya se aplicaron, fuera de esta PR, la máquina
de build Standard y un Ignored Build Step que saltea `docs/`, `review/`, `review-only/`, `claude/` y `release/`.
Esta tarea sigue el circuito normal: PR con revisión independiente.

El gate nuevo solo se puede ejecutar desde `develop` (`workflow_run` lee la rama por defecto), así que la prueba
real es posterior al merge. Hasta ver un `e2e-preview` GREEN con el gate nuevo, los Preview de `feat/*` siguen
activos. Recién después el Ignored Build Step pasa a construir solo `develop`.

## Regla de pruebas
La evidencia RED tiene que fallar por el comportamiento real que falta. Está prohibido fabricar RED o GREEN:
- comentando código;
- adulterando expectations;
- agregando ramas `if (test)`;
- usando mocks que eviten el camino de producción;
- debilitando una aserción solo para que pase CI.

Una **mutación** que rompe a propósito la regla para demostrar que el test la protege es válida si es local,
temporal, restaurada y sin commit.
