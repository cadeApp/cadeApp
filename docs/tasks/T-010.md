# T-010 — CI: saltear jobs pesados en pushes de solo docs cuando el repo es privado

- **Zona / dueño:** P1 · **Issue:** #73 · **Fase:** Fase 0 (Fundaciones y contratos)
- **Dependencias (mergeadas en develop):** T-003
- **Contratos a leer:** `.github/workflows/ci.yml`, `.github/workflows/verify-workflows.test.mjs`, `AGENTS.md` §6

## Objetivo
Con el repositorio **privado**, un push a una PR abierta que solo toca documentación no corre `typecheck`, `lint`,
`build`, `bundle-budget`, `db-tests` ni `audit` cuando se puede demostrar que su resultado no puede cambiar respecto
de una corrida que pasó. `unit` corre siempre, porque valida fichas, bitácoras, el plan y los ADR. Con el
repositorio público no cambia nada: el job que decide ni arranca y todo corre como siempre.

## Fuera de alcance
- `approval-policy.yml` y `migrate.yml`: no se tocan.
- Fusionar jobs para ahorrar minutos: descartado para no perder checks con nombre propio.
- Pushes a `develop`, `staging` y `main`, y PRs recién abiertas o reabiertas: corren siempre todo.

## Dependencias nuevas permitidas
- ninguna, tampoco actions de terceros: solo las ya fijadas por SHA en `ci.yml`

## DoD
- [ ] Pruebas: la decisión saltea solo si se cumplen las siete guardas (repo privado; `pull_request` `synchronize`; fast-forward; diff no vacío y todo `docs/**/*.md` o `docs/**/*.jsonl`; sin detección de renames; corrida anterior de CI de la misma rama en `success`; rama que contiene la base del merge), y cada guarda tiene una prueba que la rompe sola y exige correr todo — incluido el caso real `a71ec25` de T-006, un push de docs sobre una corrida fallida
- [ ] `ci.yml`: `unit` no depende de la decisión; `typecheck`, `lint`, `build`, `db-tests` y `audit` sí, con `!cancelled()` para que un decisor salteado o caído signifique correr todo, y `bundle-budget` sigue a `build`; el job que decide no arranca con el repositorio público
- [ ] `pnpm typecheck && pnpm lint && pnpm test`
- [ ] Sin cambios fuera de "Archivos permitidos"
- [ ] Bitácora `docs/tasks/log/T-010.md` al día y PR con evidencia

## Notas para quien retome
- Tarea de infraestructura fuera de la tabla §8 del plan, como T-000. La decidió Lautaro073 el 2026-09-24 a partir
  de la medición de minutos del issue #73: sobre 85 pushes reales a PRs, el 47 % fue solo docs; con las guardas
  el ahorro medido es de 1020 a 915 minutos, un 10 %, y solo mientras el repositorio es privado.
- **Por qué no alcanza con mirar el diff del push.** Un push de docs sobre una corrida **fallida** se saltearía los
  jobs que fallaban y la PR quedaría en verde con el código roto. No es hipotético: `a71ec25` en T-006 fue una
  bitácora pusheada sobre un CI rojo. La guarda de la corrida anterior es la que lo impide.
- **Por qué la guarda de la base se verifica con git y no con la API.** La API de Actions no guarda contra qué
  develop corrió cada CI: en las corridas de la PR #64, `pull_requests` vino vacío. El checkout de
  `refs/pull/N/merge` sí lo dice: su primer padre es la base que prueba este CI, y si la rama ya la contiene, el
  árbol probado es exactamente el de la rama.
- **Por qué `if:` a nivel de job y no `paths-ignore`.** Un job salteado por `if:` reporta «Skipped», que cuenta como
  éxito para los checks requeridos. `paths-ignore` a nivel de workflow no crea el check y lo deja en «Expected»,
  que bloquea el merge si algún día se activa la protección de ramas. Además `paths` en `pull_request` mira el diff
  de toda la PR, así que nunca ahorraría en una PR con código.
- `AGENTS.md` §6 prohíbe tocar `.github/**` salvo que la ficha lo diga: esta lo dice, y solo para los tres
  archivos listados.
