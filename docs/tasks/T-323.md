# T-323 — Hardening del mapa de comercio en staging y degradación de Google Maps

- **Zona / dueño:** P2 · **Issue:** #171 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-116, T-315, T-322
- **Contratos a leer:** `src/ui/map.tsx`, `src/lib/env.public.ts`, `src/features/merchants/components/onboarding-form.tsx`, T-116 y `docs/design/visual-task-directive.md`

## Origen

Prueba manual en staging posterior a T-322: el registro y confirmación de email funcionan, el comercio llega al onboarding y puede terminar creado, pero Google Maps muestra error de proveedor. En consola se observó un error compatible con configuración/billing de Google Maps. Cambiar un secret de GitHub no actualiza esta key pública porque el deploy de staging obtiene `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` desde el entorno **Production del proyecto Vercel `cadeapp-staging`** durante `vercel pull`.

La corrección de configuración en Vercel es una acción manual; esta tarea evita que una caída/configuración inválida del proveedor se confunda con un fallo del alta y asegura que la degradación ya prevista sea real y comprobable.

## Objetivo

Con Google disponible, ofrecer una selección de ubicación fluida en móvil y escritorio: mapa libre para pan/zoom, pin visible y movible sin realimentar el centro en cada frame, y selección por arrastre del pin o toque/click en el mapa. Si Google no carga por key ausente/inválida, billing, restricciones de referrer/API u offline, el formulario debe seguir operativo con dirección manual y presentar un estado inline claro sin exponer detalles sensibles.

## DoD
- [ ] Con Google Maps disponible el selector funciona con pan/zoom fluido, pin visible y movible y selección por arrastre del pin o toque/click; ante key ausente, billing/referrer/API failure u offline, la UI degrada a dirección manual sin bloquear el alta ni reportar falsamente que falló la creación del comercio.
- [ ] Tests RED antes del arreglo cubren key vacía, `APIProvider.onError`, `APILoadingStatus.FAILED`, offline y submit manual con mapa degradado.
- [ ] Mutación/restauración demuestra que el control falla si se elimina la transición a fallback ante error de Google o si el estado de error impide enviar una dirección válida sin coordenadas.
- [ ] El error del mapa queda separado del error de `merchantOnboardingAction`: una caída de Google no muestra falsamente el mensaje de “no se pudo crear el comercio”.
- [ ] El fallback y sus mensajes son accesibles y no exponen API keys, URLs sensibles ni texto técnico de Google.
- [ ] El mapa no usa un loop controlado `onCameraChanged → onChange → value → center` durante el pan: mover el mapa no debe re-centrarlo ni producir tirones; las coordenadas se confirman en eventos discretos (drag end del pin, toque/click, GPS o teclado).
- [ ] La UI normal usa un pin real/draggable como affordance principal. Tocar/clickear otro punto mueve el pin y actualiza la ubicación seleccionada.
- [ ] Se elimina de la vista móvil normal el D-pad flotante de 10 m y el badge técnico de lat/lng dentro del mapa. El ajuste por teclado/flechas se conserva para accesibilidad sin ocupar el canvas con un control permanente.
- [ ] Tests RED y mutaciones cubren: pan del mapa no persiste coordenadas en cada `cameraChanged`; drag end del pin sí persiste; click/tap sí persiste; reintroducir el D-pad/badge o el loop de cámara hace fallar los controles.
- [ ] **Configuración en Vercel:** `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` se configura en Vercel → proyecto `cadeapp-staging` → environment Production. GitHub Secrets NO es la fuente de verdad de esta variable pública.
- [ ] **Gate de validación visual post-merge en staging (Decisión P1 2-A):** La validación visual manual del mapa en staging estable NO bloquea el merge de PR #175 a develop. Una vez mergeada a develop, la validación visual se ejecuta durante la promoción develop → staging. Si la validación visual pasa en staging, la promoción hacia main queda habilitada; si falla, se bloquea staging → main hasta corregir el defecto. No se inventa ni anticipa evidencia visual antes del deploy real en staging; la ausencia de esa evidencia post-merge no deja T-323 / PR #175 artificialmente abierta si todo el DoD automatizable, contractual y de código está verde.
