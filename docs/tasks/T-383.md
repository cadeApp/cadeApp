# T-383 — Suscripción push en un navegador que quedó suscripto con otra cuenta

- **Zona / dueño:** P1 · **Issue:** #447 · **Fase:** Fase 3 (Calidad, operación y salida)

  obligatoria** (implementa CC-035), todavía no mergeada, con su RPC aplicada en Supabase Develop por `migrate-develop`

  `src/server/rpc/push-subscriptions.ts` (lo entrega CC-035), `e2e/specs/push-user-activation.spec.ts`

## Objetivo

Hoy, si el navegador ya tiene el endpoint push guardado a nombre de otra cuenta (por ejemplo, porque la sesión venció
sin logout), `POST /api/push/subscriptions` responde 500 por la RLS y la cuenta nueva no puede activar avisos. Con esta
tarea la ruta registra la suscripción con `register_push_subscription` (CC-035), que reasigna el endpoint a la cuenta
logueada.

## Regla de pruebas

La evidencia RED tiene que fallar por el comportamiento real que falta. Está prohibido fabricar RED o GREEN:
- comentando código;
- adulterando expectations;
- agregando ramas `if (test)`;
- usando mocks que eviten el camino de producción;
- debilitando una aserción solo para que pase CI.

Una **mutación** que rompe a propósito la regla para demostrar que el test la protege es válida si es local,
temporal, restaurada y sin commit, y se registra en la bitácora con la mutación exacta y las líneas resumen de RED y
GREEN. Mutaciones que quiten un control de seguridad con evidencia E2E: solo con el workflow `e2e-mutation` (T-347).
