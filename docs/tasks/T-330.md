# T-330 — publish_request conserva distancia NULL sin coordenadas ni centroides

- **Zona / dueño:** P1 · **Issue:** #220 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas):** CC-017 (#189)
- **Bloquea:** T-326 (#190 / PR #218); transitivamente T-313 y T-314
- **Contratos a leer:** `docs/contracts/CC-017.md`, contrato vigente de `app_private.request_cycle`

## Origen

Durante T-326 se introducen barrios activos sin centroide, estado permitido por CC-017.

La action `createDeliveryRequestAction` deja `route_distance_m` y `approx_distance_m` en null si faltan coordenadas explícitas y no hay centroides suficientes. Pero luego llama `publish_request`.

La implementación vigente de `app_private.request_cycle` calcula:

```sql
v_lat1 := coalesce(v_contacts.pickup_lat, v_pickup.centroid_lat);
v_lng1 := coalesce(v_contacts.pickup_lng, v_pickup.centroid_lng);
v_lat2 := coalesce(v_contacts.dropoff_lat, v_dropoff.centroid_lat);
v_lng2 := coalesce(v_contacts.dropoff_lng, v_dropoff.centroid_lng);

v_distance := case
  when v_lat1 = v_lat2 and v_lng1 = v_lng2 then 0
  else greatest(500, cálculo_haversine)
end;
```

Si faltan coordenadas efectivas, el cálculo queda null y PostgreSQL evalúa `greatest(500, null)` como 500. La RPC termina fabricando y persistiendo 500 m, contrario a CC-017.

## Objetivo

Alinear `publish_request` con CC-017:

- cuando existen las 4 coordenadas efectivas, conservar bounds, Haversine, redondeo y mínimo actuales;
- cuando falta cualquiera de las coordenadas efectivas porque no hay pin ni centroide, publicar conforme al resto de guards pero mantener distancia null;
- devolver `routeDistanceM: null` en ese caso;
- no modificar autorización, suscripción/piloto, rate limits, locks, estados, incidentes ni RLS.
