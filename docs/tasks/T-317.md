# T-317 — Alta de admin y enrolamiento del primer factor MFA

- **Zona / dueño:** P1 · **Issue:** #137 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-004, T-122, T-300
- **Contratos a leer:** `AGENTS.md`, `.agents/rules/**`, `docs/master-plan.md` §7 (seguridad del admin), `docs/tasks/T-004.md` (procedimiento de arranque `PR54-H03`), `src/features/admin/actions.ts` (`verifyMfaAction`, `requireAdminAal2`), `app_private.assert_admin_aal2`

## Objetivo
Hoy no hay forma de tener un admin operativo. El rol `admin` se asigna solo por SQL (master plan §7), pero el procedimiento de T-004 («para T-005») nunca llegó a un runbook. Además, ninguna tarea enrola el primer factor TOTP: T-122 solo verifica un factor que da por existente, y sin factor `verifyMfaAction` devuelve `INTERNAL_ERROR`. Esta tarea cierra ese recorrido completo: promover la cuenta → enrolar el TOTP → entrar con `aal2` → operar.

Decisión de Lautaro073 (2026-09-30): el primer enrolamiento lo hace el operador con una herramienta local de un solo uso (`tools/`), **no** una pantalla de la app. Una pantalla de enrolamiento abierta a cualquier admin sin factor dejaría llegar a `aal2` a quien tenga solo la contraseña.
