# T-333 — Cerrar carreras de Realtime y reconexión real en ofertas

- **Zona / dueño:** P2 · **Issue:** #229 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-204
- **Bloquea:** T-307 / #39 / PR #180
- **Contratos a leer:** `AGENTS.md`, `e2e/AGENTS.md`, `src/lib/hooks/use-realtime-invalidation.ts`, `src/features/requests/hooks/use-request-offers.ts`

## Origen

T-307 / PR #180 ya ejecuta `e2e/specs/notifications.spec.ts` en el gate trusted contra Vercel Preview + Supabase Develop.

Los runs trusted `37100304678` y `37138561471` reproducen dos fallos reales:

- Realtime: después del GET inicial y de insertar una oferta real, no ocurre una segunda GET del endpoint de ofertas dentro de 15 s.
- Reconnect: después de `offline -> online`, la query activa de ofertas no produce una segunda GET dentro de 15 s.
- El flujo offline que conserva el formulario sí queda GREEN.

T-333 corrige esos defectos en la capa T-204. **No se modifica el E2E de T-307 para fabricar verde.**

## Objetivo

Cerrar la carrera entre el GET inicial y la readiness de Supabase Realtime, y garantizar que una query activa de ofertas se refetchee realmente al recuperar conectividad.

Realtime debe seguir funcionando como **invalidación de queries**, nunca como escritura manual de caché.

## Defecto A — readiness de Supabase Realtime

La implementación actual crea el canal y llama `subscribe()`, pero no observa cuándo queda efectivamente listo.

Puede ocurrir:

```text
GET inicial termina
→ INSERT de oferta
→ canal todavía no SUBSCRIBED
→ evento perdido
→ no invalidateQueries
→ recién polling de 30 s podría verla
```

La corrección debe cerrar esa ventana con una invalidación catch-up al confirmar readiness del canal, sin `setQueryData`.

## Defecto B — reconnect

`useRequestOffers` declara `refetchOnReconnect: 'always'`, pero el navegador real no produce la segunda GET esperada en el E2E.

El unit test heredado no aísla correctamente el reconnect porque puede quedar satisfecho por el fetch inicial causado por `initialDataUpdatedAt: 0`.

Primero debe corregirse el control unitario para fijar baseline después del fetch inicial y exigir una llamada adicional posterior a `offline -> online`.

Si TanStack funciona al conducir directamente `onlineManager` pero el navegador real sigue sin provocar el refetch, puede agregarse un bridge global browser → `onlineManager`, sin duplicar el refetch manualmente.

## Pruebas RED obligatorias

### Realtime

El test de `useRealtimeInvalidation` debe capturar el callback de status de `subscribe()` y demostrar:

1. montar el hook;
2. completar setup;
3. antes de readiness no existe invalidación catch-up;
4. status `SUBSCRIBED` programa invalidación de las query keys del canal;
5. al vencer el debounce se llama `invalidateQueries`;
6. `setQueryData` permanece en cero;
7. un status distinto de `SUBSCRIBED` no invalida;
8. callback tardío después de unmount no invalida.

Mutación obligatoria: eliminar temporalmente el catch-up de `SUBSCRIBED` debe dejar el control RED. Restaurado, GREEN.

### Reconnect

El unit test debe:

1. montar `useRequestOffers`;
2. esperar el fetch inicial;
3. guardar baseline de llamadas;
4. transicionar `onlineManager.setOnline(false)`;
5. transicionar `onlineManager.setOnline(true)`;
6. exigir una llamada adicional posterior al baseline;
7. restaurar el estado global de `onlineManager` al finalizar.

Mutación obligatoria: `refetchOnReconnect: 'always'` → `false` debe dejar RED el control. Restaurado, GREEN.

Si se agrega bridge en `Providers`, debe tener su propio RED/GREEN verificando:

```text
window offline -> onlineManager.setOnline(false)
window online  -> onlineManager.setOnline(true)
estado inicial -> navigator.onLine !== false
```
