# T-416 — Seguridad: migrar Zod 3 a Zod 4

- **Zona / dueño:** P1 · **Issue:** #553 · **Fase:** Fase 4 — urgente (decisión técnica del agente con autorización de
  Lautaro073, 2026-10-26)
- **Dependencias (mergeadas en develop):** ninguna
- **Contratos a leer:** `.agents/rules/25-stack-y-patrones.md` (Zod es fuente de verdad de los tipos de entrada;
  dependencia aprobada) y `src/domain/rpc-contracts.ts`.

## Objetivo

Desde el 2026-10-26 el `audit` del CI falla en todas las ramas por GHSA-mrhx-c7xc-m3w5 (alto): Zod puede agotar la
memoria al validar colecciones grandes con límites. Afecta a `zod < 4.6.6` y no hay parche para la serie 3, así que
la corrección es migrar a Zod 4 (4.6.7). Se decidió migrar directamente, sin excepción temporal en el `audit`.

## Reconciliación de contratos

No cambia la semántica de ningún contrato: es un cambio de versión de la librería. Donde Zod 4 cambia el
comportamiento, se elige la API que conserva el de Zod 3:

- `z.string().uuid()` de Zod 4 exige UUID RFC 9562 (versión y variante); Zod 3 aceptaba cualquier `8-4-4-4-12`
  hexadecimal. Se usa `z.guid()`, que acepta exactamente ese formato, para no rechazar ids válidos de la base.
- Fechas ISO, `.strict()`, refinamientos y mensajes propios: se conservan o se pasan a su equivalente de Zod 4.

## Regla de pruebas
La evidencia RED tiene que fallar por el comportamiento real que falta. Está prohibido fabricar RED o GREEN:
- comentando código;
- adulterando expectations;
- agregando ramas `if (test)`;
- usando mocks que eviten el camino de producción;
- debilitando una aserción solo para que pase CI.

## Notas para quien retome

- Si una prueba cambia de resultado con Zod 4, primero se entiende por qué: solo se ajusta la prueba si el contrato
  sigue igual y el cambio es de forma (por ejemplo, el texto por defecto de un error de Zod).
