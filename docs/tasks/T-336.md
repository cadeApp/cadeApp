# T-336 — Navegación de retorno y 404 al home real de la sesión

- **Zona / dueño:** P1 · **Issue:** #247 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-118, T-201, T-334
- **Bloquea:** —
- **Contratos a leer:** `AGENTS.md`, `src/features/auth/guards.ts`, `src/features/auth/server.ts`, `src/features/notifications/offline/{error-view.tsx,not-found-view.tsx}`, `src/app/route-integrity.test.ts`

## Origen

Lautaro073 detectó el 2026-10-04 que varios controles de regreso/inicio y, en particular, el 404 terminan en `/`.

Eso es incorrecto como fallback genérico:

- `/` es la landing pública;
- un usuario autenticado debería volver al home real de la sesión que ya tiene;
- un usuario sin sesión debería ir a `/login`, no a la landing.

Casos confirmados en `develop`:

- `src/features/notifications/offline/not-found-view.tsx` → «Ir al inicio» usa `href="/"`;
- `src/features/notifications/offline/error-view.tsx` → «Ir al inicio» usa `href="/"`;
- `src/features/notifications/offline/error-views.test.tsx` fija hoy ese comportamiento esperando `href === '/'`.

T-118 y T-334 ya definen rutas canónicas por rol y onboarding. T-336 debe **reutilizar esa lógica** y no crear una segunda tabla de destinos.

## Decisión P1 — Lautaro073

Regla canónica:

- **sin sesión** → `/login`;
- **merchant autenticado**:
  - onboarding incompleto → `/merchant/onboarding`;
  - onboarding completo → `/merchant/dashboard`;
- **courier autenticado**:
  - onboarding incompleto → `/courier/onboarding/identity`;
  - onboarding completo → `/courier/feed`;
- **admin autenticado**:
  - AAL1 → `/login/mfa?redirectTo=%2Fadmin%2Fapplicants`;
  - AAL2 → `/admin/applicants`;
- merchant/courier con `consent_status` no activo conserva el flujo CC-007; T-336 no debe saltar esa regularización.

### Gateway de retorno

Para los controles genéricos de error/404, preferir **`/login` como gateway**:

- anónimo permanece en login;
- merchant/courier autenticado es redirigido por la guarda al destino de su sesión;
- admin autenticado debe usar el mismo circuito MFA/home que después del login y **no** caer en `/`.

No crear una nueva ruta `/home` salvo que la fase RED demuestre que `/login` no puede cumplir este contrato sin loops.

## Extensión R6 — middleware ejecutable

La validación real de Preview demostró que el gateway `/login` no estaba ejecutando las guards aunque la cookie Supabase estuviera presente.

Causa raíz detectada por revisión:

- la app usa `src/app`;
- el único middleware está en `/middleware.ts` en la raíz;
- Next.js 15 exige que, al usar `src`, el middleware quede dentro de `src`, al mismo nivel que `app`;
- el output de `next build` de CI no lista ningún Middleware;
- Vercel Preview no muestra ejecución de middleware y responde `GET /login 200` con sesión courier activa;
- el E2E Preview T-336 falla también después de una hard navigation.
