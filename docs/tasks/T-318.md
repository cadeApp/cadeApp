# T-318 — Mensajes claros y seguros cuando falla el registro

- **Zona / dueño:** P1 · **Issue:** #141 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-009
- **Contratos a leer:** `src/domain/errors.ts` (`DOMAIN_ERROR_CODES`, sin cambios), `src/features/auth/actions.ts` (`registerAction`), RPC `activate_account_consents`

## Objetivo
Cuando el registro falla, la pantalla mostraba siempre «Revisá los datos ingresados», aunque la causa fuera un rate limit o una falla del servicio. Esta tarea clasifica los rechazos de `supabase.auth.signUp` en errores de datos, rate limit y fallas del servicio, y muestra un mensaje distinto para cada uno, sin revelar si un email ya tiene cuenta.

Decisiones de Lautaro073 (2026-09-30, Ronda 1 de la PR #140):
- **1-A:** este bug es una tarea nueva. T-009 (issue #10, PR #60) queda cerrada.
- **2-A:** se preserva la anti-enumeración de Supabase. La respuesta sanitizada `user.identities = []` y los códigos `user_already_exists` / `email_exists` no se traducen en un mensaje que confirme que el email existe.

## Fuera de alcance
- Nuevos códigos de dominio o cambios en `src/domain/errors.ts` (requiere `contract-change`)
- Un flujo de «revisá tu email» que iguale la respuesta de un email nuevo y uno ya registrado
- Mostrar `error.message` de Supabase o cualquier detalle interno en la UI
- Reglas de contraseña nuevas en el schema

## DoD

- [ ] No revelar públicamente la existencia de cuentas: la respuesta sanitizada `identities: []`, `user_already_exists` y `email_exists` devuelven el mismo código que un dato no aceptado, no llaman `activate_account_consents` y la UI no contiene «ya existe», «email registrado» ni «cuenta existente».
- [ ] Rate limits muestran un mensaje específico.
- [ ] Errores inesperados muestran un mensaje de problema temporal.
- [ ] Excepciones o rechazos del Server Action cubiertos por test: se muestra `errorUnexpected` y no el detalle del error.

## Notas para quien retome
- Origen: con `admin@admin.com` / `12345678` en localhost, el registro devolvía el mensaje genérico. Supabase rechaza contraseñas débiles con `weak_password`.
- Residual conocido: un email nuevo sigue su flujo normal (redirige al onboarding) y uno ya registrado no. Igualar esas dos respuestas requiere un flujo de confirmación por email, fuera de alcance.
- El texto del error de datos no promete reglas de contraseña que el schema no impone (solo la longitud mínima es local; la política de Supabase puede cambiar).
- `error.message` solo se sigue mirando para la compatibilidad previa con `INVALID_SIGNUP_ROLE`, cubierta por test.
