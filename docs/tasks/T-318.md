# T-318 — Mensajes claros y seguros cuando falla el registro

- **Zona / dueño:** P1 · **Issue:** #141 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-009
- **Contratos a leer:** `src/domain/errors.ts` (`DOMAIN_ERROR_CODES`, sin cambios), `src/features/auth/actions.ts` (`registerAction`), RPC `activate_account_consents`, `supabase.auth.signUp` (respuesta sanitizada con `user.identities = []`)

## Objetivo
Cuando el registro falla, la pantalla mostraba siempre «Revisá los datos ingresados», aunque la causa fuera un rate limit o una falla del servicio. Esta tarea clasifica los rechazos de `supabase.auth.signUp` en errores de datos, rate limit y fallas del servicio, con un mensaje distinto para cada uno, y preserva la anti-enumeración de Supabase: nadie puede averiguar desde el cliente si un email ya tiene cuenta.

Decisiones de Lautaro073 (2026-09-30, Ronda 1 de la PR #140):
- **1-A:** este bug es una tarea nueva. T-009 (issue #10, PR #60) queda cerrada.
- **2-A:** se preserva la anti-enumeración de Supabase. Ante un email ya registrado, Supabase responde con éxito y un usuario sanitizado (`user.identities = []`) cuando la confirmación por email está activa, y puede responder `user_already_exists` / `email_exists` cuando no lo está. La app no puede convertir ninguna de esas señales en algo que el cliente distinga de un alta nueva válida.

## DoD
- [ ] Anti-enumeración: toda señal de cuenta existente (la respuesta sanitizada con `error: null` y `data.user.identities = []`, y los códigos `user_already_exists` y `email_exists`) produce para el cliente un resultado indistinguible de un alta nueva válida: mismo `ok`, mismos campos públicos y shape, misma navegación, ningún id real o sanitizado que permita distinguirlos y ningún texto que confirme la cuenta; en ninguno de esos casos se llama `activate_account_consents`.
- [ ] Prueba comparativa de anti-enumeración entre cuatro caminos con el mismo input: alta nueva válida, respuesta sanitizada `identities: []`, `user_already_exists` y `email_exists`. Falla si cualquiera de los tres últimos difiere del alta nueva en `ok`, en el shape o los campos públicos, en la navegación del formulario, si filtra un id o si muestra texto equivalente a «ya existe». También comprueba que esos tres no llaman `activate_account_consents`. No alcanza con buscar frases prohibidas.
- [ ] Ningún texto de la UI confirma que un email ya tiene cuenta («ya existe», «email registrado», «cuenta existente» o equivalentes), para ningún resultado de `registerAction`.
- [ ] Errores genuinos de registro clasificados con allowlist, separados del camino anti-enumeración y sin confundir fallos operativos con errores de datos: `weak_password`, `email_address_invalid` y `validation_failed` → `VALIDATION_ERROR`; `over_email_send_rate_limit` y `over_request_rate_limit` → `RATE_LIMITED`; cualquier otro código, desconocido o ausente → `INTERNAL_ERROR`. `user_already_exists` y `email_exists` no pasan por este mapper como error: siguen el camino del primer ítem.
- [ ] Rate limits muestran un mensaje específico.
- [ ] Errores inesperados muestran un mensaje de problema temporal.
- [ ] Excepciones o rechazos del Server Action cubiertos por test: se muestra `errorUnexpected` y no el detalle del error.
- [ ] Nunca se muestra `error.message` remoto. Solo se sigue leyendo para la compatibilidad previa con `INVALID_SIGNUP_ROLE`, cubierta por test.
- [ ] Sin códigos nuevos en `src/domain/errors.ts`.
- [ ] Pruebas RED reales antes de cada corrección (mutaciones aplicadas exactamente una vez y restauradas).
- [ ] `pnpm typecheck && pnpm lint && pnpm test`
- [ ] Sin cambios fuera de "Archivos permitidos"

## Notas para quien retome
- Origen: en localhost, el registro con un email de prueba y la contraseña `12345678` mostraba el mensaje genérico. Supabase rechaza contraseñas débiles con `weak_password`.
- Implementación en curso: PR #142 (`feat/T-318-register-errors`). Espera al merge de esta ficha; después se mergea `origin/develop` en esa rama (sin rebase, amend ni force-push) y `docs/tasks/T-318.md` y `docs/implementation-plan.md` salen de su diff.
- Hoy un alta nueva devuelve `ok: true` con `userId`, `role` y `redirectTo`, y el formulario navega a `redirectTo`. Para cumplir el primer ítem del DoD, la respuesta sanitizada y los dos códigos de cuenta existente tienen que devolver el mismo resultado público (un camino neutral de éxito, sin código de dominio nuevo); si un campo como `userId` no puede ser igual en todos los casos, no debe llegar al cliente en ninguno. `src/features/auth/**` está permitido para ajustar el resultado y el formulario.
- El texto del error de datos no promete reglas de contraseña que el schema no impone (solo la longitud mínima es local; la política de Supabase puede cambiar).
- Referencia de la respuesta sanitizada: `sanitizeUser` en https://github.com/supabase/auth/blob/master/internal/api/signup.go.
