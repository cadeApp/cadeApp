## Decisión P1 — PR #360 / PR360-R04 (2026-10-17): opción C

Lautaro073 autorizó **C** para resolver el fallo E2E de integración con T-361: el comercio debe visualizar el medio de pago en el detalle del viaje, sin depender de mensajes de WhatsApp.

- **Viaje con una entrega:** mostrar `Medio de pago: <etiqueta>` visible en el resumen del viaje / Card `Repartidor asignado`. Si existe un único drop, tomar su `recipientPaymentMethod`; en formato legacy sin drops, usar el dato del viaje.
- **Viaje multi-drop:** mostrar dentro de la tarjeta de **cada entrega** el `recipientPaymentMethod` de ese `drop`. No reutilizar un único valor global cuando distintos destinatarios tengan medios distintos.
- Usar `formatRecipientPaymentMethod` ya existente, con `cash → Efectivo`, `transfer → Transferencia`, `to_agree → A coordinar`. No hardcodear valores ni inventar pagos.
- **Pruebas nuevas autorizadas:** `src/features/trips/components.test.tsx` únicamente para verificar que el método correcto es visible (single cash/transfer/to_agree; multi-drop heterogéneo, scoping por tarjeta) y que el cambio rompe en RED real sin el campo antes de quedar GREEN tras el arreglo. El spec `e2e/specs/main-flow.spec.ts` debe mantener el oráculo de dos sesiones/DB, monto, contactos, reload/back y verificar el método visible dentro de la Card correcta, antes y después de recargar.
- **Seguridad y límites:** conservar T-361: el mensaje de WhatsApp **al cliente** NO incluye importes ni medio de pago. No alterar `src/lib/whatsapp.ts`, código server, contratos, RPC, RLS, SQL, migraciones, dependencias, fixtures ni controles de CI. El cambio es de UI de comercio y pruebas relacionadas; no modifica el contrato de datos.
- **Evidencia:** origen RED [run 38965095162](https://github.com/cadeApp/cadeApp/actions/runs/38965095162), SHA `c4eb0c4b`, test T-359 en `main-flow.spec.ts:257` sin `Medio de pago: Efectivo`; tras arreglo exigir nueva CI y E2E real GREEN sobre HEAD final, sin falsear assertions, fixtures, mocks, snapshots ni timeouts. No marca el DoD como completo por esta autorización.

Esta aprobación **sólo amplía el archivo de test indicado**, no libera los demás archivos fuera de alcance. PR #360 sigue requiriendo revisión independiente y decisión de merge de Lautaro073.

## Decisión P1 — PR #360 / PR360-R05 (2026-10-17): opción C, misma PR

Lautaro073 autorizó explícitamente **la opción C y que la corrección se implemente en la misma PR #360** (`feat/T-359-detalle-merchant-post-aceptacion`). Esta autorización es excepcional y estrictamente acotada a un test E2E propiedad de T-366, que quedó incompatible con la guarda H03 de T-359 al integrarse `develop`.

- **Única excepción de archivo autorizada para R05:** en `e2e/specs/request-states.spec.ts`, exclusivamente el caso `T-366 (§5.1): Solicitud vencida se reconcilia al consultar historial y aparece como Expirada sin esperar sweep`, cambiar la expectativa global de botón visible a **ausencia estricta del botón exacto** (`await expect(page.getByRole('button', { name: /^aceptar$/i })).toHaveCount(0);`). Conservar sin modificar las aserciones `Expirada`, `Ofertas recibidas`, rechazo RPC `REQUEST_EXPIRED`, concurrencia, auditoría, aislamiento, paginación, historial Vencidas/Todas y demás casos de `request-states.spec.ts`.
- **Pruebas obligatorias:** registrar el RED genuino existente de Playwright [run 39011178930](https://github.com/cadeApp/cadeApp/actions/runs/39011178930), y comprobar GREEN real del **E2E completo y T-366** para el nuevo SHA, junto al E2E T-359 y los tests unitarios H03. No hacer `.skip`, `.only`, `continue-on-error`, ni manipular aserciones para falsear PASS.
