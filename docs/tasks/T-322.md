# T-322 — Hotfix de registro: confirmación de email antes del onboarding

- **Zona / dueño:** P1 · **Issue:** #165 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-318, T-320
- **Contratos a leer:** `src/features/auth/actions.ts` (`registerAction`), `src/features/auth/schemas.ts` (`registerSchema`), `src/app/auth/confirm/route.ts`, `src/features/auth/guards.ts`, `src/features/legal/documents.ts`, `src/features/legal/legal-red.test.ts`, `supabase/migrations/20260922031435_schema_v1.sql` (`handle_new_user`), policies de `storage.objects` para `courier-docs`

## Origen

Prueba manual en staging posterior a T-320: al crear una cuenta courier con **Confirm email = ON**, la UI navegó inmediatamente a `/courier/onboarding/identity` antes de abrir el email. Esa página no encontró usuario y renderizó `IdentityForm` con el fallback `temp-courier`. Al subir el DNI, Storage respondió `403 new row violates row-level security policy`.

La RLS no es el problema: exige correctamente que el path sea `courier/<auth.uid()>/...`. El bug es que la aplicación muestra onboarding antes de tener una sesión confirmada.

Además, el schema/action ya admiten `displayName` y `phone` y `handle_new_user()` ya los persiste en `profiles.display_name` y `profiles.phone`, pero el formulario no los pide ni los envía. `get_trip_details` usa esos campos para mostrar al comercio el nombre y contacto del courier post-asignación.

Decisión de Lautaro073 (2026-10-01): **nombre y teléfono se piden en el momento del registro**, no en el onboarding.

## Decisión de alcance P1 — 2026-10-01 (PR167-R01)

Lautaro073 eligió la **opción A** ante la contradicción detectada por la revisión entre T-322 y la Política de Privacidad v1.0:

- T-322 mantiene `displayName` y `phone` como **obligatorios** en el registro.
- Se autoriza la ampliación mínima de alcance a `src/features/legal/documents.ts` y `src/features/legal/legal-red.test.ts` para que la política publicada describa el comportamiento real.
- La Política de Privacidad debe publicarse como una **versión nueva (`1.1`)**, con fecha/etiqueta de actualización correspondiente; no se reescribe silenciosamente el contenido identificado como v1.0.
- El cambio legal se limita a reflejar que nombre visible y teléfono son obligatorios en el registro y las consecuencias de no proporcionarlos. No se aprovecha T-322 para reescribir otras secciones legales.
- Las aceptaciones históricas de versiones anteriores se conservan; no se alteran ni eliminan filas históricas de `consents`.
- Decisión P1 — 2026-10-01 (PR167-A01): se autoriza exclusivamente `src/features/courier-onboarding/actions.test.ts` para sincronizar las fixtures de Privacy `1.1`; no se amplía el alcance a `src/features/courier-onboarding/actions.ts` ni a otros archivos de onboarding.

## Objetivo

El flujo debe ser:

`Crear cuenta → estado neutral “Revisá tu email” → abrir email → /auth/confirm → sesión → destino del rol/onboarding`.

Nunca se renderiza onboarding de courier con un identificador inventado.
