# T-315 — Deploy a Vercel desde GitHub Actions (staging y producción)

- **Zona / dueño:** P1 · **Issue:** #127 · **Fase:** Fase 3 (Calidad, operación y salida)
- **Dependencias (mergeadas en develop):** T-003
- **Contratos a leer:** `AGENTS.md`, `.agents/rules/**`, `.github/workflows/migrate.yml`, `vercel.json`

## Objetivo
Hoy ningún workflow despliega: `VERCEL_TOKEN`, `VERCEL_ORG_ID` y `VERCEL_PROJECT_ID` (environments `staging` y
`production`) están cargados pero nadie los usa, y la integración Git de Vercel no está conectada. Sin deploy, T-300
no puede verificar el deployment de staging ni `/api/health`. Este workflow despliega después de que `migrate`
termine verde: primero la base, después la app.

## Archivos permitidos
- `.github/workflows/deploy.yml`
- `.github/workflows/verify-workflows.test.mjs`
- `docs/tasks/T-315.md`
- `docs/tasks/log/T-315.md`
- `docs/revision-pr/**`

## Fuera de alcance
- Cambiar `migrate.yml`, `ci.yml` o código de producto
- Crear, modificar o leer variables de entorno del proyecto en Vercel desde el workflow
- Copiar secretos, tokens o URLs privadas al repo, issue o bitácora

## Dependencias nuevas permitidas
- `vercel@61.0.0` como herramienta de CI vía `pnpm dlx` (no entra a `package.json` ni al lockfile)

## DoD
- [ ] `deploy.yml` se dispara con `workflow_run` de `migrate` y solo despliega si ese run terminó `success` por `push`.
- [ ] `deploy-staging` (rama `staging`, environment `staging`) hace `vercel pull` → `vercel build --prod` →
      `vercel deploy --prebuilt --prod` sobre el proyecto de staging, con el commit exacto del run de `migrate`.
- [ ] `deploy-production` (rama `main`, environment `production`) exige que el run lo haya iniciado Lautaro073, igual
      que `migrate-production`.
- [ ] Después del deploy, un chequeo de `/api/health` con reintentos falla el job si no responde HTTP 200.
- [ ] Actions fijadas por SHA; la versión del CLI de Vercel fijada; `concurrency` sin cancelar despliegues en curso.
- [ ] `verify-workflows.test.mjs` cubre orden después de `migrate`, compuerta de producción, versión fijada y health.
- [ ] `pnpm typecheck && pnpm lint && pnpm test`

## Notas para quien retome
- El proyecto de Vercel de staging es `cadeapp-staging` (`https://cadeapp-staging.vercel.app`, bitácora de T-310).
  Es un proyecto propio, así que se despliega con `--prod` y su dominio de producción queda como URL estable de
  staging.
- Las variables de runtime salen del proyecto de Vercel (`vercel pull`), no de los secretos de GitHub.
- `workflow_run` toma el workflow de la rama por defecto (`develop`): `deploy.yml` queda activo al mergearse ahí.
